<objective>
Phase 22.5 was inserted into v0.5 (sha fc7b048) as a small, prerequisite-style frontend phase that closes a typed-error gap surfaced by the 21-01 audit (Section 4 row "Missing `ApiError.code`-based branching on the four typed values"). The v0.4 backend already returns a typed `code` field on its `ApiError` envelope (current values: `SESSION_ALREADY_ACTIVE`, `SESSION_ALREADY_FINISHED`, `SESSION_FINISHED`, `SET_NUMBER_DUPLICATE`), but the frontend's `client.ts:14-23` `ApiError` class does not carry that field — the only typed slots are `status: number` and `body: unknown`. Today no consumer reads `error.body.code`; the only `ApiError` consumer in the app branches on `error.status` (`(auth)/login/page.tsx:38-44`). Without a shared helper, every downstream phase that needs to disambiguate (notably 25-03 session-execution, where `clientSetId` idempotency replay and finished-session writes both can raise distinct codes) would have to either re-implement the parsing or fall back to brittle `error.message` string matching.

This plan delivers exactly the helper, no consumer migration. Two outputs:

1. **Schema + class extension.** Extend `apiErrorSchema` (`frontend/src/lib/api/schemas.ts:3-13`) with `code: z.string().optional()` so the Zod parse populates the field when the backend includes it and remains backward-compatible with payloads that omit it (legacy 4xx surfaces). Extend the `ApiError` class (`frontend/src/lib/api/client.ts:14-23`) with a `public readonly code: string | undefined` field, derived once at construction time from the parsed envelope. Existing consumers continue to work unchanged because both `body` and `status` stay where they are; the new `code` is additive.

2. **Typed helper module.** Create `frontend/src/lib/api/api-error-codes.ts` (NEW) exporting (a) a `KnownApiErrorCode` union type covering the 4 v0.4 values, (b) a frozen `ApiErrorCode` constants object so consumers write `ApiErrorCode.SESSION_FINISHED` instead of magic strings, (c) a `KNOWN_API_ERROR_CODES` array used at runtime for `isKnownApiErrorCode(value)`, and (d) two helpers — `isApiError(err)` (instanceof guard, narrows `unknown -> ApiError`) and `isApiErrorWithCode(err, code)` (narrowed guard that asserts both `instanceof ApiError` AND `err.code === code`). Plus `apiErrorCodeMessageKey(code)` returning the i18n key path under a new `errors.api.*` namespace, defaulting unknown codes to `errors.api.generic`. The file is forward-compat: an unknown backend code (added later) parses cleanly because the Zod schema accepts any string; the helper just falls through to the generic key.

Tests: vitest unit suite for the helper module covering all three guards, the message-key mapping for the 4 known codes plus a forward-compat unknown code, and the `apiErrorSchema` regression that confirms `code` is optional. Augment `client.test.ts` (existing 3 it-blocks) with one new it-block that asserts `ApiError.code` is populated when the backend response carries `code` and is `undefined` when absent. No consumer page is migrated in this plan — that's the job of phases 25-03 and 22-01 (login page can adopt later; orchestrator's choice). Out of scope: i18n message string definitions (this plan declares the key paths; the actual translations land per-feature with the consumer migration; placeholder generic key lands now so unknown-code path resolves to a real translation).

The plan is intentionally narrow: pure frontend lib + tests; no backend, no migrations, no protected files, no `package.json` touch, no consumer wiring beyond the augmented `client.test.ts` regression. One sub-plan per audit verdict.
</objective>

**Constraining decisions (this planner; locked at plan time):**

- **`apiErrorSchema.code` is `z.string().optional()`, NOT `z.enum([...])`.** Forward-compat: a backend that adds a new code in v0.6 (e.g. `WORKOUT_PLAN_LOCKED` for Phase 24-04 plan-edit conflicts) would break a `z.enum([...])` schema parse. The schema must accept any string. Typing for known codes lives in the helper module via constants + a runtime predicate.
- **`ApiError.code` is `string | undefined`, NOT `KnownApiErrorCode | undefined`.** Same forward-compat argument: the class is the boundary between parsed-untrusted-wire-data and the rest of the app; widening to a known-only union would silently drop unknown codes from `error.code` and re-introduce the brittle "is the field set or not" check the helper is meant to eliminate. Consumers narrow at the call site via `isApiErrorWithCode(err, ApiErrorCode.SESSION_FINISHED)`.
- **`ApiErrorCode` is an `as const` object, not a TypeScript `enum`.** TS enums emit runtime objects with bidirectional mapping that confuses tree-shaking and create surprising `Object.values` enumeration order. The `as const` pattern is what the rest of the codebase uses (e.g. existing `LINKS` arrays in `nav.tsx`).
- **`isApiError(err): err is ApiError` uses `instanceof ApiError`, NOT a duck-type check.** The helper imports `ApiError` from `@/lib/api/client`. This is fine because `api-error-codes.ts` lives in the same feature folder and is a strict consumer of `client.ts`; the dep direction is `api-error-codes.ts -> client.ts` only (no cycle).
