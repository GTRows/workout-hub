Create `V27__session_sets_is_pr.sql` with two statements in order:

  1. `ALTER TABLE session_sets ADD COLUMN is_pr BOOLEAN NOT NULL DEFAULT false;`
  2. Backfill via single CTE (drafted in audit Section 5):

      ```sql
      WITH ranked AS (
          SELECT
              ss.id AS set_id,
              ROW_NUMBER() OVER (
                  PARTITION BY ws.user_id, ss.exercise_id
                  ORDER BY
                      CASE
                          WHEN ss.weight_kg IS NULL OR ss.reps_done <= 0 THEN NULL
                          WHEN ss.reps_done = 1 THEN ss.weight_kg
                          ELSE ss.weight_kg * (1 + ss.reps_done::numeric / 30)
                      END DESC NULLS LAST,
                      ss.created_at ASC
              ) AS rk
          FROM session_sets ss
          JOIN workout_sessions ws ON ws.id = ss.session_id
          WHERE ss.completed = TRUE
            AND ws.ended_at IS NOT NULL
      )
      UPDATE session_sets
      SET is_pr = TRUE
      FROM ranked
      WHERE session_sets.id = ranked.set_id
        AND ranked.rk = 1;
      ```

      The Epley expression is inlined (Postgres has no UDF for it); `setScale(3, HALF_UP)` is irrelevant for ordering because comparison is on the raw `numeric`. The `created_at ASC` tiebreak ensures the earliest set wins ties (matches `PrDetector.beatsPriorBest` strict-greater behavior — equal Epley does NOT beat prior, so the first-appearance set is the one durably flagged).

      DO NOT add a partial unique index on `(session_id, exercise_id) WHERE is_pr` — multiple PRs across sessions for the same `(user, exercise)` pair are explicitly out-of-shape; uniqueness is enforced by application logic in Task 3, not at the schema level. The backfill produces at most one `is_pr=true` row per `(user, exercise)`, but the schema permits the application to transiently violate this during update-path re-election.

      WHY no UDF: existing migrations (V25, V26) use only inline SQL; introducing a function for Epley would land schema bloat and a follow-up ownership question. Inline arithmetic matches `analytics/AnalyticsService.epley` semantics exactly because Postgres `numeric` arithmetic is associative and the `* (1 + reps/30.0)` expression has no rounding hazard at the column scale (`weight_kg NUMERIC(6,2)`).
