# Phase 37 - Plan 01: Redesign StructuredLoggingTest to boot the full app so prod logging activates

**Milestone:** v0.6 Operational Maturity (closing phase)
**Phase:** 37 - structured-logging-test-fix
**Plan:** 37-01 (only sub-plan; closes deferred i-9)
**Status:** Not started
**Author date:** 2026-05-09

## Goal

Re-enable `backend/src/test/java/com/workouthub/common/logging/StructuredLoggingTest.java`
by replacing its broken minimal-context harness with one that boots the real
`WorkoutHubApplication` under the `prod` profile. The test must prove two contract
assertions from `docs/SELF_HOSTED_CONTRACT.md` section 8 actually hold against the
running production logging pipeline:

1. **Shape:** stdout lines are valid JSON containing both a `message` field and an
   ISO-8601 `@timestamp`.
2. **Deny-list masking:** an MDC entry whose key is `authorization` (deny-listed in
   `SecretMaskingStructuredLoggingCustomizer`) never leaks its value into the JSON
   stdout.

The disabled test today (Phase 3 Plan 01 artifact, `@Disabled` since v0.3) uses a
`@SpringBootConfiguration`-only `MinimalConfig` static class with
`webEnvironment = NONE` and `@ActiveProfiles("prod")`. That harness does not trigger
Spring Boot's `LoggingApplicationListener` reconfiguration to ECS structured logging
because the listener only fires for full Spring Boot application startup — not for a
trimmed test that bypasses `WorkoutHubApplication`. The result: the test ran with the
default human-readable Logback layout, found no JSON line in captured output, and was
disabled with a tracking note.

This plan removes the disable, moves the test onto the same Testcontainers Postgres
plumbing the rest of the integration suite uses, and pins the prod-profile log capture
to the real production logging configuration.

## Architecture Decision: Boot WorkoutHubApplication via Testcontainers + @ActiveProfiles("prod"); capture stdout with OutputCaptureExtension

**Decision:** Convert `StructuredLoggingTest` from a `@SpringBootConfiguration`-only
unit test into a full Spring Boot integration test that:

- Inherits the Testcontainers Postgres scaffolding from
  `backend/src/test/java/com/workouthub/support/AbstractIntegrationTest.java`
  (so the prod profile's Hibernate `ddl-auto: validate` + Flyway can boot against a
  real Postgres rather than failing on `SPRING_DATASOURCE_URL`).
- Uses `@SpringBootTest(classes = WorkoutHubApplication.class, webEnvironment = NONE)`
  so the entire production logging pipeline (`LoggingApplicationListener` ->
  ECS console formatter -> `SecretMaskingStructuredLoggingCustomizer`) is wired
  exactly as it would be in `docker compose up`.
- Activates the prod profile via `@ActiveProfiles("prod")` so
  `application-prod.yml` is merged on top of `application.yml` and the
  `logging.structured.format.console=ecs` switch fires.
- Continues to use Spring Boot's `OutputCaptureExtension` because the existing test
  already documented (in its class JavaDoc) that `OutputCaptureExtension` is the only
  capture mechanism that wraps stdout *before* the Logback `ConsoleAppender` opens its
  reference to the original `PrintStream`. A `@BeforeEach`-based `System.setOut`
  swap demonstrably fails for Logback structured output and is not in scope.
- Suppresses `JwtAuthenticationFilter` / `UserIdMdcFilter` side effects by using
  `WebEnvironment.NONE` (no servlet container, no inbound requests). Logging emission
  happens via direct SLF4J `Logger.info` calls inside the test methods, which is what
  the deny-list masking contract is actually scoped to.

**Why this is the right call here:**

- **Real activation, not a mock.** The previous attempt failed because it stopped one
  layer short of triggering `LoggingApplicationListener`. Booting
  `WorkoutHubApplication` directly is the smallest change that closes that gap.
- **Self-Hosted Contract fidelity.** Section 8 of the contract says prod must emit
  ECS JSON with a deny-list. The test now exercises the same code path operators see
  in production, not a divergent harness.
- **Reuses existing test infra.** `AbstractIntegrationTest` already pre-starts a
  reusable Postgres container (`withReuse(true)`) and registers `app.jwt.*`,
  `app.cors.*`, and datasource properties via `@DynamicPropertySource`. No new
  Testcontainers wiring needed.
- **No protected-file edits.** Plan touches one test class and (optionally) one new
  test-only support class. `pom.xml`, `application.yml`, `application-prod.yml`,
  `compose.yml`, `.github/workflows/**`, and `scripts/**` are all UNTOUCHED.
- **Local-Maven-gap aware.** Per repo memory, backend `mvn` is unavailable on this
  Windows host. The plan's verification gate is structural (file presence, expected
  Java symbols, no `@Disabled`) plus a CI run on push; no local mvn execution is
  assumed.

**Rejected alternatives:**

1. *Keep `@SpringBootConfiguration` + `MinimalConfig` and try to coax
   `LoggingApplicationListener` with explicit `SpringApplicationBuilder`* —
   rejected. Brittle: depends on internal Spring Boot startup ordering and stops
   working on every minor 3.5.x bump. The full-app boot is the supported path.
2. *Use a programmatic `LoggerContext` rebuild inside the test* — rejected. The
   contract is "the prod profile must emit ECS JSON", not "the customizer class
   compiles". Reconfiguring Logback by hand inside the test verifies the wrong
   thing and would silently still pass after a real-world regression.
3. *Use `webEnvironment = RANDOM_PORT` and emit a fake HTTP request to drive the
   logging chain through `UserIdMdcFilter`* — rejected for THIS plan. Adds servlet
   container startup cost and an HTTP client just to prove the JSON shape. The
   `UserIdMdcFilter` MDC propagation is already exercised by every other
   `*IntegrationTest` indirectly (their stdout is JSON in CI when prod profile is
   active in future test runs); a dedicated filter test belongs in a separate
   sub-plan if the operator ever wants it.
4. *Capture stdout via a custom `TeeOutputStream` redirect inside `@BeforeEach`* —
   rejected. The original Phase 3 plan tried this; the existing class JavaDoc
   already documents why it does not work (`ConsoleAppender` caches the original
   `System.out` reference at appender-init time, before any test code runs).
   `OutputCaptureExtension` is the canonical Spring Boot solution.
5. *Move the assertions into a Logback `Appender` mock that intercepts events
   before they hit stdout* — rejected. That tests Logback wiring, not the
   prod-profile JSON-on-stdout contract. We need the actual stdout bytes.
6. *Drop the test entirely and rely on operator inspection at deploy time* —
   rejected. i-9 is explicit about reopening with a redesign, not a deletion. A
   regression in `application-prod.yml` (e.g. a future merge that reverts
   `logging.structured.format.console: ecs`) must fail CI, not first-deploy.
7. *Write a new `application-test-prod.yml` profile that mirrors prod minus
   Postgres* — rejected. Adds a parallel config surface that drifts. Using the
   real `application-prod.yml` against a Testcontainer Postgres preserves
   single-source-of-truth.

   `prodMasksDenyListedMdcFields`) intact. Their bodies are correct; the only
   reason they fail today is the harness, not the assertions.

   helper as-is. It correctly walks the captured output backwards looking for a
   JSON line containing the needle.

## Risk + Mitigation

| Risk | Probability | Mitigation |
|---|---|---|
| Boot under `prod` profile fails because `application-prod.yml` references a customizer class but Hibernate `ddl-auto: validate` cannot connect | LOW | `AbstractIntegrationTest` already supplies a Testcontainers Postgres URL via `@DynamicPropertySource` before context refresh. Flyway runs against the container; `ddl-auto: validate` then validates against the live schema. This is the same path every `*IntegrationTest` already takes. |
| Spring banner pollutes captured stdout and the JSON-line walker matches a banner line | LOW | Plan adds `properties = { "spring.main.banner-mode=off" }` to suppress the banner. The `lastLineMatching` helper additionally only matches lines starting with `{`, which the banner does not. Belt-and-braces. |
| `OutputCaptureExtension` does not see Logback output because Logback caches `System.out` reference | NONE | `OutputCaptureExtension` installs its tee on the JVM's `System.out` *before* the test class loads, which is *before* `LoggingApplicationListener` initializes Logback's `ConsoleAppender`. This is the documented Spring Boot test idiom for capturing structured logs. The original test class JavaDoc (kept as-is) already explains why this works and the alternative does not. |
| `@ActiveProfiles("prod")` activates a feature outside logging that fails (e.g. a hypothetical prod-only health check) | LOW | Reading `application-prod.yml`: it ONLY overrides `logging.structured.*`, `logging.level.*`, `logging.include-application-name`. No other prod-only config exists in this repo as of v0.6. If a future prod-profile config is added, the contract section 8 test will catch it via integration-test failure, which is the desired behaviour. |
| Adding another Testcontainers consumer to the suite slows down CI noticeably | LOW | `AbstractIntegrationTest` declares `withReuse(true)` and the static container starts once per JVM. The test adds one extra Spring context refresh (~3-5s in CI), no new container. |
| The plan's harness still does not activate ECS in the test (i.e. the redesign also fails) | LOW-MEDIUM | If the CI run shows the test still finds no JSON line, escalate as a Rule 3 deviation. Diagnostic next step: dump `LoggingSystem.get(getClass().getClassLoader()).getClass().getName()` inside the test to confirm Spring Boot's `LogbackLoggingSystem` is active, and inspect Spring Boot 3.5's `LoggingApplicationListener` source for any preconditions the Testcontainers harness violates. |
