<objective>
Phase 25.5 was inserted into v0.5 (sha f026474) as a small, prerequisite-style frontend phase that closes a typed-payload gap surfaced by the 21-01 audit (Section 4d "Frontend wrappers calling endpoints that diverge from v0.4 contract" + Section 6 net-new phases row `phase-25.5-session-set-zod-schema`). Phase 25-01 already extended the `addSetRequestSchema` / `updateSetRequestSchema` discipline to the `POST /api/sessions/{id}/sets` and `PUT /api/sessions/{id}/sets/{setId}` boundaries (`schemas.ts:112-129`); 25-04 finished `updateSetRequestSchema`. The remaining wrappers in `endpoints.ts` that bypass Zod validation today are concentrated in two places: (a) the export/import surface (`fetchFullExport` returns `unknown`; `importFullDump` returns a hand-written `ImportResult` type alias at `endpoints.ts:369-378` rather than a schema-derived type); and (b) the push-subscription helper in `subscribe.ts:35` which validates neither the VAPID public-key response nor the outbound `SubscribeBody`. The audit Section 4d names two of these explicitly:

- `importFullDump` (`endpoints.ts:369-386`) - "uses a hand-written `ImportResult` type rather than a Zod schema. `warnings` and `suggestions` are optional `string[]`, so a backend regression that drops these fields silently passes."
- `subscribePush` (`subscribe.ts:35-38`) - "calls `GET /api/push/vapid-public-key` and `POST /api/push/subscribe` with inline `VapidResponse` and `SubscribeBody` types instead of Zod schemas in `frontend/src/lib/api/schemas.ts`. Drift risk if the backend wire format changes."

This plan delivers EXACTLY the schema extension to those two surfaces - one schema per backend response DTO, plus an outbound request schema for the push subscribe body. The audit is followed verbatim: `fetchClaudeSummary` is INTENTIONALLY left untyped (Section 4d explicitly classifies it as "intentionally untyped pass-through" with PASS verdict because no consumer reads fields - `export-client.tsx:51-56` writes the body straight to `downloadJson`). `fetchSectionExport` is also INTENTIONALLY left untyped because each of its 5 sections returns a different slice of `FullExportDto` (a discriminated-union schema would either over-constrain to one section or duplicate every nested record); the audit gives no verdict against this wrapper. `fetchSessionsCsv` returns `text/csv` via `api.raw` and is correctly typed as `string` (CSV is not a Zod target).

Plan-locked: the backend's secondary constructor (`ImportResultDto.java:15-24`) defaults `warnings` and `suggestions` to `List.of()` when absent at construction time, so the wire payload may omit them OR send `[]`; both must parse. Keeping them `optional()` (rather than `default([])`) is the conservative choice that matches the existing inline `ImportResult` shape (`endpoints.ts:369-378`) and avoids changing the public symbol's runtime semantics.

**Constraining decisions (this planner; locked at plan time):**

- **`importResultSchema.warnings` and `.suggestions` are `z.array(z.string()).optional()`, NOT `.default([])`.** The backend's secondary constructor (`ImportResultDto.java:15-24`) defaults to `List.of()` BEFORE Jackson serialization, so the wire payload from the live backend would carry `[]` for both fields when no warnings exist. However, the existing inline `ImportResult` type at `endpoints.ts:369-378` declares both as `string[] | undefined` (optional, not defaulted), and the consumer `export-client.tsx:300, 312` checks `r.warnings && r.warnings.length > 0` (handles both undefined and empty array). Promoting to `default([])` would silently transform `undefined` -> `[]` at parse time, which CHANGES the runtime semantics for any caller that asserts `=== undefined`. The conservative migration is `.optional()` with no default; consumers continue to handle both shapes.
- **`fullExportSchema` numeric fields backed by Java `BigDecimal` use `z.number()`, not `z.string()`.** Jackson's default serialization for `BigDecimal` is a JSON number unless `WRITE_BIGDECIMAL_AS_PLAIN` is configured to emit a string. The backend uses default Jackson config (verified at audit time via the absence of any JsonComponent/SerializationFeature override in `JacksonConfig`); BigDecimal serializes as a number. Drift risk if a future backend phase opts into string serialization for BigDecimal: the schema parse will fail loudly, surfacing the drift at the boundary. Acceptable.
- **`fullExportSchema` Java `Instant` and `LocalDate` fields use `z.string()`, not `z.string().datetime()` or `z.string().date()`.** The Zod 3.x `.datetime()` validator is strict ISO-8601 with optional offset; `.date()` requires `YYYY-MM-DD`. Both would catch drift but also brittle the schema against any backend Jackson config quirk. The audit-aligned conservative choice is `z.string()` matching the existing `schemas.ts` pattern (e.g. `sessionDetailSchema.startedAt: z.string()` at line 103).
