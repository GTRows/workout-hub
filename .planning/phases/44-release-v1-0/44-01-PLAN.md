## Goal

Land the single release commit that cuts `v1.0.0` from `main`, push the annotated tag to fire `.github/workflows/release.yml`, then observe the workflow for the multi-arch GHCR publish + draft GitHub Release. The plan produces three artifacts: (a) one git commit on `main` with three protected-file edits in lockstep (`IDENTITY.yaml` 0.6.0 -> 1.0.0, `backend/pom.xml` 0.6.0 -> 1.0.0, `frontend/package.json` 0.6.0 -> 1.0.0) plus a CHANGELOG rotation that turns the empty `## [Unreleased]` block into a populated `## [1.0.0] - YYYY-MM-DD` block summarising every Phase 38-43 deliverable; (b) one annotated tag `v1.0.0` pointing at that commit; (c) a captured observational verdict on the resulting CI workflow run (release.yml passes; multi-arch GHCR images at `ghcr.io/gtrows/workouthub-{backend,frontend}:1.0.0` are pulled and digest-verified; the draft GitHub Release at `gh release view v1.0.0` carries the extracted `## [1.0.0]` body as notes).

The `docs/MIGRATION.md` `## v1.0.0` section is already populated (Phase 43-01 landed it at lines 265-330; the executor confirms it stays unchanged in this plan and writes a fresh `## vNext` placeholder above the existing template marker if needed). No other doc edits, no new tests, no source-code changes, no schema migrations, no compose-topology change.

The post-tag observational gate is part of the plan's verification scope, not a follow-up phase: the executor watches `gh run watch` for the release-workflow run, asserts both backend + frontend images are published multi-arch (amd64 + arm64) with digest pins captured into the release body, and confirms the draft release is reachable. The maintainer-facing Publish click on the draft release is OUT of scope (per `IDENTITY.yaml#release.draft_first: true` + `RELEASE.md` "Post-release" step "Click Publish in GitHub" — that is a manual maintainer action and the orchestrator is not authorised to fire it).

This is the final plan in the v1.0 milestone. After this plan ships green, the milestone-close bookkeeping (archive `.planning/milestones/v1.0-ROADMAP.md`, update `.planning/MILESTONES.md`, advance `.planning/STATE.md`) follows as the standard milestone-end checkpoint per `.claude/docs/orchestration.md` line 79.

## Architecture Decision: single sub-plan; one release commit; one annotated tag; post-tag observational verdict captured on the same plan; ZERO source-code edits; ZERO test edits; ZERO scripts/Dockerfile/compose/workflow edits; FOUR protected-file touches (IDENTITY.yaml + CHANGELOG.md + backend/pom.xml + frontend/package.json) all in one commit

**Decision:** Author Phase 44 as a single release-cut sub-plan. Reasons:

- **The deliverable is mechanical.** Per `RELEASE.md` "Cut the release" Steps 1-6 the runbook prescribes a single release commit (Step 4: `chore(release): v<version>`), then a single annotated tag (Step 5: `git tag v<version> -m "Release v<version>"`), then `git push && git push --tags` (Step 6). The v0.4.0 / v0.5.0 / v0.6.0 cuts followed this cadence verbatim (precedent: `c8fab14` / `5efaeb5` / `08cc968`). Splitting into multi-leg sub-plans would inflate bookkeeping for no engineering benefit.
- **CHANGELOG rotation is the only content edit.** Plan-author audited HEAD (`3b415a8` via Phase 43-01 close) and confirmed the `## [Unreleased]` block in `CHANGELOG.md` (lines 11-18) is currently EMPTY — no Phase 38 / 39 / 40 / 41 / 42 / 43 entries were folded into `[Unreleased]` during their respective cycles. The release-cut plan must therefore both POPULATE the entries AND rename the heading to `## [1.0.0] - YYYY-MM-DD`. The populated body is sourced from the per-phase summaries at `.planning/phases/38-e2e-tests/38-01-PLAN.md` (and any 38-01-SUMMARY.md output), `.planning/phases/39-testcontainers-major/39-01-PLAN.md`, `.planning/phases/40-framework-majors/40-{01,02,03}-PLAN.md`, `.planning/phases/41-security-hardening/41-01-PLAN.md`, `.planning/phases/42-docs-completion/42-01-PLAN.md`, and `.planning/phases/43-backup-restore-drill/43-01-PLAN.md` plus the closure paragraphs in `.planning/ISSUES.md` (i-5 closed, i-7 closed, i-14 closed; i-6b / i-7b / i-8b new) and `.planning/STATE.md` Locked-in Decisions section.
- **MIGRATION.md `## v1.0.0` already landed in Phase 43-01.** Plan-author confirmed at lines 265-330 of HEAD `docs/MIGRATION.md` that the v1.0.0 entry exists in full (Required env var changes / Schema and data migration / Compose runtime changes / One-shot commands / Rollback subsections all populated). Phase 44 does NOT re-edit MIGRATION.md beyond a sanity-check Read; the executor verifies the section is intact at the date the release commit lands, and re-asserts the trailing `## vNext` template block is preserved at lines 334+. If the `## vNext` block is missing (Phase 43 may not have re-added it after replacing the placeholder), Task 2 below adds it back. If it is present, Task 2 is a no-op.
- **Three derived-manifest version bumps in lockstep.** `IDENTITY.yaml#version` (line 32, currently `0.6.0`), `backend/pom.xml#/project/version` (line 16, currently `0.6.0`), and `frontend/package.json#/version` (line 4, currently `0.6.0`) all bump to `1.0.0` in the same commit. `pnpm-lock.yaml` does NOT need a recompute: the v0.4.0 / v0.5.0 / v0.6.0 cuts all bumped `frontend/package.json#/version` without recomputing the lockfile (the lockfile hash is keyed on the dependency tree, not on the project's own version field). `/gtr:doctor` is the drift validator; the executor runs it pre-commit to confirm zero manifest drift.
- **`/gtr:release` slash-command vs hand cadence.** The CLAUDE.md `## Release` section describes `/gtr:release <version>` as the mechanical wrapper that "does the bump (IDENTITY.yaml + pom.xml + package.json), rotates CHANGELOG, commits, tags. Push is always manual." The executor MAY invoke `/gtr:release 1.0.0` to do Tasks 3-7 in one shot; if the slash command is unavailable or behaves unexpectedly (silent on a protected-file gate, mis-ordered the CHANGELOG bump, etc.), the executor falls back to the hand cadence (Tasks 3-7 individually as documented below). Both paths are acceptable; verification asserts the END state, not the path. Plan-author chose to document the hand cadence in full so the plan is durable independent of the slash-command implementation. The executor records WHICH path they took (slash-command vs hand cadence) in the `44-01-SUMMARY.md` write that follows execution.
- **Annotated-tag conventions.** Per `RELEASE.md` "Versioning rules" the tag format is `v<version>` (e.g. `v1.0.0`); annotated tag with message `Release v1.0.0`. Tag is created locally with `git tag v1.0.0 -m "Release v1.0.0"` on the release commit, then pushed with `git push origin v1.0.0` (NOT `git push --tags` which can leak local-only tags; precedent v0.4.0 / v0.5.0 / v0.6.0 used the targeted single-tag push). The release-workflow trigger is the tag push, so the order is: commit + push commit, then tag, then push tag. (Per `.github/workflows/release.yml#on.push.tags: ['v*.*.*']`.)
- **Post-tag observational verdict is part of the plan's scope.** The release-workflow has historically failed (v0.3.0 release-blocking bean collision; v0.3.1 GHCR-tag-casing failure that needed v0.3.2; per `CHANGELOG.md` lines 370-403). Treating "tag pushed" as the END of the plan and not "release-workflow green + multi-arch images digest-verified + draft release reachable" would let a regression slip into milestone close. Verification step VS-2 below explicitly captures the post-tag observational gate; the executor watches the workflow with `gh run watch`, captures both image digests (`docker buildx imagetools inspect ghcr.io/gtrows/workouthub-{backend,frontend}:1.0.0` per platform), and confirms the draft release exists with extracted notes via `gh release view v1.0.0`. The Publish click is intentionally OUT of scope (operator-controlled per `IDENTITY.yaml#release.draft_first: true`).
- **No `.planning/PROJECT.md` / `ROADMAP.md` / `STATE.md` / `MILESTONES.md` mutation in this plan.** Those edits land at the milestone-close checkpoint (post-Phase-44, orchestrator-managed per `.claude/docs/orchestration.md` line 79) — Phase 44 is the final phase IN the milestone, not the milestone-archive bookkeeping operation. The orchestrator's milestone-close summarizer handles the archive write, the MILESTONES.md prepend, the STATE.md "What's next" advance, and the ISSUES.md status sweep. This plan stops at "tag pushed + workflow green + draft release reachable".

(i-5 / i-7 / i-14 were closed in Phases 40 / 39 / 41; i-6b / i-7b / i-8b were opened in those same phases. The CHANGELOG `### Known Issues (carried forward)` subsection enumerates the OPEN issues at release time — i-3, i-6b, i-7b, i-8b, i-12, i-13, i-15 — but does not mutate the issue file.)

- **No `.github/workflows/**` edit.** The existing release.yml from Phase 11-01 (multi-arch GHCR publish, lowercase IMAGE_PREFIX from v0.3.2 fix) is unchanged. The v0.4.0 / v0.5.0 / v0.6.0 cuts all used this workflow without modification. Workflow paths are protected per CLAUDE.md.

Same shape as the post-v0.6 cut state. This is what the v1.1+ work writes into.

**Why not split into multi-leg sub-plans:**

1. *44-01 = manifests + CHANGELOG only; 44-02 = git tag and push; 44-03 = post-tag observational verdict* — rejected. The three are mechanically inseparable (the tag must point at the release commit, and the workflow trigger is the tag push). Splitting adds three commits + three sub-plan SUMMARY files for what RELEASE.md prescribes as a single Steps-1-through-6 cadence.
2. *44-01 covers an AUDIT first; 44-02 lands the actual cut* — rejected. There is no architectural decision to lock in; the CHANGELOG content is mechanical (sourced from per-phase summaries + STATE.md + ISSUES.md), and the version bumps are line-level edits. Adding an AUDIT pass would be ceremony.
3. *Defer the post-tag observational verdict to the milestone-close checkpoint* — rejected. The release workflow has historically failed (v0.3.0 / v0.3.1 precedent); making the ship-or-no-ship decision part of the release-cut plan keeps the failure window inside the plan's scope, not on the milestone-close path.
4. *Click Publish on the draft release as part of this plan* — rejected. Per `IDENTITY.yaml#release.draft_first: true` and `RELEASE.md` "Post-release" Step 4 ("Click Publish in GitHub"), the Publish action is a manual maintainer step. The orchestrator-driven plan stops at "draft release exists with notes attached"; the maintainer reviews and clicks Publish. Automating the Publish click would invert the draft-first contract.
5. *Patch one of the existing CI failures (none currently active) inside the same plan as a "while you're there" fix* — rejected. CLAUDE.md "What NOT to Do" + global instructions both forbid drive-by changes; if a CI failure surfaces between plan-author time and execute time, the executor surfaces it as a blocking issue and the orchestrator decides whether a hotfix sub-plan is appropriate.
6. *Backfill v0.5.0 / v0.6.0 entries into MIGRATION.md retroactively* — rejected. The Phase 43-01 plan-author already audited this and confirmed both releases shipped zero operator-visible env-var / schema / runtime changes; the milestone archives are the canonical record. The `## v1.0.0` MIGRATION entry is already in tree from Phase 43-01.
7. *Make the release commit a merge commit from a `release/1.0.0` branch* — rejected. The v0.4.0 / v0.5.0 / v0.6.0 cuts all landed as direct commits on `main` (per `git log v0.4.0` / `v0.5.0` / `v0.6.0` precedent). The CLAUDE.md "Branch Strategy" section permits direct-to-main for release-bookkeeping commits ("small, safe fixes can go on `main` if the project convention allows"). A separate release branch would add ceremony for no engineering benefit.
8. *Add a sanity smoke test (`docker compose up + curl /healthz`) as part of verification* — rejected. The release-workflow already runs the full backend `mvn verify` and frontend `pnpm test` + `pnpm typecheck` + `pnpm lint` jobs as preconditions to the multi-arch image build (per release.yml). Adding a local smoke step would duplicate work and is moot on this Windows host (local Maven gap; backend tests run only in CI).
