**Tech stack available (carried from v0.3 + Phase 14):** Java 21, Spring Boot 3.5.x, Spring Web, Spring Data JPA, Hibernate `@UuidGenerator`, Jackson with `serializationInclusion = NON_NULL`, Flyway migrations, JUnit 5 + Testcontainers Postgres, Spring Security with JWT filter and `AUTH_MODE=forward-auth` opt-in, Spring Data `Page<>`/`Pageable` for paginated history.

**Established patterns (carried from v0.3 + Phase 14):**
- Feature-sliced packages (`sessions/`, `workouts/`, etc.).
- Controller -> Service -> Repository, transactions on services, DTOs at HTTP boundary.
- Validation via `jakarta.validation` on request DTOs.
- Flyway migrations are immutable; new schema = new `V<n>__*.sql`.
- Tests: JUnit 5 + Testcontainers, no H2.
- Phase 14 lesson: explicit child-repo `saveAndFlush(child)` after `parent.addChild()` to materialize `@UuidGenerator` ids before mapper read. Sessions package uses this pattern at `SessionSetsService.add` (`sets.saveAndFlush(set)`) so cascade-id risk is already mitigated for session sets - confirm in audit.

**Constraining decisions:**
- v0.3 contract section 7: built-in JWT default, no OIDC client. Endpoint auth requirements must reflect this.
- `ddl-auto: validate` - schema cannot drift; migrations are the only source of truth.
- ProjectBrief Phase 4 explicitly carves out two analytics endpoints (`/api/exercises/:id/last-performance`, `/api/exercises/:id/progress`); Phase 16 (sessions-analytics) is the formal owner per `.planning/ROADMAP.md`. Sessions code that ships those endpoints today is in-package but out-of-Phase-15 scope - the audit must call this out so Phase 16 planning starts from a known position.
- ProjectBrief Phase 4 line 311: "Frontend stores sets in IndexedDB then syncs when connectivity returns." The backend must therefore tolerate retried POSTs without producing duplicates. Audit must evaluate whether the current `(session_id, exercise_id, set_number)` UNIQUE + 409 path is sufficient or whether a client-supplied idempotency key is required.
