## Architecture Decision: docs-only single sub-plan; new file `docs/BACKUP_RESTORE_DRILL.md` (operator-runnable runbook); MIGRATION.md vNext -> v1.0.0; ZERO protected-file edits; ZERO source-code edits

**Decision:** Author Phase 43 as a single docs-only sub-plan. Reasons:

- **The deliverable mass is all markdown.** The roadmap's three named items (drill, cron example, MIGRATION updates) are all content edits to documentation. Splitting into multi-leg sub-plans would inflate the bookkeeping cost (multiple SUMMARY files, multiple commits, multiple CI rounds) for no engineering benefit. The four files are mutually independent at the diff level (BACKUP.md is additive, MIGRATION.md is additive, the new BACKUP_RESTORE_DRILL.md is wholly new, DEPLOYMENT.md + README.md cross-links are one-line adds each).
- **No `compose.yml` change.** The `pg_dump` sidecar is already wired in tree at `compose.yml` lines 90-131 (Phase 7 deliverable). The drill exercises that existing primitive by pointing operators at the artifacts the sidecar already writes (`./data/backups/<date>.dump`). Adding a "drill mode" toggle to compose.yml would (a) be a `compose.yml` edit (protected file; spawn prompt explicitly says surface as `status: blocked` if needed), (b) duplicate operator-layer work — the drill is meant to run on the operator's host, against THEIR backup artifacts, not against a fresh-stack-up cycle, (c) inflate the v1.0-hardening single-commit cadence. The right primitive for the drill is a documented `docker run --rm postgres:16-alpine ...` recipe the operator runs when they want to verify their backup posture; that's exactly what BACKUP_RESTORE_DRILL.md will document.
- **No `scripts/` change.** The drill is documentation, not automation. A new `scripts/restore-drill.sh` would (a) be a new file under `scripts/` (protected; spawn prompt: "scripts/ is protected. New scripts under scripts/ need user approval"; surface as `status: blocked`), (b) need testing infrastructure (a CI job that exercises the drill against a known-good dump, which would be a `.github/workflows/**` edit — also protected), (c) duplicate the `docs/BACKUP.md` lines 42-57 dry-run recipe that's already in tree. Documentation is the right substrate; the operator runs the drill manually, the drill documentation captures the steps, the steps are deterministic shell + docker commands the operator already runs daily.
- **No `.github/workflows/**` change.** Auto-running the drill on CI would require either (a) a stored-secret backup artifact to drill against (security smell — the drill artifact would have to be a real production-shape dump, which is data-leak-prone), or (b) a synthetic dump created on-the-fly inside the CI job, which would test only that the sidecar's pg_dump output round-trips back through pg_restore — a property already covered by the existing Testcontainers integration tests at the schema level. ## Tasks

### Task 1: Author docs/BACKUP_RESTORE_DRILL.md (new file)

**File:** `docs/BACKUP_RESTORE_DRILL.md` (create new)

**Action:**

Write a self-contained operator runbook for verifying backup integrity. Source seed: the existing `docs/BACKUP.md` lines 42-57 dry-run recipe (which already restores into a throwaway `wh-restore-check` container and asserts `\dt` shows the canonical tables). Expand the seed into a full drill document.

Structure the document with these sections (in order):

1. **Title + lead paragraph** (3-5 sentences). Restate why the drill exists: a backup that has never been restored is not a backup. Per `docs/SELF_HOSTED_CONTRACT.md` Section 5.2, the application puts data where backups can find it but does not perform the backup; the operator owns backup execution AND backup verification. Recommended cadence: quarterly (every 90 days), or after any change to the backup posture (sidecar enable/disable, host-cron move, retention adjustment).

2. **Prerequisites** (bullet list). Operator must have:
   - Docker and `docker compose` on the host running this stack.
   - At least one backup artifact on disk: either `./data/backups/<date>.dump` (from the opt-in `pg_dump` sidecar) OR `./backups/<date>.sql.gz` (from `scripts/backup.sh` host cron). The drill supports both formats; the operator picks whichever they actually use.
   - Free disk space at least 1.5x the size of the backup artifact (the throwaway container needs space to load the dump).
   - No production write traffic during the drill window — the drill does NOT touch the live database; it spins up an isolated `postgres:16-alpine` container on a non-default port and tears it down at the end. The live stack is unaffected.

3. **Drill mode A: pg_dump sidecar artifact (`./data/backups/<date>.dump`, custom format)** (numbered procedure).
   - Step 1: pick the artifact. Show `ls -la ./data/backups/` and pick the most recent `.dump` file.
   - Step 2: spin up the throwaway container.
     ```sh
     docker run -d --name wh-restore-drill \
         -e POSTGRES_USER=drill \
         -e POSTGRES_PASSWORD=drill \
         -e POSTGRES_DB=drill \
         -p 127.0.0.1:55432:5432 \
         postgres:16-alpine
     ```
     Note the host port `55432` is intentionally non-default to avoid clashing with the live `db` service on `5432`. Bind to `127.0.0.1` per Self-Hosted Contract.
   - Step 3: wait for readiness.
     ```sh
     until docker exec wh-restore-drill pg_isready -U drill -d drill; do sleep 1; done
     ```
   - Step 4: restore the dump via `pg_restore`.
     ```sh
     dump=./data/backups/<date>.dump
     docker exec -i wh-restore-drill pg_restore \
         -U drill -d drill --clean --if-exists --no-owner --no-privileges \
         < "$dump"
     ```
     Reasoning notes for the operator: `--clean --if-exists` matches the script's pg_dump option set; `--no-owner --no-privileges` strips the original cluster's role/privilege metadata since the throwaway container has its own roles. Stderr will contain `pg_restore: error: could not execute query: ERROR:  role "<original-user>" does not exist` lines for any role-owned object — those are EXPECTED in drill mode and do NOT indicate a corrupt dump.
   - Step 5: assert the schema is intact.
     ```sh
     docker exec wh-restore-drill psql -U drill -d drill -c "\\dt"
     ```
     Expected output includes (at minimum): `users`, `user_profiles`, `refresh_tokens`, `exercises`, `workout_plans`, `workout_days`, `workout_day_exercises`, `workout_sessions`, `session_sets`, `body_metrics`. Refer to `docs/DATA_SCHEMA.md` "Domain map" for the full canonical table list.
   - Step 6: assert representative row counts (sanity, not exact).
     ```sh
     docker exec wh-restore-drill psql -U drill -d drill -c \
         "SELECT 'users' AS tbl, COUNT(*) FROM users
          UNION ALL SELECT 'sessions', COUNT(*) FROM workout_sessions
          UNION ALL SELECT 'sets', COUNT(*) FROM session_sets
          UNION ALL SELECT 'metrics', COUNT(*) FROM body_metrics;"
     ```
     The drill PASSES if (a) the query returns four rows, (b) the counts are within an order of magnitude of what the live system reports, (c) every count is `>= 0` (and is `> 0` for at least `users` if the system has any registered users).
   - Step 7: tear down.
     ```sh
     docker rm -f wh-restore-drill
     ```
     The drill leaves zero residue: no host volumes, no networks, no orphan containers.

4. **Drill mode B: scripts/backup.sh artifact (`./backups/<date>.sql.gz`, plain SQL)** (numbered procedure).
   - Step 1: pick the artifact. Show `ls -la ./backups/` and pick the most recent `.sql.gz` file.
   - Step 2: spin up the throwaway container (identical to mode A's step 2).
   - Step 3: wait for readiness (identical to mode A's step 3).
   - Step 4: restore the dump via `gunzip | psql`.
     ```sh
     dump=./backups/<date>.sql.gz
     gunzip -c "$dump" | \
         docker exec -i wh-restore-drill psql -U drill -d drill
     ```
     Stderr behaviour identical to mode A (role-not-found warnings expected).
   - Steps 5-7: identical to mode A (assert schema, assert row counts, tear down).

5. **What the drill validates** (small list).
   - The dump file is non-empty and structurally valid (gzip-clean for mode B, pg_dump-custom-clean for mode A).
   - Every CREATE TABLE / CREATE INDEX / CREATE CONSTRAINT statement applies cleanly — i.e. no schema drift between the dump's snapshot and Postgres 16's parser.
   - At least one user-data row survives the round-trip (assertion 6).

6. **What the drill does NOT validate** (small list — be explicit per the contract's "no false promises" posture).
   - Application-layer invariants (e.g. `is_pr` recompute correctness on the restored set; the live backend's `MetricsService.UpsertResult` 200/201 split). Those are application-layer concerns, exercised by the backend integration test suite, not by a backup drill.
   - Foreign-key cascade behaviour under live write load.
   - Backup throughput / recovery-point-objective (RPO) — the drill measures restore-ability, not RPO.
   - Offsite backup integrity — `scripts/backup.sh` deliberately does not know about remote storage (per `docs/BACKUP.md` line 60). The operator pushes `.sql.gz` / `.dump` files offsite via restic / rclone / borg / S3-CLI / etc.; offsite-side verification is the operator's responsibility, separate from this drill.

7. **Failure modes and triage** (small bulleted list).
   - **`pg_restore: error: could not read from input file: end of file`** (mode A) — dump is truncated. Re-take the dump from the live system; investigate disk-full or container-OOM during the original `pg_dump` run.
   - **`gzip: stdin: not in gzip format`** (mode B) — file is not a valid gzip. Either the file is a `.sql` plain file misnamed as `.sql.gz`, or the file is a `pg_dump` custom-format file misnamed. Use `file <path>` to confirm.
   - **`psql: error: connection to server ... refused`** (both modes) — the throwaway container hasn't finished starting. Re-run step 3 (`pg_isready`) until it returns 0.
   - **CREATE TABLE fails with `column "X" does not exist`** — schema drift between dump-vintage and Postgres 16 parser. Indicates the dump was taken against a different Postgres major version OR the dump is corrupted. Investigate.
   - **`\dt` output is empty** — `pg_restore` succeeded but no schema landed. Indicates the dump is empty or the dump was taken against an empty database.
   - **Row-count assertion returns counts of 0 across the board** — drill artifact was taken before any user activity. Either retake the artifact after some user data lands, OR accept the zero-count as expected for a fresh install drill.

8. **Recommended cadence and integration with operator routine**.
   - Run the drill **quarterly** (every 90 days) at minimum. Pin to a calendar reminder; set the calendar entry to fire on the first business day after the start of each quarter.
   - Run the drill **after any change to the backup posture**: enabling/disabling the `pg_dump` sidecar, moving `BACKUP_DIR`, changing `PG_DUMP_RETENTION_DAYS`, switching from sidecar to host-cron or vice versa.
   - Run the drill **before a major upgrade**: upgrading Postgres past 16, migrating to a new host, restoring from offsite. The drill in its current form does NOT cover Postgres-major-version upgrade compatibility (that's a separate `pg_upgrade` drill — out of scope for this doc).
   - Record drill outcomes in the operator's runbook (timestamp, artifact filename, row counts, pass/fail). The drill itself is stateless; recording is the operator's job.

9. **Cross-references** (small list at end of file).
   - For backup capture (the half this doc does not cover): `docs/BACKUP.md`.
   - For schema reference (which tables to expect in `\dt`): `docs/DATA_SCHEMA.md`.
   - For deployment context (where artifacts live, what `./data/backups/` is): `docs/DEPLOYMENT.md`.
   - For the binding contract (who-owns-what split): `docs/SELF_HOSTED_CONTRACT.md` Section 5.2.
   - For per-version operator upgrade steps: `docs/MIGRATION.md`.

Length budget: 100-180 lines. Tone: matches `docs/BACKUP.md` and `docs/DEPLOYMENT.md` (short paragraphs, fenced code blocks, terse English, NO emoji per `CLAUDE.md`).
