**Tech stack available:** Next.js 15.1 App Router (Server Components default), TypeScript strict, Vitest + jsdom.

**Constraining decisions (from STATE.md):**
- Frontend `/healthz` and `/livez` are PROCESS LIVENESS ONLY. The frontend is stateless; coupling its health to backend reachability would propagate backend outages into the frontend's own up/down indicator. The reverse proxy upstreams them independently.
- Both endpoints return identical bodies (`{"status":"alive"}`) - they exist as separate routes for orchestrator compatibility (k8s-style livez vs healthz semantics) but their behavior is the same per the locked-in decision.

**Plan 02-01 prerequisite:** Backend `/healthz` and `/livez` must exist before this plan re-points the compose probe at `/healthz`. Plan 02-01 lands first.

**Note on protected files:** `compose.yml` is protected. The single edit in Task 2 will trigger a confirmation prompt - approve and continue.

  <action>
Create two App Router route handlers. Both must export a `GET` handler returning a JSON body with status field. Both are process-liveness only - they do NOT ping the backend, do NOT touch IndexedDB, do NOT read any persistent state.

`frontend/src/app/api/healthz/route.ts`:

```ts
export const dynamic = "force-dynamic";
export const runtime = "nodejs";

export function GET() {
  return new Response(
    JSON.stringify({ status: "alive" }),
    { status: 200, headers: { "content-type": "application/json" } }
  );
}
```

`frontend/src/app/api/livez/route.ts` is identical (or imports from the healthz module - your call). Keeping them separate files makes their orchestrator semantics visible at a glance and avoids confusing future edits.

The `dynamic = "force-dynamic"` and `runtime = "nodejs"` exports prevent Next from statically rendering or edge-routing the response - probes need real-time, in-process answers.

Add a Vitest test at `frontend/src/app/api/healthz/route.test.ts` (mirroring the project's co-located test pattern):

```ts
import { describe, it, expect } from "vitest";
import { GET } from "./route";

describe("/api/healthz", () => {
  it("returns 200 with status alive", async () => {
    const res = GET();
    expect(res.status).toBe(200);
    const body = await res.json();
    expect(body.status).toBe("alive");
  });
});
```

A single test file covering `/api/healthz` is enough; `/api/livez` is structurally identical and adding a duplicate test would just be coverage theater. If livez later diverges, add a test then.

Do NOT add any backend reachability check. Do NOT read env vars in the handlers. Do NOT add caching headers - probes do their own caching decisions.
