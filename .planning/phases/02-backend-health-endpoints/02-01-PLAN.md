Create a new `HealthController` under the existing `common/web/` package (alongside `GlobalExceptionHandler`):

```java
@RestController
public class HealthController {
    private final DataSource dataSource;
    private final FlywayMigrationsApplied flywayCheck; // see below

    public HealthController(DataSource dataSource, FlywayMigrationsApplied flywayCheck) {
        this.dataSource = dataSource;
        this.flywayCheck = flywayCheck;
    }

    @GetMapping("/livez")
    public ResponseEntity<HealthStatusDto> livez() {
        return ResponseEntity.ok(new HealthStatusDto("alive", null));
    }

    @GetMapping("/healthz")
    public ResponseEntity<HealthStatusDto> healthz() {
        // 1. DB ping with a 1-second query timeout
        try (Connection c = dataSource.getConnection()) {
            if (!c.isValid(1)) {
                return ResponseEntity.status(503).body(new HealthStatusDto("unready", "db_unreachable"));
            }
        } catch (SQLException ex) {
            return ResponseEntity.status(503).body(new HealthStatusDto("unready", "db_error: " + ex.getClass().getSimpleName()));
        }
        // 2. Flyway migrations applied (no pending migrations means schema validate would pass)
        if (!flywayCheck.allApplied()) {
            return ResponseEntity.status(503).body(new HealthStatusDto("unready", "migrations_pending"));
        }
        return ResponseEntity.ok(new HealthStatusDto("ready", null));
    }
}
```

`FlywayMigrationsApplied` is a tiny inner-or-helper component that asks Flyway whether `pending()` is empty. Implement it as a `@Component` in the same package:

```java
@Component
class FlywayMigrationsApplied {
    private final Flyway flyway;
    public FlywayMigrationsApplied(Flyway flyway) { this.flyway = flyway; }
    boolean allApplied() {
        return flyway.info().pending().length == 0;
    }
}
```

Spring Boot autoconfigures a `Flyway` bean when `spring-boot-starter-data-jpa` + `flyway-core` are on the classpath, which they already are (verified via `backend/pom.xml`).

`HealthStatusDto` is a Java record under `common/web/dto/`:

```java
public record HealthStatusDto(String status, String reason) {}
```

`reason` is null on success; populated on degraded/unready responses for human-readable cause. NON_NULL serialization (already configured in `JacksonConfig`) will omit `reason` when null.

Do NOT add any logging on the success path - healthcheck probes hit these endpoints every 15s and would flood logs. Log only on the unready paths (use `log.warn`).

Do NOT remove or break `/actuator/health` - other monitoring may depend on it. The two endpoints coexist.

Do NOT add `@PreAuthorize` or any authorization annotation. The endpoints must be reachable from the container's own healthcheck command, which runs without an Authorization header. SecurityConfig will allowlist them in Task 2.

```java
@AutoConfigureMockMvc
class HealthControllerIntegrationTest extends AbstractIntegrationTest {

    @Autowired MockMvc mvc;

    @Test
    void livezReturns200WithStatusAliveWithoutAuth() throws Exception {
        mvc.perform(get("/livez"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.status").value("alive"));
    }

    @Test
    void healthzReturns200WithStatusReadyWhenDbAndMigrationsAreUp() throws Exception {
        mvc.perform(get("/healthz"))
                .andExpect(status().isOk())
                .andExpect(jsonPath("$.status").value("ready"));
    }
}
```

The unready paths (DB down, migrations pending) are intentionally NOT exercised here - they require either Testcontainers manipulation that fights the abstract base class or unit-mocking the DataSource which couples the test to internals. The contract's correctness check is "ready when up"; the unready paths are guarded by the explicit code branches and will be exercised by operator-side runtime if those failure modes occur.

Do NOT add `@Disabled`. Do NOT mock the DataSource - the integration test framework already provides a real one.
