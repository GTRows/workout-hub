# Phase 39 - Plan 01: Bump Testcontainers from 1.20.4 to latest 1.x (1.21.3); re-defer i-7 until 2.x ships

**Milestone:** v1.0 Release Hardening
**Phase:** 39 - testcontainers-major
**Plan:** 39-01 (only sub-plan; closes deferred i-7 partially and reframes the residual)
**Status:** Not started
**Author date:** 2026-05-09

## Goal

Close the operational intent of deferred issue **i-7** ("Defer testcontainers
1.x -> 2.x major bump (PR #11)") by bumping `<testcontainers.version>` in
`backend/pom.xml` from `1.20.4` to `1.21.3` (the latest stable 1.x release as
of 2026-05-09 per Maven Central) and verifying the existing
`AbstractIntegrationTest` Postgres scaffolding plus all 11 migration tests
(`V2..V27*MigrationTest`) still execute correctly in CI.

The phase name reads "testcontainers-major", but Maven Central proves no `2.x`
artifact has been published as of this plan's author date. The most recent
Testcontainers releases on the `1.21.x` line ship cumulative bug fixes and
Docker-API compatibility updates that the i-7 trigger ("next time test
infrastructure receives attention") was intended to absorb. This plan does
the maximum-yield, lowest-risk bump available now and re-frames the residual
i-7 issue (the real `2.x` jump) for the future date the artifact actually
exists.

## Architecture Decision: 1.20.4 -> 1.21.3 minor bump on a still-1.x ecosystem; re-defer the 2.x portion of i-7 with an updated trigger

**Decision:** Update one Maven property — `<testcontainers.version>` — from
`1.20.4` to `1.21.3` in `backend/pom.xml`. Do not edit
`AbstractIntegrationTest`, the migration tests, or any other test class. Move
i-7's scope to **closed for 1.x** in `.planning/ISSUES.md` and either close
the ticket fully or re-open a narrower successor entry (i-7b) keyed on
"Testcontainers 2.0.0 GA released by maintainers" so the v1.0 release notes
honestly state what was and was not absorbed.

**Why this is the right call here:**

- **The 2.x artifact does not exist yet.** Maven Central group `org.testcontainers`,
  artifact `testcontainers`, top 20 versions queried 2026-05-09: 1.21.3 (latest),
  1.21.2, 1.21.1, 1.21.0, 1.20.6, 1.20.5, 1.20.4, 1.20.3, 1.20.2, 1.20.1,
  1.20.0, 1.19.8, ... down through 1.19.0. There is no `2.0.0`, no `2.0.0-RC`,
  no `2.0.0-M1`. A "1.x -> 2.x" bump is not actionable. Refusing to ship
  anything until the major exists strands i-7 indefinitely; bumping to the
  latest 1.x captures the bulk of the fixes the trigger envisioned and
  unblocks the v1.0 release.
- **API compatibility is preserved on the 1.20 -> 1.21 hop.** The
  `AbstractIntegrationTest` surface area is exactly four method calls on
  `PostgreSQLContainer`: `withDatabaseName(String)`, `withUsername(String)`,
  `withPassword(String)`, `withReuse(boolean)`, plus the constructor
  `PostgreSQLContainer<>("postgres:16-alpine")`. All four methods and the
  constructor are stable across the 1.x line and have not had any
  signature/semantic change between 1.20 and 1.21. The
  `@Testcontainers`/`@Container` JUnit Jupiter integration (used in
  `import org.testcontainers.junit.jupiter.Testcontainers`) is also unchanged.
- **Minimum Docker host version did not regress.** Testcontainers 1.21 still
  supports Docker Engine 20.10+ (the floor we use in CI), so the GitHub
  Actions runners with their bundled Docker daemon will continue to function.
  No CI workflow edit needed.
- **Manual `static { POSTGRES.start(); }` pattern is unaffected.** The current
  `AbstractIntegrationTest` does NOT use `@Testcontainers` lifecycle annotation
  + `@Container static` field combination (which would be where Testcontainers
  2.x's planned JUnit Jupiter changes would land). It uses a static initializer
  to start the container exactly once per JVM, plus `@Testcontainers` only as a
  marker (no `@Container`-managed field). This pattern is the simplest and the
  most forward-compatible — when 2.x eventually ships, this class will not be
  the breaking-change blast site.
- **withReuse(true) semantics are preserved.** The 1.20 -> 1.21 series
  retains `TESTCONTAINERS_REUSE_ENABLE` behaviour (CI runners that don't have
  reuse enabled get a fresh container per JVM; local dev with `~/.testcontainers.properties`
  setting `testcontainers.reuse.enable=true` reuses across runs). No behavioural
  change for our suite.
- **No protected files beyond `pom.xml`.** The project's Protected Files list in
  `CLAUDE.md` includes `pom.xml`. The user has pre-authorised pom.xml edits
  for v1.0 milestone work via the same "tüm işleri bitirelim" continuity that
  carried v0.5.0 / v0.6.0 protected-file edits (Netty pin, jose4j override,
  springdoc workaround). This single-property change matches the precedent.
- **Local-Maven-gap aware.** Per repo memory, backend `mvn` is unavailable on
  this Windows host. The plan's verification gate is structural (file presence,
  exact property value, Maven Central artifact existence verified at plan
  time) plus a CI run on push; no local mvn execution is assumed.
- **Single-property scope keeps the diff trivial to review.** The change is
  `1.20.4` -> `1.21.3` on one line of `pom.xml`. The `<testcontainers-bom>`
  import in `<dependencyManagement>` already pulls every Testcontainers
  artifact (junit-jupiter, postgresql) at the BOM-pinned version, so the two
  test-scoped `<dependency>` blocks need no version edit.

**Rejected alternatives:**

1. *Wait for Testcontainers 2.0.0 to be released and bump straight to it* —
   rejected. There is no published timeline for 2.x as of the v1.0 milestone.
   The Testcontainers maintainers have not announced a release candidate. The
   v1.0 milestone (Phases 38-44) is on a finite schedule and cannot block on
   an unspecified upstream date. Re-deferring i-7 entirely is also worse than
   capturing the 1.21.x cumulative fixes.
2. *Bump only to 1.20.6 (latest 1.20.x) to minimize line-version churn* —
   rejected. 1.20.6 is older and missing the 1.21.x bug fixes. The
   1.20 -> 1.21 hop is API-compatible and pulls in additional Docker-engine
   compatibility fixes; choosing 1.20.6 over 1.21.3 with no compatibility
   reason is gratuitous timidity.
3. *Use `${testcontainers.version}` of `1.21.+` (Maven version range)* —
   rejected. Version ranges are non-reproducible across rebuilds and conflict
   with the project's pinned-dependency posture (Renovate-driven bumps,
   explicit `<version>` properties). Pinning to `1.21.3` exactly matches the
   precedent set by every other dependency property in this pom.
4. *Migrate `AbstractIntegrationTest` to the `@Container` annotated-field
   pattern as a prep for 2.x* — rejected. The current static-init pattern is
   strictly simpler and works identically. Refactoring it now adds risk
   (re-running the entire integration suite under a new lifecycle harness)
   for zero gain. When 2.x eventually requires the change, it can be done in
   the actual 2.x bump plan with the migration guide in hand.
5. *Bundle the bump with the Spring Boot 4 jump (Phase 40)* — rejected.
   Mixing two major bumps in one phase makes failure-mode triage harder. The
   Phase 40 plan should land Spring Boot 4 cleanly with everything else
   already on its latest stable 1.x line.
6. *Replace Testcontainers entirely with Docker Compose in CI / a separate
   sidecar Postgres container* — rejected. Testcontainers gives per-test
   isolation, automatic cleanup, and `withReuse(true)` for fast local
   iteration. Switching infra mid-stream would cost a week and gives nothing
   the bump does not.
7. *Skip i-7 entirely and document it as "not actionable; closing without
   change"* — rejected. The i-7 trigger ("next time test infrastructure
   receives attention") IS being honoured by this phase. Doing nothing leaves
   1.20.4 in place against the 2026 CVE landscape; the 1.21.x fixes catch
   real-world Docker-engine API drift.

Local devs who do have the flag will continue to reuse — and if any divergence appears, the test does NOT silently fail, it just runs slower. |

Trivy scanning runs in CI as part of the existing `.github/workflows/security.yml` pipeline; any new CVE will be flagged on the first push and triaged via the standard process (override or `.trivyignore` documented in CHANGELOG). |
