<objective>
Split `POST /api/metrics` status code on the upsert branch: 201 Created on first POST for a given `(userId, recordedDate)`, 200 OK on every subsequent POST that mutates an existing row. Closes 17-01-AUDIT Section 4 Part A "Direction A" verdict and finishes Phase 17 (4/4).

Purpose: Today the controller returns 201 unconditionally (`MetricsController.java:44`), which encodes "Created" semantics on the UPDATE branch and contradicts HTTP RFC 9110 §15.3. The existing test `repeatedPostForSameDateUpdatesInsteadOfInserting` at `MetricsIntegrationTest.java:74` asserts `isCreated()` on the second POST — locking the drift in. The fix mirrors the Phase 15-02 `clientSetId` precedent (`SessionSetsService.AddSetResult` + `SessionSetsController.java:36-38`): service returns a `(dto, wasCreated)` wrapper, controller maps the boolean to a status code. The V6 UNIQUE-by-`(user_id, recorded_date)` constraint encodes the date-keyed contract, so per-id PUT is explicitly NOT introduced (audit Section 4 Part B verdict).

Output: 1 inner record on `MetricsService`, 1 service signature change with create/update branch detection, 1 controller status-code mapping, 1 existing test assertion flip, 1 new test locking the status pair plus id stability across the upsert. No migration. No DTO change. No new endpoint.
</objective>

      Optional<BodyMetric> existing = repo.findByUserIdAndRecordedDate(userId, req.recordedDate());
      boolean wasCreated = existing.isEmpty();
      BodyMetric entity = existing.orElseGet(() -> {
          BodyMetric fresh = new BodyMetric();
          fresh.setUserId(userId);

      return new UpsertResult(toDto(repo.save(entity)), wasCreated);
  }

          @AuthenticationPrincipal AppUserPrincipal principal,
          @Valid @RequestBody UpsertBodyMetricRequest req) {
      UpsertResult result = service.upsert(principal.userId(), req);
