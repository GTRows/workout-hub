## Architecture Decision: defer Jackson 3 source-rewrite to Phase 47 (rename Phase 47 to `spring-boot-4-with-jackson-3`); rewrite ROADMAP + ISSUES + STATE; no source-file or pom edits in Phase 46

**Decision:** Treat Phase 46 as a paperwork-only deferral phase. The actual 36-file rewrite + the `Jackson2ObjectMapperBuilderCustomizer` -> Spring Boot 4 Jackson 3 customizer flip + the `<spring-boot-starter-parent>` 3.5.14 -> 4.0.x bump + the Spring Framework 7 / Spring Security 7 / Hibernate 7 / Jakarta EE 11 BOM audit + the Jackson2-module + Prometheus-actuator package-relocation imports + the Netty 4.2.12 -> 4.2.13 micro-bump (the i-14 follow-up that the SB4 BOM forces) all land together inside Phase 47, in a single commit, validated by a single CI round-trip.

**Why this is the right call here (four blockers, each independently sufficient):**

1. **Spring Boot 3.5.14 has no Jackson 3 auto-configuration surface.** The codebase's `backend/src/main/java/com/workouthub/common/config/JacksonConfig.java` declares a `@Bean Jackson2ObjectMapperBuilderCustomizer` (line 14). That class lives at `org.springframework.boot.autoconfigure.jackson.Jackson2ObjectMapperBuilderCustomizer` and its very name is Jackson 2-specific (the `2` suffix is part of the class identifier, not a version on the `org.springframework.boot.*` package coordinate). Spring Boot 3.5 has no equivalent `JacksonObjectMapperBuilderCustomizer` for the Jackson 3 (`tools.jackson.*`) family; the equivalent customizer lands only in Spring Boot 4's `spring-boot-jackson` module (per the i-8b enriched body's "spring-boot-jackson2" relocation note). A pure source rewrite that flips the imports to `tools.jackson.*` would leave `JacksonConfig` referencing `Jackson2ObjectMapperBuilderCustomizer` on Jackson 2's symbol but populating it with `tools.jackson.databind.SerializationFeature` symbols — a compile error.

2. **Spring Framework 6.2 (Spring Boot 3.5's Spring version) ships only the Jackson 2 `HttpMessageConverter` family.** `MappingJackson2HttpMessageConverter` and `MappingJackson2XmlHttpMessageConverter` are auto-registered by Spring MVC's `WebMvcConfigurationSupport` when Jackson 2 is on the classpath. Spring Framework 6.2 does NOT ship a `MappingJacksonHttpMessageConverter` (Jackson 3) equivalent — that surface lands in Spring Framework 7 / Spring Boot 4 per the published Spring Boot 4.0.6 BOM mapping (Spring Framework 7.0.7). Therefore, even if the 36 source files were rewritten to `tools.jackson.*`, the runtime HTTP message conversion would still be done by Jackson 2 because Spring MVC's converter resolution does not see Jackson 3 on Spring Boot 3.5. The migration would be source-only theatre with no runtime semantic change. That's worse than not migrating because it breaks the codebase invariant that source surfaces match runtime behaviour.

3. **Both Jackson 2 and Jackson 3 simultaneously on the classpath is a packaging hazard.** Adding `tools.jackson.core:jackson-databind:3.x` as an explicit Maven dep alongside Spring Boot 3.5's transitive `com.fasterxml.jackson.core:jackson-databind:2.18.x` would put both API families on the runtime classpath. The 36-file rewrite would compile against Jackson 3, but Spring Boot 3.5's auto-configured `ObjectMapper` `@Bean` (created via `JacksonAutoConfiguration` from `spring-boot-autoconfigure`) would still be a Jackson 2 `ObjectMapper`. Any caller injecting `ObjectMapper` would get the Jackson 2 instance (e.g., `AuditLogService` line 16 `private final ObjectMapper objectMapper;` — the type is unqualified at the import site; if the source flips to `tools.jackson.databind.ObjectMapper` the bean injection would fail with `NoSuchBeanDefinitionException` because the auto-configured bean is the Jackson 2 type). Resolving this requires either (a) explicit `@Bean tools.jackson.databind.ObjectMapper` registration AND a deliberate exclusion of `JacksonAutoConfiguration`, OR (b) waiting for Spring Boot 4 where the auto-configuration is itself Jackson 3-aware. Path (a) is a hack that exists nowhere else in the codebase and would be reverted in Phase 47 anyway; path (b) is the clean choice.

4. **Test infrastructure (`MockMvc`, `@WebMvcTest`, the 28 integration tests injecting `ObjectMapper`) is also Jackson 2 -auto-wired on Spring Boot 3.5.** `@SpringBootTest` brings in `JacksonAutoConfiguration` which produces a Jackson 2 `ObjectMapper` `@Bean`. The 28 integration tests use `@Autowired ObjectMapper objectMapper` to convert request/response bodies (`AuthFlowIntegrationTest.java` line 9 imports `com.fasterxml.jackson.databind.ObjectMapper` and the Jackson-marshalling lines 75-200ish parse JSON bodies in MockMvc assertions). Flipping the test-side imports to `tools.jackson.*` while the runtime bean is still Jackson 2 would surface the `NoSuchBeanDefinitionException` documented in blocker 3, multiplied by 28. The minimum viable green test suite would require maintaining a parallel Jackson 2 + Jackson 3 import scheme during the transition window — a tax that exists exactly because Spring Boot 3.5 cannot host Jackson 3 cleanly.

The four blockers compound: even if we accept blocker 1 and add a `JacksonObjectMapperBuilderCustomizer` shim in `JacksonConfig`, blockers 2-4 still apply because the runtime serialization resolves through Spring Framework 6.2's converter chain. There is no Spring Boot 3.5-compatible workaround that produces a runnable, test-green Jackson 3 source-only intermediate state. The migration's first runnable shape IS Spring Boot 4.

**Why deferral-into-Phase-47 (not deferral-into-some-future-issue):**

- **Phase 47 is pre-scoped for the Spring Boot 4 bump per ROADMAP.md line 99 (i-8b's full scope).** Adding the Jackson rewrite into the same commit changes Phase 47's surface from "1 pom.xml line + ~6 import-line fixes (Jackson2 + Prometheus relocations)" to "1 pom.xml line + 36 source files rewritten + ~6 import-line fixes" — meaningful but not pathological. The combined commit is still a single coherent unit of work: "migrate to Spring Boot 4, including its Jackson 3 default and the package relocations the bump forces."
- **i-8b's enriched body already enumerates Path A vs Path B.** Plan 46-01 picks Path B (full Jackson 3 migration; the user's explicit choice per the spawn prompt) and locks Phase 47 onto Path B by renaming it. The Path A alternative (`spring-boot-jackson2` compat module) is closed off — the rename signals the decision.
- **CI round-trip arithmetic:** doing 46 then 47 would require two CI passes. Doing 47 only requires one. The local-Maven-gap (`local_maven_gap.md`) makes every CI pass the bottleneck on Windows; halving them is a real saving.
- **Mirror precedent:** v1.0 Phase 40-02 deferred Next 16 because next-intl 3.x peer-pinned to `next ^15`. The deferral consolidation (Phase 40-02 -> Phase 48 in v1.1) sequenced both jumps into one phase. Phase 46 -> 47 is the same playbook one level inwards: re-sequence before any source change rather than after a rolled-back attempt.
- **No protected-file edit needed in Phase 46.** ROADMAP.md, ISSUES.md, STATE.md are all unprotected. `backend/pom.xml` (protected) stays untouched in this phase. The protected-file pre-authorisation flow exercises in Phase 47 only.
- **No CI gate needed for Phase 46.** The deferral commits do not change runtime behaviour; the v1.1 milestone's CI invariant is preserved (CI stays green at the 45-shipped baseline).
