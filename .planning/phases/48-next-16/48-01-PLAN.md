## Architecture Decision: bump `next` to `^16.x` (latest stable) + `eslint-config-next` to `^16.x` in `frontend/package.json`; regenerate `frontend/pnpm-lock.yaml`; rename `middleware.ts` -> `proxy.ts` (preferred path) and update `middleware.test.ts` -> `proxy.test.ts`; wrap login page body in `<Suspense>` with a fallback; bump `engines.node` to `>=20.9.0`; keep webpack as the bundler (`--webpack` flag) for the v1.1 ship; close i-6b in ISSUES.md + STATE.md

**Decision:** A six-edit single-commit cadence:

1. `frontend/package.json` — bump `"next": "^15.1.0"` -> `"next": "^16.x"` (use the published `latest` dist-tag at execute time; `^16.0.0` minimum). Bump `"eslint-config-next": "^15.5.15"` -> `"eslint-config-next": "^16.x"` (lockstep with the Next major). Bump `"engines.node": ">=20.0.0"` -> `">=20.9.0"`.
2. `frontend/pnpm-lock.yaml` — regenerated by `pnpm install` after the package.json edits.
3. `frontend/src/middleware.ts` -> `frontend/src/proxy.ts` — rename via `git mv`; rewrite the function name from `middleware` to `proxy` per the Next 16 codemod contract. Internal logic (PROTECTED_PREFIXES array, guardOrPassThrough, inferStatus, getRegistry().record bound metric call, config.matcher with the 12 protected segments + 3 operator paths) preserved verbatim. The `export const config = { matcher: [...] }` shape is unchanged.
4. `frontend/src/middleware.test.ts` -> `frontend/src/proxy.test.ts` — rename via `git mv`; update the import statement from `import { PROTECTED_PREFIXES, config, middleware } from "./middleware"` to `import { PROTECTED_PREFIXES, config, proxy } from "./proxy"`. The test bodies that call `middleware(req)` switch to `proxy(req)`. The 9 test cases (3 matcher coverage + 3 redirect behavior + 4 metric recording) preserve their assertions verbatim. Test-suite descriptive labels switch from "middleware" to "proxy" cosmetically.
5. `frontend/src/app/(auth)/login/page.tsx` — split into a parent Server Component wrapper (or keep as Client Component but lift the `useSearchParams`-reading body into a child component) wrapped with `<Suspense fallback={...}>`. The fallback is a small inline auth-skeleton (no `RouteSkeleton` "auth" variant exists per the audit; either add an "auth" variant to `frontend/src/components/skeletons/route-skeleton.tsx` OR inline a simple skeleton fragment in the login page). Plan-author selects the inline-fragment path (lower surface area, no new RouteSkeleton variant needed, no new test for the skeleton).
6. `.planning/ISSUES.md` + `.planning/STATE.md` — close i-6b; flip lock-in posture; advance Current Position cursor.

**Bundler choice:** Keep the existing webpack path for the v1.1 ship by NOT changing the `dev` / `build` scripts. Next 16's default flips to Turbopack; passing `--webpack` to the relevant scripts opts back into webpack. Turbopack-as-default is the i-6b trigger item (i): "decide whether to enable Turbopack as the default bundler OR pass `--webpack` to keep the existing webpack path." Plan-author selects `--webpack` for the v1.1 ship because (a) Turbopack may surface unrelated regressions on first build that bisect would blame on the Next 16 bump, (b) the i-6b body explicitly says "Both work; Turbopack is the recommended path going forward but may surface unrelated regressions on first build", (c) keeping webpack preserves the v0.6 + v1.0 build evidence baseline (zero unrelated bundle-size or build-time deltas), (d) Turbopack-as-default migration is a separate concern that deserves its own follow-up sub-plan. **Sub-decision:** the `dev` and `build` scripts in `frontend/package.json` get a `--webpack` flag. If Next 16 does NOT accept `--webpack` on `next start` (the production runner), only `next dev` and `next build` get the flag. (i-6b body says the flag is on `next dev` and `next build`; `next start` does not bundle.)

**Suspense wrapping strategy:** Two paths:
- **Path A (parent + child split):** Make `frontend/src/app/(auth)/login/page.tsx` the parent Client Component that returns `<Suspense fallback={<LoginSkeleton />}><LoginForm /></Suspense>`. Move the existing 99-line form body into a new file `frontend/src/app/(auth)/login/login-form.tsx` (Client Component). Rationale: cleanest separation; matches the codebase pattern (`session-client.tsx`, `dashboard/page.tsx` etc.).
- **Path B (single-file with inline child component):** Keep `page.tsx` as a single file. Define the form body as an internal function component (`function LoginForm() { ... }`) and return `<Suspense fallback={<inline skeleton />}><LoginForm /></Suspense>` from the default export. Rationale: minimal surface mutation; one file edit; preserves the existing test mock structure (`vi.mock("next/navigation", ...)` at the top of `page.test.tsx` continues to work because the inner `LoginForm` calls `useSearchParams()` on the mocked module).

Plan-author selects **Path B** because (a) it minimizes file count churn (one file edit vs three), (b) preserves the existing test structure (`page.test.tsx` mocks `next/navigation` and renders `<LoginPage />` directly; with Path B the mock continues to satisfy the inner `LoginForm`'s `useSearchParams()` call inside the same render tree), (c) the Suspense boundary in Path B still satisfies Next 16's hard-error gate because `useSearchParams()` is called inside a child component wrapped by `<Suspense>` at the page module's default export level. The fallback is a tiny inline `<div role="status" aria-busy="true" className="space-y-3"><div className="h-7 w-1/3 animate-pulse rounded bg-muted" /><div className="h-10 w-full animate-pulse rounded bg-muted" /><div className="h-10 w-full animate-pulse rounded bg-muted" /></div>` (matching the existing skeleton-pulse aesthetic without adding a new RouteSkeleton variant).

**Why this is the right call here:**

- **i-6b has an enriched closure spec (steps 1-9 in the body).** Phase 48 IS the closure window per the v1.1 milestone scope.
- **Single-commit cadence matches v1.0 / v1.1 standard.** All six edits land together; CI validates the bump as a unit.
- **Path B Suspense wrapping minimizes test churn.** The existing `page.test.tsx` mocks `next/navigation` at the module level; that mock satisfies any caller of `useSearchParams()` regardless of which component-tree depth the call lives at. The Suspense fallback never appears in the React tree under the test mock because the mocked `useSearchParams` resolves synchronously and the `<Suspense>` boundary never throws.
- **Webpack-flag retains v0.6 + v1.0 build evidence baseline.** Bisect surface stays clean; if Phase 48 ships green and a later perf-budget plan (i-15 / Phase 49) chooses Turbopack, the bisect still pins regressions on the right commit.
- **Renaming middleware to proxy preferred over deprecation-warning acceptance.** The codemod is upstream; the surface mutation is mechanical (function rename + test import-name update). Accepting the deprecation warning would leave a CI log nag for every build until Next 17 turns it into an error, and the technical debt would carry into the v1.1.0 release notes. Rename is the cleaner contract.
- **No `next.config.ts` mutation needed.** The codebase has no `images:` block to migrate (zero `next/image` callers in source), no `experimental.cacheComponents` opt-in, no `unstable_rootParams` usage, no `next/legacy/image` imports, no AMP, no `images.domains` (deprecated; replaced by `images.remotePatterns`). The framework-default path covers the codebase as-is.
- **`@types/node` already at `^25.6.0`.** No bump needed; the i-6b trigger item is pre-satisfied at HEAD.
- **CI is the verification backstop, but local gates are authoritative.** Frontend gates run on the Windows dev host (no local-maven-gap analogue for the frontend); the executor gets immediate feedback without waiting for the GitHub Actions cycle. CI re-runs the same gates as a regression backstop.

**Rejected alternatives:**

1. *Bump to a Next 16.x RC instead of stable* — rejected. The i-6b trigger says "next@^16.2.6 (or whatever is current latest stable at probe time)". RC pins are unstable and don't meet the v1.1 ship-quality bar.
2. *Accept the deprecation warning in middleware.ts instead of renaming* — rejected. See "Why this is the right call" bullet above. The codemod cost is one rename + one test import update; the carry-forward cost of a CI log nag plus eventual Next 17 hard error is worse.
3. *Add `RouteSkeleton variant="auth"` to `frontend/src/components/skeletons/route-skeleton.tsx` for the Suspense fallback* — rejected as scope creep. The login Suspense fallback is a one-off; adding a new variant requires updating the type union, adding a new switch arm, AND extending the existing `frontend/src/components/skeletons/route-skeleton.test.tsx` test suite (which asserts test-id coverage for every variant). Inline skeleton in the page module is one file, zero new tests, zero type-union edits.
4. *Path A (parent + child split into two files) instead of Path B (single-file with internal `LoginForm` function)* — rejected. See "Suspense wrapping strategy" bullet above. Path A creates a new file and forces re-mocking strategy in the test; Path B is a single-file edit that the existing test mock satisfies.
5. *Enable Turbopack as the default bundler in this plan* — rejected. See "Bundler choice" bullet above. Bundler change is a separate concern; bisect cleanliness is the v1.1 release-quality bar.
6. *Bundle the `images.remotePatterns` migration (since `images.domains` is deprecated in 16) into this plan* — rejected. Codebase has no `images.domains` usage in `next.config.ts` and zero `next/image` callers; nothing to migrate.
7. *Pre-emptively migrate `useSearchParams` reads to async Server Component params instead of Suspense-wrapping* — rejected as scope creep. The Suspense wrap is the i-6b trigger; converting the login page to read query params via a Server Component prop would require splitting the form into a child Client Component AND threading the `searchParams` prop through, which is a different architectural choice from the i-6b body's stated remediation ("the simplest fix is to lift the `useSearchParams`-reading body into a child client component and wrap the parent in `<Suspense>`").
8. *Run `next/codemod middleware-to-proxy` instead of manual rename* — accepted in spirit but not in execution. The codemod is mechanical (rename file + rename function); doing the two edits by hand is faster and avoids pulling in a one-off codemod tool dependency. The result is identical.
9. *Bundle the bump with i-15 (Lighthouse CI; Phase 49)* — rejected. v1.1 explicitly sequences Phase 48 BEFORE Phase 49. Bundling violates the "in sequence (each its own commit and CI pass)" v1.0 / v1.1 rule.
10. *Re-defer i-6b to a v1.2 milestone* — rejected. v1.1 explicitly schedules i-6b for Phase 48 per the milestone-opening scope. The deferral playbook applies when a major bump has unresolved compatibility blockers. Next 16 has zero compatibility blockers in this codebase per the i-6b body's enriched analysis (every Next 16 surface change has a known remediation or is a NON-blocker); deferring would be dishonest planning.
11. *Run `pnpm install --frozen-lockfile=false` then commit a hand-edited `pnpm-lock.yaml`* — rejected as machine-output drift risk. The lockfile is regenerated by `pnpm install` after the package.json edits; the tool's deterministic output is the canonical lockfile. Hand-editing risks divergence from the dependency tree pnpm actually resolves.
12. *Keep `eslint-config-next` at `^15.5.15` and accept any new lint errors that the framework version mismatch introduces* — rejected. The eslint-plugin-next bundled inside the config bumps in lockstep with Next major versions to introduce / remove rules tied to the new App Router conventions; running 15.x lint config against a 16.x runtime would flag false positives or miss real issues.
13. *Update CHANGELOG.md to record the Next 16 bump under `## [Unreleased]`* — rejected. Spawn prompt explicitly says "DO NOT modify CHANGELOG". CHANGELOG rotation is Phase 50 release scope.
14. *Audit every test file for `useSearchParams` mocks and add Suspense wrappers* — rejected. The test mock at `frontend/src/app/(auth)/login/page.test.tsx` lines 11-15 (`vi.mock("next/navigation", ...)`) satisfies Path B's inner `LoginForm` `useSearchParams()` call. The other 25 files that use `useSearchParams` (per the grep audit) are NOT under a `<Suspense>` boundary issue because they live inside (app) group routes that already have streaming-Suspense from Next's App Router default behavior at the segment boundary.
15. *Touch `frontend/next.config.ts`* — rejected. No `images:`, `experimental:`, `turbo:`, `webpack:`, or other config block changes are needed because the codebase has no callers that depend on the changed defaults.
16. *Add a new test that explicitly asserts the `proxy` export shape (e.g. `expect(typeof proxy).toBe("function")`)* — rejected as redundant. The existing 9-test `proxy.test.ts` (renamed from `middleware.test.ts`) already imports `proxy` and calls it; the import-and-call resolves the function-shape assertion implicitly.
17. *Add a new e2e test that exercises the Suspense fallback path on the login page* — rejected as test-surface creep. The Suspense fallback is only visible during async-data resolution; under the `useSearchParams` mock used in `page.test.tsx`, the fallback never renders. An e2e test would need to either trigger a real async navigation or mock the React internals; both are out-of-scope.
