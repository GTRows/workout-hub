# Phase 38 - Plan 01: Harden Playwright critical-flow + responsive specs against the live default-locale UI

**Milestone:** v1.0 Release Hardening (opening phase)
**Phase:** 38 - e2e-tests
**Plan:** 38-01 (specs-only sub-plan; CI wiring deferred to a follow-up sub-plan)
**Status:** Not started
**Author date:** 2026-05-09

## Goal

Make the two existing Playwright specs under `frontend/e2e/` actually pass against
a real `docker compose up` stack running the default Turkish locale, and add a
third spec covering the explicit gap in the roadmap line ("register -> login ->
workout -> session save"). The roadmap entry uses the historical wording, but
public registration was removed in t-51 (see `frontend/e2e/critical-flow.spec.ts`
header JavaDoc); this plan formalises the canonical critical path as
**admin-seeded login -> active workout day -> log three sets -> finish session
-> download Claude summary**.

The blocker preventing the existing specs from passing today is locale drift:
the specs use English regex locators (`/log in/i`, `/email/i`, `/password/i`,
`/start workout|antrenmani baslat/i`) but the default i18n locale is `tr` (per
`CLAUDE.md` and `frontend/messages/tr.json`), so a fresh `docker compose up`
serves "Giris", "E-posta", "Sifre", "Antrenmani baslat". `/log in/i` does not
match "Giris" and `/email/i` does not match "E-posta". Plan 38-01 fixes this
by switching the specs to locale-stable selectors (input `id`, `type`, `data-testid`,
explicit Turkish + English alternatives in name regexes) and tightening
the locator strategy on the session execution flow so it actually waits for
real network completion instead of relying on `page.waitForTimeout(400)`.

In addition, plan 38-01 adds:

- A third spec, `e2e/session-save-resume.spec.ts`, that proves a partially
  logged session is recoverable after a hard navigation (the offline-first
  contract from Phase 25). This closes the literal "session save" line item
  from the roadmap with a behaviour the existing critical-flow spec does not
  exercise: navigate away mid-session, return via the dashboard "Resume" path,
  and confirm logged sets are still present.
- A `frontend/e2e/README.md` documenting how to run the suite locally
  (`E2E_WEB_BASE_URL`, `E2E_ADMIN_EMAIL`, `E2E_ADMIN_PASSWORD`), how the
  admin-seeded login is wired (`APP_ADMIN_EMAIL` + `APP_ADMIN_PASSWORD_HASH`
  via `scripts/hash-password.sh`), and what each spec covers.
- An update to `.planning/STATE.md` Current Position block when the plan ships
  (handled by `/gsd:execute-plan` summary capture, not by this plan body).

CI wiring (a `e2e` job in `.github/workflows/ci.yml` that boots the stack and
runs `pnpm test:e2e`) is deliberately deferred to **plan 38-02** because
`.github/workflows/**` is on the protected-files list and adding a new job is a
material CI change that warrants its own review surface. Plan 38-02 should be
opened as soon as 38-01 is verified locally.

## Architecture Decision: Locale-stable selectors + admin-seeded login + dedicated network waits; defer CI wiring to a separate sub-plan

**Decision:** Rewrite the existing two specs and add a third, all under
`frontend/e2e/`, using the following locator strategy:

1. **Form fields** — select by stable HTML attributes (`page.locator('#email')`,
   `page.locator('#password')`, `page.locator('input[type="email"]')`,
   `page.locator('input[type="password"]')`). The login page already renders
   `id="email"` and `id="password"` on the inputs (verified in
   `frontend/src/app/(auth)/login/page.tsx` lines 73-95). These are i18n-immune.
2. **Action buttons** — keep `getByRole('button', { name })` but make the regex
   include both the EN and TR string literally:
   - Login submit: `/^(Giris|Log in)$/i`
   - Start workout: `/^(Antrenmani baslat|Start workout)$/i`
   - Resume: `/^(Devam et|Resume)$/i`
   - Finish session: `/^(Antrenmani bitir|Finish workout)$/i`
   - Download summary: `/^(Ozeti indir|Download summary)$/i`
   The TR strings come from `frontend/messages/tr.json` (lines 47, 49, 85, 335)
   and the EN strings from `frontend/messages/en.json` (same keys). The
   regex is anchored to avoid accidentally matching banner text.
3. **Set-row inputs and "Done" buttons** — switch from text regex to
   `data-testid` attributes that the executor adds to the session-execution
   client. The current spec uses `getByLabel(/^reps$|^tekrar$/i)` and
   `getByRole('button', { name: /^done$|^tamam$/i })`, which are fragile
   because the i18n key for the rep input label may not be exactly "Reps" /
   "Tekrar" (varies between `session.repsLabel`, `setForm.reps`, etc.).
   Adding `data-testid="set-reps-input"` and `data-testid="set-done-button"`
   on the set-row component makes the locator i18n-immune AND robust against
   future copy changes. This is a one-line non-functional addition to a single
   client component.
4. **Network waits** — replace the existing `page.waitForTimeout(400)` after
   each "Done" click with `page.waitForResponse((res) => res.url().includes('/api/sessions/') && res.url().endsWith('/sets') && res.status() < 400)`.
   This makes the spec deterministic in CI (where the 400 ms timer races with
   slow Postgres warmup) and removes the only `waitForTimeout` in the suite.
5. **Admin login fixture** — extract the login flow into
   `frontend/e2e/fixtures/auth.ts` exporting `loginAsAdmin(page)`. All three
   specs then share one canonical login path. Removes copy-paste drift across
   specs.

**Stack assumption:** Specs run against a live `docker compose up` (or `pnpm
dev` proxying to a backend on port 8080) seeded with one admin via
`APP_ADMIN_EMAIL=admin@workouthub.local` and a `bcrypt` hash of
`E2E_ADMIN_PASSWORD=ChangeMe-Admin-1!`. The seeding path is `AdminSeeder` (per
`backend/src/main/java/com/workouthub/admin/AdminSeeder.java`). The plan's
`frontend/e2e/README.md` documents the exact commands.

**Why this is the right call here:**

- **Closes the locale gap** that prevents the existing skeletons from running
  green. Without (1) and (2), the suite is decorative.
- **No protected-file edits.** Per `CLAUDE.md`'s Protected Files list, the
  files this plan touches are all unprotected: `frontend/e2e/*.spec.ts`,
  `frontend/e2e/fixtures/auth.ts` (new), `frontend/e2e/README.md` (new), and
  `frontend/src/app/(app)/session/[id]/session-client.tsx` (test-id add only).
  `package.json`, `playwright.config.ts`, and `.github/workflows/ci.yml`
  are NOT touched.
- **Playwright already a dev-dep.** `frontend/package.json` lines 40 and 16
  declare `@playwright/test ^1.49.0` and a `test:e2e` script. No
  `package.json` mutation is required, removing the protected-file halt
  condition this phase would otherwise hit.
- **Configuration already correct.** `frontend/playwright.config.ts` already
  defines `testDir: ./e2e`, the `chromium` project, `baseURL` from
  `E2E_WEB_BASE_URL`, and `retries: 2` in CI. No config changes needed.
- **Scope-disciplined.** Plan 38-01 is specs-only. CI wiring (which would
  edit a protected workflow) is deferred to plan 38-02 so a maintainer can
  approve the workflow edit explicitly.
- **Local-Maven-gap aware.** Per repo memory, backend `mvn` is unavailable on
  this Windows host. The plan's verification gate is structural (file presence,
  selector audit, `pnpm typecheck` + `pnpm test:e2e --list` to confirm the
  Playwright runner enumerates the specs without compile errors). Full e2e
  execution against a live stack runs in plan 38-02's CI job, not locally.

**Rejected alternatives:**

1. *Edit `playwright.config.ts` to default the locale to `en` for tests* —
   rejected. The default-locale build is what operators ship; tests should
   exercise the same locale operators see, not a test-only locale. Also
   `playwright.config.ts` does not control Next.js i18n; that lives in
   `frontend/src/middleware.ts` and `frontend/i18n/` and is harder to
   override per-test.
2. *Pin tests to `?lang=en` query strings or `Accept-Language` headers* —
   rejected. The next-intl middleware does not honour an explicit lang
   override on every route (the matcher is in `middleware.ts` and resolves
   from cookie / Accept-Language). Adding a lang-override path just for tests
   creates a parallel surface; using both EN+TR literals in the regex is
   cheaper.
3. *Extract all i18n strings the spec needs and import them into the spec
   file* — rejected. Couples specs to the message-bundle build, fights
   Next.js' i18n loader, and makes the spec fragile to message-key renames.
   Anchored EN+TR alternation regex is the smallest stable surface.
4. *Use Playwright's `getByLabel` exclusively and rely on the form's
   `<Label htmlFor>` linkage* — partially adopted. `getByLabel` is fine
   for explicit labels but the existing regex `/email/i` does not match
   "E-posta". Switching to `getByLabel(/E-posta|Email/i)` works but the
   form ALSO renders `id="email"` directly on the input, which is a stronger
   contract (the input's `id` attribute is in the source code, not a
   translated copy). Plan uses `id`-anchored locators where available and
   anchored EN+TR `getByLabel` regexes elsewhere.
5. *Wire the CI e2e job in this same plan* — rejected. `.github/workflows/**`
   is protected. Touching it requires explicit user approval and is a
   material change that should be reviewed in isolation. Plan 38-02 owns it.
6. *Add a backend integration test that exercises the same critical path
   instead of a frontend e2e* — rejected. The roadmap explicitly says
   "Playwright critical flows", and the value of e2e is exercising the
   browser layer (offline queue, set-row form submission, auth token
   refresh) that backend integration tests cannot reach.
7. *Skip the third spec (`session-save-resume`) and rely on the existing
   critical-flow spec to cover the "session save" wording* — rejected. The
   existing spec finishes the session immediately after logging three sets;
   it never proves the partial-progress recovery contract. Roadmap line
   says "session save", which in the offline-first design means
   "logged sets persist across navigation". A dedicated spec is the right
   surface.
8. *Add `data-testid` attributes everywhere instead of selectively* —
   rejected. Test-id sprawl pollutes production HTML. Plan adds test-ids
   only on the two locators the spec actually needs (`set-reps-input`,
   `set-done-button`) and relies on stable HTML semantics (input id, role)
   elsewhere.
9. *Delete the existing `responsive-360.spec.ts` because mobile checks are
   covered by the perf-budget doc (i-15)* — rejected. The responsive spec
   is cheap, deterministic, and proves a different contract (no horizontal
   overflow at 360px). Keep and harden.

### Task 5: Add the session-save-resume spec

**File:** `frontend/e2e/session-save-resume.spec.ts` (new)

**Action:**

Create the spec covering the partial-progress recovery contract. The body
proves: log in, start a session, log ONE set, navigate to `/exercises`,
return to `/dashboard`, click Resume, return to the session, confirm the
logged set's reps value is still "10".

Outline (executor copies verbatim, adjusting only inline comments for
tone — no emoji):

```ts
import { expect, test } from "@playwright/test";
import { loginAsAdmin } from "./fixtures/auth";

/**
 * Proves the offline-first session contract: a session that has logged at
 * least one set survives navigation to another route and is resumable from
 * the dashboard. Companion to critical-flow.spec.ts (which finishes the
 * session immediately).
 */

test.describe.configure({ mode: "serial" });

test("partial session survives navigation and is resumable", async ({ page }) => {
  await loginAsAdmin(page);

  // Start a session from the dashboard. If a session is already active
  // from a prior failed run, resume it; otherwise start one.
  const startButton = page.getByRole("button", { name: /^(Antrenmani baslat|Start workout)$/i });
  const resumeButton = page.getByRole("button", { name: /^(Devam et|Resume)$/i });
  if (await resumeButton.isVisible().catch(() => false)) {
    await resumeButton.click();
  } else {
    await startButton.click();
  }
  await expect(page).toHaveURL(/\/session\//);
  const sessionUrl = page.url();

  // Log ONE set.
  const repsInput = page.locator('[data-testid="set-reps-input"]').first();
  const doneButton = page.locator('[data-testid="set-done-button"]').first();
  await repsInput.fill("10");
  await doneButton.click();
  await page.waitForResponse(
    (res) =>
      /\/api\/sessions\/.+\/sets$/.test(res.url()) &&
      res.request().method() === "POST" &&
      res.status() < 400
  );

  // Navigate away and back via the dashboard.
  await page.goto("/exercises");
  await page.goto("/dashboard");
  await expect(resumeButton).toBeVisible();
  await resumeButton.click();
  await expect(page).toHaveURL(sessionUrl);

  // Confirm the logged set's value persisted.
  await expect(repsInput).toHaveValue("10");
});
```

- Imports `loginAsAdmin` from `./fixtures/auth`.
- Does NOT call any finish-session button.
- Uses `data-testid` selectors (so it matches the test-ids added in Task 1).

## Risk + Mitigation

| Risk | Probability | Mitigation |
|---|---|---|
| Default-locale TR strings drift in a future i18n update and break the EN+TR alternation regex | LOW | Anchored `^(Giris|Log in)$/i` style regex; if `messages/tr.json` changes "Giris" -> "Giris Yap" the spec will fail loudly with a clear locator-not-found error rather than passing silently. The test then accompanies the message-bundle change in the same PR. |
| `data-testid` collides with another consumer (e.g. RTL test) | LOW | `Grep` audit in Task 8 confirms exactly one occurrence each. The existing `session-client.test.tsx` does not query by `data-testid`. |
| `waitForResponse` predicate is too narrow and times out | LOW | Predicate matches `/\/api\/sessions\/.+\/sets$/` with method POST and status < 400 — exactly what the session-execution flow emits per `frontend/src/lib/api/endpoints.ts`. If the endpoint shape changes (e.g. `POST /api/sessions/{id}/set-batch`), the spec fails loudly and the predicate updates with the endpoint change. |
| Fresh CI run finds no admin user because seeding env vars are not set | EXPECTED | This plan is specs-only; CI is plan 38-02. Plan 38-02 is responsible for setting `APP_ADMIN_EMAIL` + `APP_ADMIN_PASSWORD_HASH` in the e2e job env. Local runs use whatever `.env` values the operator already has. |
| `frontend/e2e/screenshots/` clutters `git status` after a local run | LOW | `screenshots/.gitignore` ignores all files except `.gitkeep` and the gitignore itself. PNGs from `responsive-360.spec.ts` stay untracked locally. |
| Adding `data-testid` to production code violates "no test-ids in prod" convention | LOW | `CLAUDE.md` does not prohibit `data-testid`. Two attributes on two elements is the minimum surface. The alternative (i18n-coupled label regex) is more fragile. Document the convention in `frontend/e2e/README.md` so future contributors know the policy. |
| Running `pnpm exec playwright test --list` requires the Playwright browser binaries to be installed | LOW | `--list` does NOT need browsers — it only parses spec files. Browser installation (`pnpm exec playwright install`) is needed only at execution time, which is plan 38-02's concern. |
| The session-save-resume spec races the offline queue and reads the rep value before the optimistic UI update lands | LOW | Spec uses `waitForResponse` after the "Done" click, ensuring the server has accepted the set before navigation. After return, `expect(repsInput).toHaveValue("10")` retries within Playwright's expect timeout (10s per `playwright.config.ts`), which is ample for the server-render of the resumed session. |
