## Architecture Decision: One sub-plan covers all four files; DATA_SCHEMA.md is the only true rewrite, the other three are audit-and-refresh; no source code, no protected files, no migrations, no CHANGELOG

**Decision:** Author Phase 42 as a single sub-plan, not multi-leg. Reasons:

- **The deliverable mass is asymmetric.** DATA_SCHEMA.md is a placeholder-to-document rewrite (~80-150 lines of new content). API.md, DEPLOYMENT.md, README.md are all audit-and-refresh operations (likely tens of lines of net diff each — refreshing version anchors, verifying env var lists, adding cross-links). Splitting into 42-01 (DATA_SCHEMA + API) and 42-02 (DEPLOYMENT + README) would inflate the bookkeeping cost (two SUMMARY files, two commits, two CI rounds) for no engineering benefit. The four files are mutually independent at the diff level.
- **All four files are docs-only.** No Java source change, no Flyway migration, no `pom.xml`, no `frontend/package.json`, no `compose.yml`, no `.github/workflows/**`, no `scripts/**`. The protected-files list per `CLAUDE.md` is entirely UNTOUCHED. The plan's executor never has to halt at the pre-edit hook.
- **DATA_SCHEMA.md content is fully derivable from the migration set.** All 28 V-files exist on disk under `backend/src/main/resources/db/migration/`; 17 of them contain `CREATE TABLE` per Grep. The doc is a careful read-and-summarize pass over those files plus the JPA entity definitions; no runtime introspection needed (and it would be impossible anyway since `local_maven_gap` blocks local mvn / Docker Postgres on this Windows host). The migration filenames + `CREATE TABLE` blocks are the source of truth.
- **API.md, DEPLOYMENT.md, README.md need confirmatory audit, not rewrite.** The post-Phase-19 / post-Phase-33 / post-Phase-34 versions of these files are already operator-grade. The v1.0 review has two real jobs: (a) verify nothing has drifted since the last refresh (env vars, route lists, version anchors), (b) add cross-links to the new DATA_SCHEMA.md so the documentation cluster is internally consistent. Neither is a rewrite.
- **No CHANGELOG, no RELEASE.md, no IDENTITY.yaml change.** Spawn prompt explicitly forbids those; the v1.0 release cut is Phase 44. CHANGELOG entries for the docs phase live in the Phase 44 release prep.
- **No `.planning/ISSUES.md` mutation.** No issue is closed by this plan; no new issue is opened by it. The only open issue that touches docs is i-13 (SpringDoc bump to remove `ControllerAdviceBean` workaround), and that closes by editing `pom.xml` + Java source, not by editing `docs/API.md`. i-15 (Lighthouse CI / bundle-size) requires `.github/workflows/**` + `scripts/**` + `frontend/package.json` edits, all protected; out of scope.
- **No CI gate beyond the markdown-lint + link-check workflows already in place.** This is a content-correctness pass; the validation is "did the executor capture the schema accurately and refresh the env-var lists" — verifiable by Read-and-grep at verification time, not by a build.

**Why not split into per-file sub-plans:**

1. *42-01 = DATA_SCHEMA.md only; 42-02 = API.md + DEPLOYMENT.md; 42-03 = README.md* — rejected. The README cross-link addition depends on DATA_SCHEMA.md existing first; running them in separate sub-plans across days adds churn without engineering benefit. A single executor session can sequence them naturally.
2. *42-01 = audit-only AUDIT.md; 42-02 = the actual edits* — rejected. Phase 13, 15, 16, 17, 18, 19 used a leading audit because those phases had architectural decisions to lock in (DTO shape, SpringDoc artifact pick, security-scheme design). Phase 42 has no architecture decisions; the four deliverable shapes are already named verbatim by the roadmap. Adding an AUDIT pass would be ceremony.
3. *42-01 covers DATA_SCHEMA.md only; defer the other three to a v1.1 doc cycle* — rejected. The roadmap explicitly names all four in the Phase 42 line; deferring would mean either renaming the phase or opening a new issue. Both are worse than just landing the four together.
4. *Inline a "what's missing" stub doc instead of writing DATA_SCHEMA.md* — rejected. The placeholder text already says "captures the ER overview once PHASE 1 lands the first real migration"; PHASE 1 closed years ago in real time. The placeholder is the issue Phase 42 was authored to close.
5. *Hand-write the schema as a copy of the SQL* — rejected. The migrations are the canonical SQL; duplicating them in markdown would create a drift surface (the schema bumps every time a new V-file lands). The doc summarizes (table list + relationships + invariants), it does NOT reproduce DDL.
6. *Auto-generate DATA_SCHEMA.md via SchemaCrawler / SQL-Hibernate-introspection* — rejected. Adds a runtime tool dep (`pom.xml` mutation) for content that changes maybe once per phase. Hand-write the doc; refresh it the next time a V-file lands. The cost is bounded.
7. *Generate DATA_SCHEMA.md by walking the JPA entities only* — rejected. Entities and migrations can drift (Phase 1 lock-in: `spring.jpa.hibernate.ddl-auto=validate` makes the migrations the truth and entities the consumer). The migration set is the right source.
