<objective>
Add an opt-in `pg_dump` sidecar service to `compose.yml` per `docs/SELF_HOSTED_CONTRACT.md` section 5.2. The sidecar runs on a cron schedule, writes `pg_dump --format=custom` snapshots into `./data/backups/<date>.dump`, and prunes old snapshots by retention days. Default off (operator opts in via Compose profile).

Purpose: Operators need a first-party path to point-in-time-ish Postgres backups without writing their own sidecar. Keeping this service profile-gated means it does not run on a fresh `docker compose up` - the operator explicitly opts in.

Output: New service block in `compose.yml`, host directory `data/backups/.gitkeep`, README/CONFIGURATION reference (Phase 9 will polish).

**Research decision (made during planning):** Use `prodrigestivill/postgres-backup-local` (maintained, multi-arch amd64+arm64, has cron + retention + custom format built-in). Building a custom alpine + cron + pg_dump image would duplicate a battle-tested project for marginal benefit. Pin to a specific version tag.
</objective>

Add a new service `db_backup` (or `pg_dump`) to `compose.yml`, gated by Compose profile `backup`. Use `prodrigestivill/postgres-backup-local:16` (matches the db service's Postgres 16). Pin to a specific point release if a tag like `:16-alpine` exists; otherwise use `:16` and document that Renovate will bump it.

```yaml
  pg_dump:
    image: prodrigestivill/postgres-backup-local:16
    profiles: ["backup"]
    restart: unless-stopped
    env_file:
      - .env
    environment:
      POSTGRES_HOST: db
      POSTGRES_DB: ${POSTGRES_DB}
      POSTGRES_USER: ${POSTGRES_USER}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_EXTRA_OPTS: "--format=custom --blobs"
      SCHEDULE: ${PG_DUMP_SCHEDULE:-0 3 * * *}
      BACKUP_KEEP_DAYS: ${PG_DUMP_RETENTION_DAYS:-7}
      BACKUP_KEEP_WEEKS: 0
      BACKUP_KEEP_MONTHS: 0
      HEALTHCHECK_PORT: 8080
    volumes:
      - ./data/backups/:/backups
    networks:
      - workouthub-net
    depends_on:
      db:
        condition: service_healthy
    deploy:
      resources:
        limits:
          cpus: "0.5"
          memory: 128M
        reservations:
          cpus: "0.05"
          memory: 32M
    healthcheck:
      test: ["CMD-SHELL", "wget -q --spider http://localhost:8080/ || exit 1"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 30s
```

Notes on choices baked in:
- `profiles: ["backup"]` means the service is inert under plain `docker compose up`. Operator runs `docker compose --profile backup up -d` OR sets `COMPOSE_PROFILES=backup` in their `.env`.
- `BACKUP_KEEP_WEEKS=0` and `BACKUP_KEEP_MONTHS=0` keep retention purely day-based. The image's default rolls weekly/monthly snapshots; operators who want that can override these env vars in their `.env`.
- `HEALTHCHECK_PORT=8080` is the image's built-in HTTP server reporting last-backup-status; the healthcheck probes it. The port is internal to the container only (not published), so no host-port conflict.
- Volume `./data/backups/:/backups` follows the bind-mount pattern (Phase 1).
