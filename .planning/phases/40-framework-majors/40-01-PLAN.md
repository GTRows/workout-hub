## Architecture Decision: re-defer i-8 as i-8b; do not bump pom.xml; preserve every existing AbstractIntegrationTest / SpringDoc-workaround / structured-logging surface unchanged

**Decision:** Do **not** edit `backend/pom.xml`. The `<parent>` `<version>` is already at `3.5.14`, which is the tail of the published 3.5.x patch line on Maven Central as of 2026-05-09 (verified at plan-author time via the authoritative `maven-metadata.xml` whose `<lastUpdated>` is `20260423155822`; the version chain ends at `3.5.14` before the major break to `4.0.0-M1`). There is no `3.5.15` or higher stable patch available to bump to. The Spring Boot 4 jump is a real major migration (Jackson 2 -> Jackson 3 default, Jackson2 module relocation, Prometheus actuator endpoint relocation, Spring Framework 7, Spring Security 7, Hibernate 7, Jakarta EE 11) that exceeds the original 40-01 single-line-bump budget. Re-defer it as i-8b and leave the runtime pinned at 3.5.14 for v1.0.

**Why this is the right call here:**

- **3.5.14 IS the tail of the 3.5.x patch line.** Authoritative source: `https://repo1.maven.org/maven2/org/springframework/boot/spring-boot-starter-parent/maven-metadata.xml` (queried 2026-05-09). The 3.5 chain in order: `3.5.0, 3.5.1, 3.5.2, 3.5.3, 3.5.4, 3.5.5, 3.5.6, 3.5.7, 3.5.8, 3.5.9, 3.5.10, 3.5.11, 3.5.12, 3.5.13, 3.5.14`. The next published version is `4.0.0-M1`. The `<lastUpdated>` field is `20260423155822` (2026-04-23). No newer 3.5.x patch is available. The codebase pin is already at the tail. A "bump to the latest 3.5.x patch" within v1.0 is therefore a no-op.
- **Spring Boot 4 cannot land within the original 40-01 single-line-bump budget.** The executor's enriched i-8 note documents three breaking-change surfaces that the original plan did not foresee:
  1. `Jackson2ObjectMapperBuilderCustomizer` package relocation (`org.springframework.boot.autoconfigure.jackson` -> `org.springframework.boot.jackson2.autoconfigure`). Affects `JacksonConfig.java`. Trivial import-line edit.
  2. `PrometheusScrapeEndpoint` + `PrometheusOutputFormat` package relocation (`org.springframework.boot.actuate.metrics.export.prometheus` -> `org.springframework.boot.micrometer.metrics.autoconfigure.export.prometheus`). Affects `PrometheusMetricsController.java`. Trivial import-line edits.
  3. **BLOCKING — Jackson 2 vs Jackson 3 default-classpath shift.** Spring Boot 4 makes Jackson 3 (`tools.jackson.*`) the default transitive of `spring-boot-starter-web` via the `spring-boot-starter-jackson` -> `spring-boot-jackson` chain. The Jackson 2 family (`com.fasterxml.jackson.*`) is now opt-in via the separate `spring-boot-jackson2` module. This codebase has **36 files** referencing Jackson 2 — `JacksonConfig`, `ClaudeSummaryDto.@JsonNaming(SnakeCaseStrategy)`, `AuditLogService`, all DTO `@JsonInclude(NON_NULL)` annotations, `WebPushNotificationDispatcher`, `GoogleFitParser`, `AppleHealthParser`, etc. The post-rollback CI showed `package org.springframework.boot.jackson2.autoconfigure does not exist` even after the import-path fix because the `spring-boot-jackson2` module is not pulled in transitively by any of the starters this project uses (`spring-boot-starter-web`, `-data-jpa`, `-security`, `-validation`, `-actuator`).
- **Two real follow-up paths exist; both exceed v1.0 scope.** Either (a) add `spring-boot-jackson2` as an explicit dependency AND verify Spring MVC's `HttpMessageConverter` selection picks the Jackson 2 `ObjectMapper` (not the Jackson 3 one — both will be on the classpath simultaneously), OR (b) migrate all 36 Jackson 2 usages to Jackson 3 (`tools.jackson.*`). Path (a) needs runtime verification that the local-Maven-gap cannot validate without a CI round-trip per attempt. Path (b) is a 36-file mechanical edit plus annotation re-validation that exceeds the i-8 single-bump budget. Neither fits v1.0 release-hardening's "small, ship-able, single commit + test pass" cadence.
- **Mirror the i-7/i-7b playbook from Phase 39-01.** That phase faced the same pattern: an issue named "1.x -> 2.x major bump" whose 2.x artifact did not yet exist, so Phase 39-01 captured the maximum-yield 1.x cumulative bump (1.20.4 -> 1.21.3) and re-deferred the 2.x portion as i-7b with a precise upstream-publish trigger. The i-8 case is symmetrical in structure: an issue named "3.4 -> 4.0 major bump" whose `4.0.x` artifact exists but whose adoption requires a Jackson-2-vs-3 codebase decision the v1.0 milestone cannot absorb. The mirror is: (i) close i-8 with a closure note recording what was actually done (re-deferred after rollback; no runtime change; 3.5.x line confirmed at tail patch), (ii) create i-8b with the precise re-open trigger (Jackson 2 -> 3 codebase migration sub-plan completes OR `spring-boot-jackson2` module proves runtime-viable in a dedicated probe sub-plan).
- **Preserve every existing surface unchanged.** No edits to `backend/pom.xml`, `backend/src/main/java/com/workouthub/common/config/JacksonConfig.java`, `backend/src/main/java/com/workouthub/metrics/web/PrometheusMetricsController.java` (or wherever the actuator surface lives), `SecurityConfig.java`, `OpenApiConfig.java`, `application.yml`, `application-prod.yml`, the structured-logging customizer, the SpringDoc 2.6.0 ControllerAdviceBean workaround, or the AbstractIntegrationTest scaffolding. The plan output is strictly `.planning/ISSUES.md` + `.planning/STATE.md` bookkeeping plus the PLAN.md replacement that this file represents. Zero protected-file runtime edits.
- **CVE posture is unchanged from v0.6.0.** The original feedback note hinted that bumping the 3.5.x patch would close pending CVEs. The Maven Central index proves no newer 3.5.x patch exists, so there is no in-flight CVE to close on the 3.5.x line via this plan. Trivy posture for v1.0 stays identical to v0.6.0 (Netty CVE-2026-42577 remains suppressed via `.trivyignore` per i-14; Spring Boot 3.5.14 transitive deps carry no known new CVE that v0.6.0's CI Trivy scan reported as unsuppressed). The CVE posture is the trigger for i-14 (Phase 41 security-hardening), not this plan.
- **Local-Maven-gap aware.** Per repo memory, backend `mvn` is unavailable on this Windows host. The plan's verification gate is structural only (file presence, exact pin values via `Read` calls, `Grep` checks for issue-bookkeeping presence/absence). No CI run is required because no runtime artifact changes; the bookkeeping commit still runs CI as a sanity check (and is expected to pass green identically to the v0.6.0 baseline because no production code changes).
- **Single-bookkeeping-commit posture matches the roadmap.** The roadmap line says "in sequence (each its own commit and test pass)". This plan produces exactly one commit (PLAN.md replacement + ISSUES.md i-8 close + i-8b open + STATE.md mapping update) and one CI green pass before sub-plan 40-02 (Next 16) starts. No mixing.
