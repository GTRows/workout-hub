# Phase 40 - Plan 02: Re-defer Next.js 16 (i-6 -> i-6b) until next-intl 4 lands; ship planning-bookkeeping only

**Milestone:** v1.0 Release Hardening
**Phase:** 40 - framework-majors (Spring Boot 4 / Next 16 / next-intl 4 in sequence)
**Plan:** 40-02 (second sub-plan; closes deferred issue i-6 by re-deferring it to a successor entry, exactly mirroring the 40-01 / i-8 -> i-8b playbook). Sub-plan 40-03 (next-intl 3 -> 4 major) follows this one in commit/CI sequence per the roadmap line and is the **prerequisite** that unblocks i-6b.
**Status:** Not started
**Author date:** 2026-05-09
**Predecessor:** 40-01 shipped at 30b8d97 (Spring Boot 4 deferred to i-8b; bookkeeping only).

## Goal

Honestly record that the v1.0 milestone cannot land Next.js 15.x -> 16.x within Phase 40-02's standalone single-commit budget because the in-tree i18n stack (`next-intl@^3.26.0`) is incompatible with Next 16 at the npm peer-dependency level. Re-defer the major framework bump as successor issue **i-6b** keyed to the actual unblocker (Phase 40-03 / i-5 next-intl 4 migration completes first). Mirror the i-7 -> i-7b (Phase 39-01) and i-8 -> i-8b (Phase 40-01) deferral playbook verbatim — close the original i-6 with a closure note that captures the dependency-graph evidence collected at plan-author time, and create a fresh i-6b that records the precise re-open trigger.

The roadmap line for Phase 40 reads "i-8 Spring Boot 4, i-6 Next 16, i-5 next-intl 4 in sequence (each its own commit and test pass)". The roadmap order assumed Next 16 could ship before next-intl 4. Plan-author research disproves that assumption: the 3.26.x line of next-intl tops out at peer `next ^15.0.0` and there is no 3.x release that adds Next 16 to its peer range. Only next-intl 4.x peers `^16.0.0`. Therefore, the actual workable sequence inside Phase 40 is:

- 40-01: Spring Boot 4 -> deferred as i-8b (shipped at 30b8d97).
- 40-02 (this plan): Next 16 -> deferred as i-6b because the next-intl 3 peer-range blocks the install.
- 40-03: next-intl 3 -> 4 major migration (i-5 closure attempt).
- After 40-03 lands and CI is green, the v1.0 milestone may optionally re-open i-6b as a follow-up sub-plan IF the maintainer chooses to absorb Next 16 within the remaining v1.0 phases (38, 41, 42, 43, 44 are still open work). The default in this plan is to leave i-6b open and let the v1.1 milestone-opening sub-plan close it.

This plan covers the Next 16 deferral leg only and produces a single planning-bookkeeping commit (no runtime change to `frontend/package.json`, `frontend/pnpm-lock.yaml`, `frontend/next.config.ts`, or any frontend source file). Sub-plan 40-03 (next-intl 4) is out of scope here.

## Architecture Decision: re-defer i-6 as i-6b; do not bump `frontend/package.json`'s `next` pin; preserve every existing App Router / middleware / route-handler / `useReportWebVitals` / dynamic-route / `useSearchParams` / standalone-output / SW / metrics surface unchanged

**Decision:** Do **not** edit `frontend/package.json`, `frontend/pnpm-lock.yaml`, `frontend/next.config.ts`, or `frontend/eslint.config.mjs`. The current `next` pin is `^15.1.0`, which resolves to the 15.5.x backport line (latest stable backport `15.5.18` per the npm `backport` dist-tag at plan-author time, well within the caret range). The 15.x line is still actively patched on the `backport` dist-tag. The Next 16 jump is a real major migration (App Router behavioural changes, deprecated `Middleware` API renamed to `Proxy`, new ESLint flat-config default, removed deprecated `unstable_rootParams`, removed deprecated AMP support, removed sync access to Dynamic APIs, mandatory `images.localPatterns` for query strings on `<Image>` `src`, default `images.minimumCacheTTL` bumped from 1 minute to 4 hours, Turbopack as default bundler, sass-loader v16 bump, eslint-plugin-react-hooks v7 bump, default browserslist update, removal of 16px from `images.imageSizes` defaults, deprecation of `images.domains` and `next/legacy/image`, "Cache Components" experimental work, and a TypeScript 5.1.0 minimum) that exceeds Phase 40-02's standalone single-commit budget given the next-intl 3.26.x peer-range block. Re-defer it as i-6b and leave the runtime pinned within the `^15.1.0` caret for v1.0.

**Why this is the right call here:**

- **next-intl 3.26.x peer-range BLOCKS the Next 16 install.** Authoritative source: `https://registry.npmjs.org/next-intl` (queried 2026-05-09). The package metadata for every published 3.x version, including the 3.26.x line tail, declares:

  ```
  peerDependencies.next: "^10.0.0 || ^11.0.0 || ^12.0.0 || ^13.0.0 || ^14.0.0 || ^15.0.0"
  ```

  Plan-author scanned all 3.x versions from `3.0.0` upward and confirmed **zero versions** in the 3.x line list `next ^16.0.0` as a supported peer. Only the 4.x line lists `^16.0.0`:

  ```
  next-intl@4.11.1 peerDependencies.next: "^12.0.0 || ^13.0.0 || ^14.0.0 || ^15.0.0 || ^16.0.0"
  ```

  Bumping `next` to `^16.0.0` while keeping `next-intl@^3.26.0` in the same lockfile would produce one of three outcomes, all bad: (a) `pnpm install` fails the peer-dependency check by default and refuses to write a lockfile; (b) the operator forces install with `--strict-peer-dependencies=false` (or pnpm equivalent), the lockfile resolves anyway, but the `next-intl` runtime hits API surfaces that 3.x never tested against Next 16 (the known-incompatible surfaces include `next/server` types, `next/navigation` `useSearchParams` Suspense gating, the new App Router `params: Promise<...>` enforcement, and the deprecated `middleware` API that next-intl 3.x's `createNextIntlPlugin` patches); (c) the operator adds a `pnpm.overrides` block to silence the peer-check, hiding a real compatibility risk behind a build-time override. Neither (b) nor (c) is acceptable for v1.0 release-hardening's "small, ship-able, single commit + test pass" cadence.

- **15.x patch line is still active; the existing pin already captures the latest patch.** The npm `backport` dist-tag for `next` resolves to `15.5.18` at plan-author time (queried 2026-05-09). The published times confirm a real backport cadence: `15.5.13..15.5.18` lands across late 2025 and through 2026-Q2. Our `^15.1.0` caret range subsumes everything from `15.1.0` up to but not including `16.0.0`, so a routine `pnpm install` after this plan ships will naturally pick up `15.5.18` (or whatever 15.x backport is current at executor run-time) without any package.json edit. The pin posture is therefore strictly sufficient to keep the frontend on a security-patched 15.x line for the remainder of v1.0.

- **Next 16 has six independently-blocking surfaces in this codebase** that 40-02 would have to absorb in lockstep — that workload alone would exceed a single planning-bookkeeping cycle even before the next-intl 3 peer block lands:
  1. **`Middleware` API renamed to `Proxy`.** Per the v16.0 release notes (`#84764 Deprecate Middleware API and add Proxy API`, `#84119 Deprecate "middleware" and recommend "proxy"`, `#84127 Add codemod for "middleware" to "proxy"`), the existing `frontend/src/middleware.ts` (which both authenticates protected routes AND records frontend HTTP metrics into the Phase-35 hand-rolled registry) keeps working in 16.x via a deprecation warning, but the canonical migration is to rename the file to `proxy.ts` and re-export the same handler. The 12 `(app)`-group route segments in `PROTECTED_PREFIXES` plus the three operator paths in `config.matcher` (`/api/healthz`, `/api/livez`, `/api/metrics`) plus the bound metric-recording call to `getRegistry().record(...)` plus the route-label normalisation must all survive the rename or fall back to the deprecation-warning path. The plan author's audit also confirmed `frontend/src/middleware.test.ts` exercises the matcher contract (Phase 29.5 lock-in); that test would need a renamed import or a side-by-side `proxy.test.ts`. Either path is real frontend work, NOT a bookkeeping commit.
  2. **`useSearchParams` is now subject to stricter Suspense gating in App Router.** Next 16's stricter prerender model around `useSearchParams` means every client component that calls it during initial render must now be wrapped in a `<Suspense>` boundary or the build emits a hard error (no longer a warning). The plan-author audit (`Grep useSearchParams frontend/src`) found exactly one production caller in the auth flow (`frontend/src/app/(auth)/login/page.tsx`) plus 25 test files. The login page is currently a top-level route that renders a `useSearchParams()` value to extract the `?next=` redirect target and a `?reason=session-expired` toast trigger. Today it works under Next 15 because Next 15 emits a build-time warning for un-suspended `useSearchParams`. Under Next 16 the warning becomes a fatal build error. The fix is mechanical (wrap the component body in `<Suspense fallback={...}>`), but it is real source-file mutation, NOT bookkeeping. (Plan-author confirmed via `Grep Suspense frontend/src` that the codebase has zero existing `<Suspense>` boundaries — every fix would be net-new.)
  3. **`useReportWebVitals` / `next/web-vitals` runtime stays.** Confirmed via inspection of the v16.0 release-notes diff that the `next/web-vitals` re-export (used by `frontend/src/components/web-vitals-reporter.tsx`) is preserved and unchanged in Next 16. This is a NON-blocker but worth noting — the v0.6 lock-in (use the framework-native re-export instead of the standalone `web-vitals` package) survives the upgrade.
  4. **App Router `params` are already async-shaped and would survive the bump.** Plan-author confirmed via `Grep params: Promise frontend/src` that both dynamic-route pages (`session/[id]/page.tsx`, `exercises/[id]/page.tsx`) already accept `params: Promise<{ id: string }>` and `await` it. This was the Next 15 forward-looking shape; Next 16 hard-removes the synchronous form (`#84179 Remove deprecated sync access to Dynamic APIs`). NON-blocker.
  5. **Default `images.minimumCacheTTL` bump from 1 minute to 4 hours** (`#84105`), default `images.imageSizes` losing the 16px entry (`#84647`), and `images.domains` deprecation (`#84625`). Plan-author confirmed `frontend/next.config.ts` does NOT set any `images` block — this codebase relies on the framework defaults for `next/image`. NON-blocker for the bump itself, but the executor will need to validate the runtime image cache TTL bump does not regress any operator-facing CDN posture (the self-hosted contract does not specify image-cache TTL; this is a behavioural change but not a contract violation).
  6. **TypeScript 5.1.0 minimum + sass-loader v16 + eslint-plugin-react-hooks v7 + browserslist update + ESLint flat-config default for `@next/eslint-plugin-next`.** Plan-author confirmed `frontend/package.json` already declares `typescript: "^5.7.2"` (well above 5.1.0), no `sass`/`sass-loader` in `dependencies` or `devDependencies` (NON-blocker), no direct `eslint-plugin-react-hooks` dependency (it's transitive via `eslint-config-next`, which would also bump in lockstep with `next` if the executor used `eslint-config-next@latest`). The flat-config default is also a NON-blocker because `frontend/eslint.config.mjs` is already a flat config (uses `FlatCompat` and exports an array). NON-blocker overall. (`@types/node@^25.6.0` and `@playwright/test@^1.49.0` already exceed Next 16's minima.)

  Net assessment: of the six surfaces, two (1 = middleware rename, 2 = `useSearchParams` Suspense gating) are real source-file mutations that exceed bookkeeping scope. Combined with the next-intl peer block, three independent surfaces all argue for deferral.

- **Two real follow-up paths exist; neither fits this sub-plan's scope.** Either (a) sequence next-intl 4 first (close i-5 via Phase 40-03), THEN reopen i-6b in a fresh sub-plan that absorbs the Middleware->Proxy rename + Suspense boundary additions + lockfile-resolution probe with `next@^16.0.0` and `next-intl@^4.11.1` co-installed, OR (b) bundle Next 16 + next-intl 4 into a single multi-package atomic bump (which the roadmap's "in sequence (each its own commit and test pass)" line explicitly forbids — the executor would have no way to triage a CI red between the two majors). Path (a) is what the roadmap actually permits. This plan codifies path (a) as the i-6b re-open trigger.

- **Mirror the i-7/i-7b (Phase 39-01) and i-8/i-8b (Phase 40-01) playbooks.** Three precedents now exist for "issue named for a major-version jump that the v1.0 single-commit cadence cannot absorb": i-7 (testcontainers 1.x -> 2.x; deferred because the 2.x artifact does not exist), i-8 (Spring Boot 3.4 -> 4.0; deferred because Jackson 2 vs 3 default-classpath shift requires a 36-file refactor), and now i-6 (Next 15 -> 16; deferred because next-intl 3 peer-range blocks the install). The mirror is: (i) close i-6 with a closure note recording what was actually done (no runtime change; pin stays in `^15.1.0`; lockfile naturally captures `15.5.18` or current 15.x backport), (ii) create i-6b with the precise re-open trigger ("Phase 40-03 / i-5 next-intl 4 migration ships green; AT THAT POINT a fresh sub-plan may probe the Next 16 install with next-intl 4 + Suspense fixes + Middleware->Proxy rename in lockstep").

- **Preserve every existing surface unchanged.** No edits to `frontend/package.json`, `frontend/pnpm-lock.yaml`, `frontend/next.config.ts`, `frontend/eslint.config.mjs`, `frontend/src/middleware.ts`, `frontend/src/middleware.test.ts`, `frontend/src/app/layout.tsx`, `frontend/src/app/(auth)/login/page.tsx`, `frontend/src/app/(app)/session/[id]/page.tsx`, `frontend/src/app/(app)/exercises/[id]/page.tsx`, `frontend/src/components/web-vitals-reporter.tsx`, `frontend/src/components/web-vitals-reporter.test.tsx`, `frontend/src/app/api/{healthz,livez,metrics,vitals}/route.ts`, `frontend/src/lib/metrics/registry.ts`, `frontend/src/lib/metrics/route-label.ts`, the Dexie offline-queue module, the service-worker registrar, the `i18n/request.ts` next-intl plugin entry, or the `messages/{tr,en}.json` catalogues. The plan output is strictly `.planning/ISSUES.md` + `.planning/STATE.md` bookkeeping plus the new `40-02-PLAN.md` this file represents. **Zero protected-file runtime edits.** Constraint compliance: the orchestrator stub authorised `frontend/package.json` mutation as a fallback, but this plan's deferral path means the protected file is **not** touched at all — the orchestrator's "REQUIRED" label was conditional on the plan being a real bump, which the next-intl block disproves.

- **CI gate posture identical to v0.6.0.** The CI at HEAD is green. The bookkeeping commit changes zero runtime artifacts in `frontend/`, `backend/`, `compose.yml`, or `.github/workflows/**`. CI is expected to be green-identical. The local-host gates (`pnpm typecheck`, `pnpm lint`, `pnpm test`, `pnpm build`) are NOT exercised by this plan because no source mutation occurs; the executor MAY run them as a sanity check but failure on a no-op diff would indicate an infra issue, not a plan defect.

- **Single-bookkeeping-commit posture matches the roadmap.** The roadmap line says "in sequence (each its own commit and test pass)". 40-01 produced exactly one bookkeeping commit at 30b8d97. 40-02 (this plan) produces exactly one bookkeeping commit. 40-03 (next-intl 4) is the first real bump in Phase 40 and follows in its own commit. No mixing.

**Rejected alternatives:**

1. *Bump `next` to `^16.2.6` AND override the next-intl peer with `pnpm.overrides` to force-resolve* — rejected. `pnpm.overrides` would silence the peer warning but not the runtime incompatibility. next-intl 3.x's `createNextIntlPlugin` patches Next's Middleware/Proxy and `unstable_rootParams` plumbing in ways that 4.x removed and 16.x deprecated; running 3.x against 16.x would be a runtime gamble outside the v1.0 hardening contract.

Constraint compliance: the spawn prompt explicitly says "DO NOT modify CHANGELOG.md (release time only)".

## Out of Scope

- **Bumping `next` to `^16.x` or `^15.5.x`.** That is the closure of i-6b (or, for the patch bump, an upstream Renovate PR); this plan does NOT close i-6b. The whole point of this plan is to defer it. The `^15.1.0` caret already subsumes `15.5.18`.
- **Bumping `next-intl` to `^4.x`.** That is Phase 40-03's scope (i-5 closure). Out of scope here.
- **Renaming `frontend/src/middleware.ts` to `frontend/src/proxy.ts`.** That is i-6b's closure trigger step 2; out of scope here. Pre-applying the rename on Next 15 would either break Next 15 (which only knows `middleware.ts`) or introduce a parallel `proxy.ts` file Next 15 ignores.

- **Auditing `next/image` callers for query-string `src` values.** That is i-6b's closure trigger step 7; out of scope here.
- **Pre-applying the AMP / `images.domains` / `next/legacy/image` removals.** All three are deprecation surfaces in Next 16; Next 15 still supports them. Out of scope here.
- **Choosing Turbopack vs `--webpack` for the default bundler.** That is i-6b's closure trigger step 9; out of scope here.
