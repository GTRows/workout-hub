# Phase 40 - Plan 03: Bump next-intl from 3.26.x to 4.x (closes deferred issue i-5)

**Milestone:** v1.0 Release Hardening
**Phase:** 40 - framework-majors (Spring Boot 4 / Next 16 / next-intl 4 in sequence)
**Plan:** 40-03 (third sub-plan; closes deferred issue i-5 next-intl 3 -> 4 major bump). Predecessor 40-02 shipped at ea7d0d3 (Next 16 deferred to i-6b).
**Status:** Not started
**Author date:** 2026-05-09

## Goal

Bump `next-intl` from `^3.26.0` to `^4.11.1` in `frontend/package.json`, regenerate `frontend/pnpm-lock.yaml`, and migrate the few breaking-change surfaces the 4.0 release introduced. Close deferred issue **i-5** in `.planning/ISSUES.md` and update `.planning/STATE.md` accordingly. The runtime stays on Next 15 — next-intl 4.11.1 declares `peerDependencies.next: "^12.0.0 || ^13.0.0 || ^14.0.0 || ^15.0.0 || ^16.0.0"`, so the bump is forward-compatible AND back-compatible: it does NOT require Next 16 (which remains deferred under i-6b until a fresh sub-plan absorbs the Middleware-to-Proxy rename, the `useSearchParams` Suspense gating, and the lockfile-resolution probe).

The roadmap line for Phase 40 reads "i-8 Spring Boot 4, i-6 Next 16, i-5 next-intl 4 in sequence (each its own commit and test pass)". Phase 40-01 deferred i-8 -> i-8b. Phase 40-02 deferred i-6 -> i-6b. Phase 40-03 (this plan) is the first plan in Phase 40 that actually moves a runtime version pin. It is the prerequisite that unblocks the eventual i-6b closure (the Next 16 install requires next-intl 4 in the lockfile per the npm peer-range evidence captured in 40-02).

## Architecture Decision: bump `next-intl` from `^3.26.0` to `^4.11.1`; migrate the four codebase-affecting 4.0 breaking-change surfaces; preserve every existing `useTranslations`/`getTranslations`/`useLocale`/`useFormatter` call site verbatim; do not opt into the new strictly-typed ICU args or the augmented-types `AppConfig` registration

**Decision:** Edit `frontend/package.json` to set `next-intl: "^4.11.1"`. Run `pnpm install` to regenerate `frontend/pnpm-lock.yaml`. Migrate the four 4.0 breaking surfaces that this codebase actually touches (enumerated below). Do NOT migrate to the optional opt-in features (augmented `AppConfig` types, strictly-typed ICU args) — those are polish work and orthogonal to the major-version close.

**npm registry evidence (captured at plan author time, 2026-05-09):**

- `next-intl@latest` dist-tag: `4.11.1` (published 2026-05-07-ish per the registry timeline).
- `next-intl@4.11.1` peerDependencies: `{"next": "^12.0.0 || ^13.0.0 || ^14.0.0 || ^15.0.0 || ^16.0.0", "react": "^16.8.0 || ^17.0.0 || ^18.0.0 || >=19.0.0-rc <19.0.0 || ^19.0.0", "typescript": "^5.0.0"}`. Our `next: ^15.1.0`, `react: ^19.0.0`, `typescript: ^5.7.2` all satisfy.
- `next-intl@4.0.0-beta-00a79d4` (first 4.x preview, 2024-11-15) peerDependencies excluded `^16.0.0` from the next range, but the 4.x stable line picked up `^16.0.0` shortly after.
- The 4.0 GA migration guide is published at `https://next-intl.dev/blog/next-intl-4-0` (Mar 12, 2025; updated since).

**Codebase-affecting breaking changes from the next-intl 4.0 release notes:**

1. **Modernized build output: ESM-only (except `next-intl/plugin` which stays dual ESM+CJS).** Affects: `next.config.ts` imports `next-intl/plugin` (dual-mode; NON-blocker). All other imports in `frontend/src/**/*.{ts,tsx}` are ESM-style (`import { ... } from "next-intl"`); Vitest + Next.js both run ESM natively. NON-blocker.

2. **React peer bumped to `>=17` and modern JSX transform.** Codebase already runs React 19. NON-blocker.

3. **TypeScript minimum bumped to `5`.** Codebase declares `typescript: "^5.7.2"`. NON-blocker.

4. **`getRequestConfig` must return `locale`.** `frontend/src/i18n/request.ts` already returns `{ locale, messages }` (line 16 of the current file). NON-blocker (the test was preemptively-correct for the 3.22+ shape).

5. **`NextIntlClientProvider` now inherits `messages` and `formats` from `i18n/request.ts` automatically.** This is OPT-IN cleanup — passing them explicitly still works (the docs explicitly note the props remain valid; opting out requires `messages={null}` / `formats={null}`). The codebase has 27 call sites that explicitly pass `messages={...}`:
   - `frontend/src/components/providers.tsx` (the root provider, fed from `frontend/src/app/layout.tsx`'s `getMessages()` call): KEEP the explicit pass-through. The runtime path receives `messages` from a server-component await and threads them through to the client provider; auto-inheritance only works when the child provider is rendered under a server component that already called `getMessages()` (which is what happens here, but explicit is safer than implicit and avoids a behavioural change risk).
   - 25 test files (every `*.test.tsx` that wraps a client component in `<NextIntlClientProvider locale="en" messages={messages}>`): KEEP the explicit pass-through. Tests use synthetic mocked messages tailored to the assertion under test, NOT the real `frontend/messages/{tr,en}.json` catalogue. Auto-inheritance would not pick up the test-specific message subset (there is no server-component context in jsdom-based tests).

   Net assessment for surface 5: **no source mutation required**. The 27 call sites continue to work under 4.x because the props still take precedence over auto-inheritance. The optional cleanup is intentionally deferred (out of scope for closing i-5).

6. **GDPR + locale cookie + `defineRouting` + `domains` + `localePrefix` changes.** All N/A: the codebase does NOT use locale-based routing. `frontend/src/i18n/request.ts` resolves locale via `NEXT_PUBLIC_DEFAULT_LOCALE` env var (default `"tr"`); there is no `defineRouting` call, no `domains` config, no `localePrefix`, no `[locale]` segment in the App Router file tree, no `next-intl/middleware`, no `next-intl/navigation` re-exports of `Link`/`useRouter`/`usePathname` (the codebase imports those from `next/navigation` directly). NON-blocker.

7. **Stricter Next.js 15 client-provider boundary requirement (PR #1541).** Per the 4.0 release notes: "If you don't already have a `NextIntlClientProvider` in your app that wraps all Client Components that use next-intl, you now have to add one." Codebase audit: `frontend/src/components/providers.tsx` wraps every client component (it sits inside `frontend/src/app/layout.tsx`'s `<body>`, around `{children}`). All 47 `useTranslations` / `useLocale` / `useFormatter` call sites surfaced by Grep (in `(app)/*-client.tsx`, `(auth)/login/page.tsx`, `(app)/dashboard/page.tsx`, `components/{nav,bottom-nav,logout-button,install-prompt-card,push-permission-card,exercise-progress-chart,exercise-personal-record-card,errors/route-error,skeletons/route-skeleton,dashboard/{last-weight,weekly-summary}-card}.tsx`) render under that provider via the App Router root layout. NON-blocker.

8. **`format.relativeTime` in client components may need `now` arg explicit (PR #1536).** Codebase audit via Grep: zero call sites use `format.relativeTime` (the only relative-date helper is `frontend/src/lib/time/relative-date.ts`, which is a hand-rolled formatter that delegates to `Intl.RelativeTimeFormat` directly, NOT `useFormatter().relativeTime`). NON-blocker.

9. **Locale-based routing: `await requestLocale` (introduced in 3.22, now required).** Already done in `frontend/src/i18n/request.ts` line 14: `const locale = resolveLocale(await requestLocale);`. NON-blocker.

10. **Removed deprecated APIs (PR #1479, PR #1482).** The 3.x deprecated surfaces removed in 4.0 are documented in the 3.x deprecation warnings; the codebase does NOT call any of them (audit: Grep for `useNow`, `useTimeZone`, the deprecated `locale` argument to `getRequestConfig`, the deprecated `NextIntlClientProvider.locale` typing edge cases — zero matches). NON-blocker.

11. **`useMessages` and `getMessages` return type-safe messages (PR #1489).** Affects `frontend/src/app/layout.tsx` line 35: `const messages = await getMessages();`. Without `AppConfig.Messages` augmentation, the return type widens to `AbstractIntlMessages` (same as 3.x). NON-blocker for runtime; the types-only opt-in (registering `interface AppConfig { Messages: typeof en }` in a `global.d.ts`) is intentionally OUT OF SCOPE here.

12. **Disallow `null`/`undefined`/`boolean` as ICU argument (PR #1561).** Audit: no `t(...)` call site in the codebase passes `null`/`undefined`/`boolean` literals or values whose runtime type could resolve to those for ICU placeholders. Spot-checked the most argument-heavy translations (`session.targetSets`, `session.kg`, `dashboard.weeklyTotal`, `metrics.weightLossKg` etc.) — every placeholder receives a `number` or `string`. NON-blocker.

13. **Middleware matcher suggestion update (PR #1720).** N/A: codebase does NOT use `next-intl/middleware`. NON-blocker.

**Net codebase impact:** Zero source files under `frontend/src/**/*.{ts,tsx}` need editing for the 3.x -> 4.x bump to compile and pass tests. The single mutation is `frontend/package.json` (the version pin) plus the regenerated `frontend/pnpm-lock.yaml`. The 13-surface breaking-change audit is captured for the plan record so an executor can verify each surface independently.

**Why this is the right call here:**

- **next-intl 4.x peers `next ^15.0.0 || ^16.0.0`.** The bump is install-clean against the existing `next: ^15.1.0` pin (which resolves to the 15.5.x backport line). No co-bump of Next required, no `pnpm.overrides`, no `--strict-peer-dependencies=false`. This is the inverse of the next-intl 3.x peer block that drove the 40-02 deferral.
- **All 13 documented 4.0 breaking surfaces are NON-blockers for this codebase.** The 40-02 deferral commentary feared a "major API change; requires migration of `frontend/messages/*.json` and `i18n/request.ts`" — that fear was conservative. The actual migration surface is zero source-file edits because (a) `i18n/request.ts` already uses the post-3.22 `await requestLocale` shape, (b) the message JSON files are valid 4.x catalogues unchanged, (c) the codebase doesn't use locale-based routing, doesn't use `format.relativeTime`, doesn't use deprecated 3.x APIs, doesn't use `next-intl/middleware`, and doesn't use `next-intl/navigation`.
- **Closes a real open vuln-alert pair (#8 and #11) called out in the i-5 entry.** The i-5 ISSUES entry notes "Closes vuln alerts: #8 and #11 (open redirect, severity medium)". The bump closes them by upgrading past the affected 3.x line.
- **Unblocks i-6b (Next 16) closure.** Phase 40-02 documented that the Next 16 install requires next-intl 4 co-installed. After 40-03 ships green, the v1.0 milestone may optionally re-open i-6b; default is to leave i-6b open and let a future plan absorb it.
- **Single-runtime-bump-commit posture matches the roadmap's "in sequence (each its own commit and test pass)" rule.** Phase 40-01 was a deferral (one bookkeeping commit). Phase 40-02 was a deferral (one bookkeeping commit). Phase 40-03 (this plan) is one runtime bump (one commit) plus a deferred-issue-close commit if the executor chooses to split, OR one combined commit that bumps the version, regenerates the lockfile, and closes i-5 in `.planning/ISSUES.md` + `.planning/STATE.md`. Combined commit is preferred to keep CI bisect-blame coherent.
- **CI is the authoritative gate.** Local Maven gap is irrelevant (no backend touch). Local pnpm `typecheck` / `lint` / `test` / `build` ARE available on this Windows host per the i-6b commentary; the executor SHOULD run them as a sanity check before pushing. The `pnpm build` standalone-trace-copy EPERM noted historically is a known host-only issue and is not the gate; the compile-success criterion is the gate.

**Rejected alternatives:**

1. *Bump to `next-intl@^4.0.0` (the GA tag) instead of `^4.11.1` (the latest stable)* — rejected. The 4.0.x -> 4.11.x patch chain captured ~7 months of bug fixes (4.0 GA shipped 2025-03-12; 4.11.1 published 2026-05-07). Bumping to the GA tag would absorb the upgrade pain twice and miss security/stability fixes the 4.x line landed since GA. Pin to `^4.11.1` to capture the latest stable.
2. *Pin to `4.11.1` exactly (no caret)* — rejected. The codebase convention for non-protected runtime deps uses caret ranges (`^15.1.0`, `^19.0.0`, `^7.54.0`, etc.). Caret-pinning matches the existing posture and lets routine `pnpm install` pick up forward-compatible patch + minor releases.
3. *Migrate to the augmented-types `AppConfig` registration AND opt into strictly-typed ICU args in the same commit* — rejected. Both are OPTIONAL polish features per the 4.0 release notes. Bundling them with the runtime bump would inflate the diff, increase the bisect-blame surface, and risk shipping a type-check regression on top of a working runtime bump. Defer to a follow-up plan if the maintainer wants the typed-message DX win.
4. *Migrate the 25 test files to drop the explicit `messages={...}` prop and rely on auto-inheritance* — rejected. Tests render in jsdom without a real server-component context, so there is no `i18n/request.ts` ambient config to inherit from. The auto-inheritance optimisation only applies when the parent server component already executed `getMessages()`. Forcing the cleanup here would break every test.
5. *Drop the explicit `messages={...}` prop in `frontend/src/components/providers.tsx`* — rejected for v1.0 scope. The current shape (server-component layout calls `getMessages()`, threads through `Providers`, explicit prop pass) is correct under both 3.x and 4.x. Auto-inheritance MIGHT work here, but the explicit pass-through is self-documenting and avoids a runtime-context lookup that could surprise an executor probing under different rendering modes. Keep.
6. *Bundle the next-intl 4 bump with the eventual Next 16 bump* — rejected by the roadmap's "in sequence (each its own commit and test pass)" rule. A combined bump would prevent CI bisect-blame between Next 16 surfaces (Middleware->Proxy, Suspense gating, image config) and next-intl 4 surfaces (the 13 above) if CI goes red. The 40-02 deferral playbook explicitly preserved this separation.
7. *Add `pnpm.overrides` to silence theoretical peer warnings* — rejected. There are no peer warnings to silence; next-intl 4.11.1 peers `next ^15.0.0 || ^16.0.0`, the codebase has `next ^15.1.0`, the install is clean.
8. *Edit `frontend/eslint.config.mjs` to add a no-deprecated-api rule for next-intl 3 imports* — rejected. The bump removes the deprecated APIs; the import would fail at compile time, not lint time. The lint config already runs `eslint-config-next`'s strict rules; adding a custom rule for a one-time migration is overkill.
9. *Update CHANGELOG.md to record the next-intl 4 bump* — rejected. CHANGELOG rotation is Phase 44 release scope. Constraint compliance: spawn prompt explicitly says "DO NOT modify CHANGELOG.md (release time only)".
10. *Update `.github/workflows/**` to add a probe job that runs `pnpm install --strict-peer-dependencies` against multiple Next versions* — rejected. Spawn prompt says "DO NOT modify .github/workflows". Existing CI matrix is sufficient.
11. *Stay on `^3.26.0` and close i-5 by re-deferring to i-5b (mirror i-6/i-6b, i-7/i-7b, i-8/i-8b)* — rejected. The 40-02 deferral was justified by a hard install block (next-intl 3.x peers cap at `next ^15.0.0`, blocks Next 16). The 40-03 case has no install block (next-intl 4.11.1 peers `^15.0.0 || ^16.0.0`, install is clean) and no migration-blocker (audit found zero source-file edits required). Deferring would be dishonest planning. Bump it.
12. *Pre-emptively migrate `frontend/src/lib/time/relative-date.ts` to `useFormatter().relativeTime`* — rejected. The hand-rolled `Intl.RelativeTimeFormat` formatter was a Phase 25/27 lock-in choice for offline-friendly relative-date rendering. Replacing it with `useFormatter().relativeTime` would introduce the new `now` arg requirement (PR #1536) and add a re-render-on-`now`-change concern. Out of scope; orthogonal to the major-version close.
13. *Add `Locale` strict typing via `declare module "next-intl" { interface AppConfig { Locale: ... } }`* — rejected for v1.0. The codebase uses `string`-typed locale throughout; the 4.0 release notes explicitly call this out as OPTIONAL ("Note that strictly-typing the Locale is optional and can be used as desired"). Defer to follow-up polish.
14. *Run `pnpm dedupe` after `pnpm install`* — rejected. The codebase doesn't run `pnpm dedupe` as a standard hygiene step; pnpm's content-addressable store already deduplicates effectively. Adding a `dedupe` invocation would be an unjustified deviation from the existing tooling posture.
15. *Use `pnpm up next-intl@4` instead of editing `package.json` then running `pnpm install`* — acceptable substitute, NOT rejected. The two paths produce equivalent lockfile output. Plan documents the explicit edit-then-install path because (a) it is auditable in Git diff, (b) it makes the protected-file mutation visible to the pre-edit hook, (c) `pnpm up` requires the same protected-file authorisation. Either path satisfies Task 1.
16. *Bump `next-intl` to `4.11.1` exactly (no caret) AND pin to a SHA-pinned npm-registry-mirror URL* — rejected. The repo doesn't pin via SHA-mirror; routine pnpm-install posture is the correct shape.
