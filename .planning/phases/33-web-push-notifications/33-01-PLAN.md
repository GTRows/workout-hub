<objective>
Phase 33 (web-push-notifications) per the v0.6 ROADMAP entry targets "workout/weight/supplement reminders wired to existing backend push package." Reconnaissance at plan time shows the backend reminder pipeline is FULLY built end-to-end and the frontend subscription UX exists, but three concrete gaps prevent a single push notification from ever reaching a user. This sub-plan closes all three in one coherent change.

**What already exists (do NOT rebuild):**

- `backend/src/main/java/com/workouthub/notifications/NotificationDispatcher.java` — interface `void send(UUID userId, String title, String body, String clickUrl)`.
- `backend/src/main/java/com/workouthub/notifications/LoggingNotificationDispatcher.java` — fallback bean: logs the would-be notification when VAPID keys are not configured.
- `backend/src/main/java/com/workouthub/notifications/WebPushNotificationDispatcher.java` — `@Primary @ConditionalOnProperty("app.push.vapid.private-key")`; fans payloads to every `PushSubscription` for the user, prunes `GONE` subs, retries `TRANSIENT_FAILURE` on next trigger.
- `backend/src/main/java/com/workouthub/notifications/WebPushSender.java` — interface with `Outcome { OK, GONE, TRANSIENT_FAILURE }`.
- `backend/src/main/java/com/workouthub/notifications/WebPushJavaSender.java` — `nl.martijndwars:web-push 5.1.2` implementation; gated by `app.push.vapid.private-key`.
- `backend/src/main/java/com/workouthub/notifications/ReminderJob.java` — `@Component` with three `@Scheduled` triggers reading `app.reminders.workout-cron`, `weight-cron`, `supplement-cron`. Each builds the `(userId, title, body, clickUrl)` tuple and calls `dispatcher.send`. Public `runWorkoutDayRemindersAt(LocalDate)`, `runWeightNudgeAt(LocalDate)`, `runSupplementRemindersAt(LocalTime)` methods are unit-test entry points already covered by `ReminderJobIntegrationTest` (5 it-blocks against real Postgres + a `@MockitoBean NotificationDispatcher`).
- `backend/src/main/java/com/workouthub/WorkoutHubApplication.java` carries `@EnableScheduling` (cron triggers fire when configured).
- `backend/pom.xml` declares `nl.martijndwars:web-push 5.1.2` plus the runtime overrides; nothing to add.
- `backend/src/main/resources/application.yml` has the VAPID config block (`app.push.vapid.{public-key,private-key,subject}`) and the cron block (`app.reminders.{workout,weight,supplement}-cron`), all env-driven.
- `backend/src/main/resources/db/migration/V10__push_subscriptions.sql` — table exists since v0.2.
- `backend/src/main/resources/db/migration/V11__supplement_reminder_time.sql` — `supplements.reminder_time TIME` column already powers `runSupplementRemindersAt`.
- `backend/src/main/java/com/workouthub/push/{PushController,PushService,VapidConfig}.java` plus `domain/PushSubscription{,Repository}.java` and `dto/{SubscribeRequest,SubscriptionDto}.java` — `/api/push/{vapid-public-key,subscribe (POST),subscribe (DELETE)}` endpoints work today and are integration-tested by `PushIntegrationTest` (6 it-blocks).
- `frontend/src/lib/push/subscribe.ts` — `subscribePush()` fetches VAPID, calls `pushManager.subscribe`, POSTs `{endpoint, keys, userAgent}` to `/api/push/subscribe`. Used by `push-permission-card.tsx`.
- `frontend/src/components/push-permission-card.tsx` — dashboard card that triggers `Notification.requestPermission()` then `subscribePush()` on Allow. Mounted on `(app)/dashboard/page.tsx` (line 24, line 93/129/145/163 — once per render branch). Test coverage at `push-permission-card.test.tsx` (4 it-blocks: default, granted, denied, unsupported).
- `frontend/src/components/service-worker-registrar.tsx` — registers `/sw.js` with explicit `scope: "/"` (Phase 32). Test at `service-worker-registrar.test.tsx`.
- `frontend/public/sw.js` — minimal SW: install / activate / fetch handlers, `wh-shell-v2` cache, `/api/` bypass, `/offline` fallback. **NO `push` event handler. NO `notificationclick` event handler.** This is the single largest gap.
- `frontend/src/lib/api/schemas.ts` carries `pushSubscribeRequestSchema` and `vapidPublicKeyResponseSchema` (Phase 25.5 zod parity).

**The three gaps this sub-plan closes:**

1. **Service-worker `push` + `notificationclick` handlers are missing.** When the backend sends a Web Push payload (signed via VAPID, body = `{"title","body","url"}` per `WebPushNotificationDispatcher.buildPayload`), the browser delivers a `push` event to the registered SW. Without a handler the platform drops the message — even if the user granted permission and the subscription is stored. The fix adds two handlers to `frontend/public/sw.js`:
   - `self.addEventListener("push", ...)` — parses `event.data.json()` (with a `try/catch` text fallback for missing payloads, which Chrome sometimes sends as keep-alive); calls `self.registration.showNotification(title, { body, icon: "/icons/icon-192.png", badge: "/icons/icon-192.png", data: { url }, tag: "wh-reminder" })` to coalesce duplicates of the same reminder window.
   - `self.addEventListener("notificationclick", ...)` — `event.notification.close()`; if a client window with the same origin is already open, focus it and `postMessage` / navigate to `data.url`; otherwise open a new window at `data.url` (default `/dashboard`). This mirrors the standard PWA pattern.
   - Bumps the cache constant from `wh-shell-v2` to `wh-shell-v3` so the new SW activates cleanly on first deploy after this lands; the activate handler already drops stale caches.

2. **No way for the user to disable push or see/manage their subscriptions.** Current state: `PushPermissionCard` shows on dashboard while `Notification.permission === "default"`, calls `subscribePush()` on Allow, then disappears forever once granted. There is no opt-out — the user must dig into browser settings to revoke. The fix adds a `NotificationsSection` component in the existing profile page that:
   - Reads `Notification.permission` and the current `PushSubscription` via `navigator.serviceWorker.ready.then(reg => reg.pushManager.getSubscription())` on mount.
   - When `permission === "granted"` and a subscription exists: shows status "Active on this device" plus a Disable button. Disable calls `subscription.unsubscribe()` (browser-side) AND `DELETE /api/push/subscribe?endpoint=...` (server-side; existing endpoint).
   - When `permission === "default"`: shows an Enable button that calls the existing `subscribePush()` helper (DRY with `PushPermissionCard`).
   - When `permission === "denied"`: shows a help message (cannot programmatically re-prompt; user must clear browser site data).
   - On a server-side test event button (admin-only? no — per-user is fine): calls a new `POST /api/push/test` endpoint that fans out a single static `("Test reminder", "If you can read this, push works.", "/profile")` notification to the caller's own subscriptions only. This is the closed-loop self-test the operator needs after configuring VAPID. Plan-locked: the test endpoint is gated to the authenticated user's OWN subscriptions only (no privilege escalation surface).

3. **Operators have no visible config story for enabling reminders.** `application.yml` defaults `app.reminders.{workout,weight,supplement}-cron` to a single dash `-` which Spring's `CronTrigger` rejects, so the `@Scheduled` triggers silently never fire (Spring's `Scheduled` annotation tolerates `-` as a "disabled" sentinel). VAPID keys are also missing from `.env.example`. The fix:
   - Adds an `# Reminders / Web Push` block to `.env.example` documenting `APP_PUSH_VAPID_PUBLIC_KEY`, `APP_PUSH_VAPID_PRIVATE_KEY`, `APP_PUSH_VAPID_SUBJECT` plus the three `APP_REMINDERS_*_CRON` knobs with sensible commented defaults (e.g. `0 0 7 * * *` for weight nudge at 07:00 daily; `0 0 8 * * *` for workout-day reminder at 08:00 daily; `0 * * * * *` for supplement minute-resolution check).
   - Adds a short `Web Push & Reminders` section to `docs/DEPLOYMENT.md` with the VAPID-key generation command (`./mvnw -q -pl backend exec:java` is overkill; use `npx web-push generate-vapid-keys` via Node — Node 22 is already a build-time dep) and the three cron envs, plus the `app.push.vapid.subject` mailto contract.
   - **Does NOT change `application.yml` defaults.** The dash sentinel is intentional (Spring treats `-` as "skip this trigger") and matches the existing convention; we document the live cron expressions instead.

**This is the only sub-plan for Phase 33.** The four-line roadmap entry maps cleanly to the three gaps above; the backend logic is already test-covered (5 it-blocks in `ReminderJobIntegrationTest` + 3 in `WebPushNotificationDispatcherTest` + 6 in `PushIntegrationTest`). After 33-01 ships and CI is green: Phase 33 closes; ROADMAP advances to Phase 34 (rest-timer-notifications), which builds on the SW `push`/`notificationclick` handlers shipped here.

If during execution the SW push handler or the `/api/push/test` endpoint expands beyond the bounded scope (e.g. needing payload schema versioning, retry queueing, or per-device opt-out granularity beyond the existing `PushSubscription` row), the executor calls a halt and the orchestrator schedules a 33-02 follow-up. The plan-locked scope here is: SW push + click handlers, profile-page notifications section, self-test endpoint, env doc.
</objective>

```js
self.addEventListener("push", (event) => {
  let payload = { title: "WorkoutHub", body: "", url: "/dashboard" };
  if (event.data) {
    try {
      payload = { ...payload, ...event.data.json() };
    } catch (_err) {
      payload.body = event.data.text();
    }
  }
  const opts = {
    body: payload.body,
    icon: "/icons/icon-192.png",
    badge: "/icons/icon-192.png",
    data: { url: payload.url || "/dashboard" },
    tag: "wh-reminder",
    renotify: false,
  };
  event.waitUntil(self.registration.showNotification(payload.title, opts));
});

self.addEventListener("notificationclick", (event) => {
  event.notification.close();
  const target = (event.notification.data && event.notification.data.url) || "/dashboard";
  event.waitUntil(
    self.clients.matchAll({ type: "window", includeUncontrolled: true }).then((all) => {
      for (const c of all) {
```

```tsx
type Status = "unsupported" | "default" | "granted" | "denied";

function readStatus(): Status {
  if (typeof window === "undefined") return "unsupported";
  if (typeof window.Notification === "undefined") return "unsupported";
  if (!("serviceWorker" in navigator)) return "unsupported";
  return Notification.permission as Status;
}

export function NotificationsSection() {
  const t = useTranslations("profile.notifications");
  const tTest = useTranslations("push.test");
  const [status, setStatus] = useState<Status>("unsupported");
  const [subscribed, setSubscribed] = useState<boolean>(false);
  const [busy, setBusy] = useState<boolean>(false);

  useEffect(() => {
    const initial = readStatus();
    setStatus(initial);
    if (initial !== "granted") return;
    let cancelled = false;
    navigator.serviceWorker.ready
      .then((reg) => reg.pushManager.getSubscription())
      .then((sub) => {
        if (!cancelled) setSubscribed(sub !== null);
      })
      .catch(() => {
        /* no-op; the section just shows the un-subscribed state */
      });
    return () => {
      cancelled = true;
    };
  }, []);

  const onEnable = async () => {
    setBusy(true);
    try {
      const res = await Notification.requestPermission();
      if (res !== "granted") {
        setStatus(res as Status);
        return;
      }
      await subscribePush();
      setSubscribed(true);
      setStatus("granted");
    } finally {
      setBusy(false);
    }
  };

  const onDisable = async () => {
    setBusy(true);
    try {
      const reg = await navigator.serviceWorker.ready;
      const sub = await reg.pushManager.getSubscription();
      if (!sub) {
        setSubscribed(false);
        return;
      }
      const endpoint = sub.endpoint;
      await sub.unsubscribe();
      await api.request({
        method: "DELETE",
        path: `/api/push/subscribe?endpoint=${encodeURIComponent(endpoint)}`,
      });
      setSubscribed(false);
    } finally {
      setBusy(false);
    }
  };

  const onTest = async () => {
    setBusy(true);
    try {
      const r = await api.request<{ delivered: number; subscriptions: number }>({
        method: "POST",
        path: "/api/push/test",
      });
      if (r.subscriptions === 0) {
        toast.message(tTest("zero"));
      } else {
        toast.success(tTest("success", { count: r.delivered }));
      }
    } catch (_err) {
      toast.error(tTest("error"));
    } finally {
      setBusy(false);
    }
  };

  const statusKey =
    status === "granted"
      ? "statusGranted"
      : status === "default"
      ? "statusDefault"
      : status === "denied"
      ? "statusDenied"
      : "statusUnsupported";

  return (
    <Card data-testid="notifications-section">
      <CardHeader>
        <CardTitle>{t("title")}</CardTitle>
        <CardDescription>{t("description")}</CardDescription>
      </CardHeader>
      <CardContent className="space-y-3">
        <p className="text-sm text-muted-foreground" data-testid="notifications-status">
          {t(statusKey)}
        </p>

        {status === "default" && (
          <Button onClick={onEnable} disabled={busy} size="sm">
            {t("title")}
          </Button>
        )}

        {status === "granted" && subscribed && (
          <div className="flex flex-wrap gap-2">
            <Button variant="outline" onClick={onDisable} disabled={busy} size="sm">
              {t("disable")}
            </Button>
            <Button variant="secondary" onClick={onTest} disabled={busy} size="sm">
              {t("testButton")}
            </Button>
          </div>
        )}

        {status === "granted" && !subscribed && (
          <Button onClick={onEnable} disabled={busy} size="sm">
            {t("title")}
          </Button>
        )}
      </CardContent>
    </Card>
  );
}
```
