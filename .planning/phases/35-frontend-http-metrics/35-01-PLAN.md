# Phase 35 - Plan 01: Frontend HTTP Metrics (i-4)

**Milestone:** v0.6 Operational Maturity
**Phase:** 35 - frontend-http-metrics
**Plan:** 35-01 (sole sub-plan)
**Status:** Not started
**Author date:** 2026-05-09

## Goal

Close deferred issue **i-4** (`.planning/ISSUES.md`): the Next.js frontend's `/api/metrics`
endpoint currently exposes only Node process gauges (uptime, RSS, heap). The Self-Hosted
Contract section 9.1 also requires "HTTP request count and duration histogram". This plan
adds in-process counters and a duration histogram, instrumented from a Next middleware,
and renders them alongside the existing process gauges in Prometheus 0.0.4 text format on
the same `/api/metrics` route. No new runtime dependency is introduced; the histogram and
counter are hand-rolled (single Node.js process, single binding, no scrape contention).

## Architecture Decision: hand-rolled in-memory registry, no prom-client

**Decision:** **Do not add `prom-client`** (or any new metrics dep). The existing
`/api/metrics` route already proves Prometheus 0.0.4 text format can be hand-emitted in
~30 lines. Phase 35 extends that hand-rolled approach with:

1. A tiny module-scoped registry (`frontend/src/lib/metrics/registry.ts`) holding two
   data structures:
   - **Counter** keyed by `(method, route, status_class)` -> integer.
   - **Histogram** keyed by `(method, route)` -> array of bucket counters + `sum` + `count`.
2. A Next.js middleware hook in `frontend/src/middleware.ts` that records start time, and
   after `NextResponse.next()` returns the response, samples `Date.now() - start`, then
   calls `record(method, route, status, durationMs)` on the registry.
3. Updates to `frontend/src/app/api/metrics/route.ts` to render the registry into the
   same Prometheus text payload following the existing process-gauge style.

**Rejected alternatives:**

1. *Add `prom-client`* - rejected. The user-supplied constraints explicitly forbid it
   without orchestrator approval, and `package.json` is on the protected-files list. The
   existing route already shows the team prefers hand-rolled emission for a small fixed
   metric set.
2. *OpenTelemetry SDK / `@opentelemetry/sdk-metrics`* - rejected. Same package.json
   protection plus far more surface area than this phase needs. We have no OTLP collector
   in the contract.
3. *Re-implement metrics on the backend side and proxy* - rejected. The backend already
   has Spring Boot Actuator; proxying does not solve the i-4 ask, which is specifically
   about the **frontend** Next.js process having no per-request instrumentation.
4. *Streaming spans / per-request structured log only (no aggregation)* - rejected. The
   contract calls out a histogram + counter, not raw events.

**Why hand-rolled is the right call here:**
- Self-Hosted Contract pins to single-instance deploys (no horizontal scale on the FE
  process), so a process-local Map is correct: when the operator restarts the container,
  counters reset to zero - that is the standard Prometheus contract for non-restorable
  counters and is acceptable per section 9.1 (`process_*` gauges already behave this way).
- Next.js standalone (`output: "standalone"` is the project mode per `frontend/Dockerfile`)
  runs the App Router on a single Node.js process, and the middleware-runtime constraints
  matter: see the **Runtime model** section below.
- The total wire format is ~10 metric lines plus per-bucket histogram lines. No registry
  abstraction is justified.

## Runtime model (load-bearing - read carefully)

Next.js 15 middleware runs on the **Edge runtime** by default. The Edge runtime has:

- A separate JavaScript realm from Node.js route handlers, so a module imported from
  middleware does **not** share global state with a module imported from
  `app/api/metrics/route.ts`.

This is a real constraint. Two ways to handle it; the plan picks (B):

- **(A) Force middleware to nodejs runtime.** Next 15 supports
  `export const config = { runtime: "nodejs" }` for middleware (stable in 15.x). With
  this, the middleware module shares the Node `globalThis` with the route handler, and a
  module-scoped Map at `frontend/src/lib/metrics/registry.ts` is the same Map for both.
  Clean, simple, no IPC.
- **(B) Same as (A), but fall back to a `globalThis.__wh_metrics` shim** so that even if
  Next swaps middleware back to Edge in a future minor, the route handler still reads
  what the middleware wrote (within the same V8 isolate; if isolates diverge the histogram
  silently empties - acceptable degradation).

**Plan picks (A) with the (B) shim as belt-and-braces.** The executor sets
`runtime: "nodejs"` on the middleware export and mounts the registry on `globalThis`
via a single getter (`getRegistry()`) that lazily initialises the singleton. If the
runtime cannot be flipped because of a Next.js constraint we did not foresee, fall back
to recording metrics inside the App Router request lifecycle via an Edge-safe alternative
- but document the gap and stop; do not silently degrade to "no metrics".

- Updated `frontend/src/middleware.test.ts` (or new sibling test if the middleware test
  file gates only the redirect logic from Phase 29.5) - covers that middleware records a
  metric for both protected and metric-eligible paths.

**Out of scope:**
- New runtime dependencies (notably `prom-client`). If during execution the team decides
  hand-rolling is too brittle, the executor must surface that as a status:blocked - **do
  not** silently `pnpm add prom-client`.
- Backend metrics (already covered by Spring Boot Actuator).

  explicitly says "Restrict by interface binding, not by application auth"; the existing

- Backend `mvn` unavailable on this Windows host. This phase is frontend-only;

- Per CLAUDE.md: "Do not add error handling for scenarios that cannot happen." The

## Tasks (atomic, ordered)

### T1 - Metric registry module

**Files:**
- New: `frontend/src/lib/metrics/registry.ts`
- New: `frontend/src/lib/metrics/registry.test.ts`

**API surface:**
```ts
export type StatusClass = "1xx" | "2xx" | "3xx" | "4xx" | "5xx";

export interface MetricsRegistry {
  record(method: string, route: string, status: number, durationMs: number): void;
  renderProm(): string; // Prometheus 0.0.4 text exposition format
  reset(): void;        // for tests only
}

export function getRegistry(): MetricsRegistry;
```

**Internal data shapes:**
- `counters: Map<string, number>` keyed by `${method}|${route}|${statusClass}`.
- `histograms: Map<string, { buckets: number[]; sum: number; count: number }>` keyed by
  `${method}|${route}`. Buckets are the standard Prometheus default bounds (in seconds):
  `[0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10]`. Plus `+Inf` (logical, not
  stored - emitted as `count`).
- `getRegistry()` lazily attaches the registry to
  `(globalThis as { __wh_metrics?: MetricsRegistry }).__wh_metrics` so middleware and
  route handler see the same object even if Next swaps runtime adapters.

**Renderer rules:**
- All metric names prefixed `wh_frontend_http_*`.
- For each `(method, route, status_class)` counter, emit one `_total` line.
- For each `(method, route)` histogram, emit `_bucket` lines (ordered by `le`), then
  `_sum`, then `_count`.
- Always emit a `# HELP` and `# TYPE` line per metric family, even when there are zero
  samples (so a fresh process still produces a valid scrape with the family declarations).

**Verification (registry.test.ts):**
- Recording a 200 GET `/api/healthz` at 12ms increments
  `wh_frontend_http_requests_total{method="GET",route="/api/healthz",status_class="2xx"}` to 1.
- Recording two requests at 12ms + 600ms produces histogram `_count = 2`, `_sum ~ 0.612`,
  with the 12ms request landing in the `0.025` bucket and the 600ms request in `1`.
- `renderProm()` output matches a regex anchored snapshot for the `# HELP`/`# TYPE` block
  shape (do not snapshot the whole text - only the family declarations).
- `reset()` zeroes both maps but leaves the singleton mounted on `globalThis`.

### T2 - Route-label normaliser

**Files:**
- New: `frontend/src/lib/metrics/route-label.ts`
- New: `frontend/src/lib/metrics/route-label.test.ts`

**Behaviour:**
- Input: `pathname` from `NextRequest.nextUrl`.
- Output: low-cardinality label.
- Rules (in order):
  1. Exact match on `/api/healthz`, `/api/livez`, `/api/metrics` -> return as-is.
  2. Match `/session/<id>` -> `/session/[id]` (any non-slash chars after the segment).
  3. Match `/exercises/<id>` -> `/exercises/[id]`.
  4. Match `/plan/<weekId>` -> `/plan/[weekId]` (only when the segment is non-empty and
     not a known sub-route like `editor`).
  5. Match `/history/<id>` -> `/history/[id]`.
  6. Match `/insights/<id>` / `/prs/<id>` / `/achievements/<id>` / `/nutrition/<id>` ->
     same pattern.
  7. Anything else -> the pathname truncated at the second slash if it has 3+ segments
     (e.g. `/foo/bar/baz` -> `/foo/bar/_other`), or as-is if 1-2 segments.

**Verification:** unit-test each rule, plus the `_other` collapse for unknown deep paths.
The normaliser must never return raw user-controlled IDs in the label set, to keep
Prometheus cardinality bounded.

### T3 - Middleware instrumentation

**Files:**
- Modified: `frontend/src/middleware.ts`
- Modified (or new sibling): `frontend/src/middleware.test.ts`

**Changes to `middleware.ts`:**
- Add `export const config = { runtime: "nodejs", matcher: [...] }` - keep all current
  protected matchers, **and** add the four operator paths (`/api/healthz`, `/api/livez`,
  `/api/metrics`, plus a generic `/api/:path*`) so middleware also fires for them. This
  is required because Phase 29.5 narrowed the matcher to 12 (app)-group entries; we
  re-broaden it deliberately for instrumentation purposes.

  **Validate during execution** that broadening the matcher does not regress the
  Phase 29.5 protected-route scaffold (the test should still pass). The auth gate logic
  inside `middleware()` already early-returns when `pathname` is not in
  `PROTECTED_PREFIXES`; broadening the compile-time matcher does not change behaviour.

- Inside `middleware()`:
  ```ts
  const start = Date.now();
  const res = guardOrPassThrough(req); // existing logic refactored into a helper
  const duration = Date.now() - start;
  if (req.nextUrl.pathname !== "/api/metrics") { // exclude scrape itself
    getRegistry().record(req.method, normalizeRoute(req.nextUrl.pathname),
                         /* status */ inferStatusFromResponse(res),
                         duration);
  }
  return res;
  ```
  Note: `NextResponse.redirect(...)` carries `status === 307`; `NextResponse.next()` is
  status `200` with the `x-middleware-next` header. Use a small helper to read the
  status the response represents (defaults to 200 when absent), as full upstream status
  resolution would require chaining into the route handler, which middleware cannot
  observe synchronously.

  **Status fidelity caveat (acceptable):** the recorded `status` is the **middleware
  outcome**, not the eventual route-handler outcome. This is the standard limitation of
  Next.js middleware-only instrumentation and is the cost of avoiding a runtime dep. The
  histogram is still useful: it captures auth-redirect latency vs. pass-through latency.
  The `wh_frontend_http_requests_total` counter exhaustively covers traffic - it just
  classifies a `5xx` route handler as `2xx` when middleware passed through. Document
  this in the metrics route's `# HELP` text so an operator is not surprised.

**Verification (middleware.test.ts):**
- A mock `NextRequest` for `/api/healthz` flows through middleware, returns
  `NextResponse.next()`-equivalent, and the registry records exactly one entry for
  `(GET, /api/healthz, 2xx)`.
- A mock `NextRequest` for `/dashboard` without the session cookie returns a redirect
  and the registry records `(GET, /dashboard, 3xx)`.
- A mock `NextRequest` for `/api/metrics` does NOT increment the registry (scrape
  exclusion).
- The Phase 29.5 redirect test (if present in the same file) still passes.

## Risks and Mitigations

- **Risk: Next.js 15 middleware does not accept `runtime: "nodejs"` in this repo's
  pinned minor.** *Mitigation:* check `next` version in `frontend/package.json` first.
  If `runtime: "nodejs"` is unsupported, fall back to: keep middleware on Edge but mount
  the registry on `globalThis` and accept that on cold starts where Next puts middleware
  in a separate isolate, the histogram is empty until a request hits a route handler
  that imports the registry directly. In that fallback, also add a "shadow recorder" in
  a Next.js instrumentation hook (`frontend/src/instrumentation.ts`) that wraps the
  request lifecycle. This is a documented escape hatch; the executor should pause and
  flag if they hit it.
- **Risk: cardinality blow-up.** *Mitigation:* `route-label.ts` is the single allow-list
  for label values. Any unknown deep path collapses to `_other`. Tests assert this.
- **Risk: middleware status is the **middleware** outcome, not the upstream handler
  outcome.** *Mitigation:* documented in `# HELP` text. Acceptable per the rationale in
  T3 and consistent with the contract's emphasis on coarse-grained operator visibility.
- **Risk: middleware adds latency to every request.** *Mitigation:* the registry's
  `record()` is two Map lookups + a numeric increment + a binary search through 11
  bucket bounds. Sub-microsecond on Node 22. Test that the registry's `record()` is
  side-effect-free except for its own state (no logging, no I/O).
- **Risk: in-memory state lost on restart.** *Accepted.* The contract is pull-based and
  Prometheus expects counter resets on process restart; the scrape's `process_start_time`
  gauge already conveys the restart point.
- **Risk: protected-files trip.** *Mitigation:* the plan does NOT touch
  `frontend/package.json`, `pnpm-lock.yaml`, `Dockerfile`, or `compose.yml`. If the
  executor finds a need to touch any of these, **stop** and surface as blocked.

## Out-of-band notes for the executor

- Use `import type` for any types crossing the middleware/route boundary. Edge and Node
  runtime adapters elide `import type` cleanly in both worlds.
- `getRegistry()` must be the only public way to access state; do **not** export the
  underlying Maps. This protects against accidental mutation from tests.
- Keep histogram bucket bounds in a single `const HISTOGRAM_BUCKETS_SECONDS` array; both
  the recorder and the renderer read from it. A change must be a single-line edit.
- Use `as const` on the bucket array so TypeScript narrows it to a readonly tuple.
- Commit-message convention for this phase: `feat(metrics-fe): add request count and
  duration histogram (phase 35; closes i-4)` for the main commit. If split, use scopes
  `feat(metrics-fe)` for code, `test(metrics-fe)` for test-only commits, and
  `docs(metrics-fe)` for the changelog/issues annotation.
- Per CLAUDE.md, do **not** add docstrings or comments to code that did not previously
  carry them; do add a short header to the new files explaining the no-deps,
  process-local design and the runtime caveat.
- If `pnpm build` fails because Next 15 in this repo does not accept
  `runtime: "nodejs"` on middleware, **stop** and reach for the instrumentation-hook
  fallback in Risks - do not silently degrade to no metrics.
