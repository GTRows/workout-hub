# Phase 36 - Plan 01: Loading Skeletons (Next.js `loading.tsx` per (app) route)

**Milestone:** v0.6 Operational Maturity
**Phase:** 36 - error-states-perf-budgets
**Plan:** 36-01 (first of three; sub-plans 36-02 error-boundaries and 36-03 perf-budgets are scoped at the bottom of this file but not executed by this plan)
**Status:** Not started
**Author date:** 2026-05-09

## Goal

Eliminate the raw "blank-during-fetch" experience that affects every authenticated route in the
(app) group. Today the layout renders the nav + bottom-nav shell instantly, but the inner client
component returns an unstyled `<p className="text-muted-foreground">{t("loading")}</p>` paragraph
once data starts streaming. There is **zero** structural skeleton coverage in `frontend/src/`
(`Grep -r Skeleton` returned no matches; no `loading.tsx` file exists anywhere under
`frontend/src/app/`). This sub-plan introduces:

1. A small reusable shadcn-style `Skeleton` primitive (CSS-only; no new runtime dependency).
2. A `loading.tsx` Next.js segment file per (app) surface that renders a route-shaped skeleton
   while the inner Server Component (or its first Client child's first paint) is preparing.
3. A discrete `<RouteSkeleton variant="..." />` component family (one variant per route shape:
   `dashboard`, `plan`, `session`, `history`, `exercises`, `metrics`, `profile`, `insights`,
   `prs`, `achievements`, `nutrition`, `export`, `exercise-detail`).
4. Replace the existing inline `<p>{t("loading")}</p>` text in client components with the
   matching `<RouteSkeleton variant="..." />` so the in-flight TanStack Query refetch path
   (post-mount) shows the same shape as the initial Next.js segment-loading path.

The result: every (app) surface paints a stable, route-shaped skeleton from the moment the
route segment begins streaming until the data is hydrated, with no visible "loading…" text and
no layout shift.

## Architecture Decision: pure CSS skeleton, no `react-content-loader`, no SVG generators

**Decision:** Hand-roll a `<Skeleton />` primitive at `frontend/src/components/ui/skeleton.tsx`
that is a single `<div>` with Tailwind utility classes (`animate-pulse rounded-md bg-muted`)
plus optional sizing props. All route-shaped skeletons are declarative compositions of that
primitive — no runtime SVG rendering, no third-party content-loader, no animation library.

**Rejected alternatives:**

1. *Add `react-content-loader`* — rejected. `frontend/package.json` is on the protected-files
   list; we cannot add a dependency. Furthermore it pulls in SVG-based rendering which gives a
   different visual texture than the existing shadcn primitives (button, input, card all use
   pulse-fill rectangles).
2. *Render skeletons inline (no `loading.tsx`)* — rejected. Next.js `loading.tsx` is the
   correct seam for "the route segment is preparing"; using it gives free Suspense integration
   and a smooth transition from segment loading to client mounted (the framework swaps the
   subtree atomically).
3. *Reuse the existing `<Card />` + spinner* — rejected. There is no spinner primitive in
   the codebase today, and the `t("loading")` text is what we are removing. Adding a spinner
   would introduce a different motion vocabulary than the rest of v0.5 ships with.
4. *One generic `<RouteSkeleton />` with a `variant` enum string* — partially adopted. The
   plan ships one `<RouteSkeleton />` component file but the `variant` is a discriminated
   union driving render branches in the same module so TypeScript narrows per variant. No
   runtime cost beyond a single switch statement; tests can target individual variants
   without separate components proliferating.
5. *Full per-route skeleton component files (`<DashboardSkeleton />`, `<PlanSkeleton />`, …)*
   — rejected. 13 surfaces would mean 13 new files plus 13 new test files; the skeletons share
   90% of their structure (heading rect + content cards). One file with a switch is simpler.

**Why this is the right call here:**

- **No protected-file edits.** `package.json` and `pnpm-lock.yaml` are untouched. Tailwind v4
  is already wired (per `frontend/postcss.config.mjs` + `app/globals.css`); `animate-pulse`,
  `bg-muted`, `rounded-md`, `h-4`, `w-1/2`, `space-y-3` are all in-scope utility classes that
  the project already uses elsewhere.
- **Self-Hosted Contract neutrality.** Skeletons are presentational and add no operator
  surface area (no new env vars, no new metrics, no contract delta). Section 9.x is silent.
- **Symmetry with the existing layout.** The (app) layout (`frontend/src/app/(app)/layout.tsx`)
  already renders `<Nav />` + `<main>` + `<BottomNav />` instantly; injecting `loading.tsx`
  in each segment puts the skeleton inside the existing `<main>` so nav stability is
  preserved.
- **Tests stay deterministic.** A single `<Skeleton />` div is trivially queryable via
  `data-testid` plus `role="status"` + `aria-busy="true"` for a11y.

## Runtime model (load-bearing)

Next.js 15 App Router treats `loading.tsx` per-segment as the Suspense fallback for the
route's children. When a segment streams, the framework renders the segment's `loading.tsx`
above the segment's actual `page.tsx` until the page's RSC payload is ready. This means:

1. `frontend/src/app/(app)/dashboard/loading.tsx` shows the dashboard skeleton during the
   first paint of `/dashboard` (cold navigation, full RSC render).
2. Once `dashboard/page.tsx` has hydrated, **the inner client component (`DashboardPage`)
   still has its own loading state** for the first TanStack Query fetch. That state today is
   a `<p>{t("loading")}</p>`. We replace that text with the same `<RouteSkeleton variant="dashboard" />`
   so the user sees the same shape during both phases (segment-loading + post-mount fetch).
3. Soft navigations between (app) routes: Next.js shows `loading.tsx` of the destination
   segment, not the source — same visual contract.

This is the standard Next 15 idiom; nothing exotic. The crossover from `loading.tsx` to the
client component's own loading state is invisible because both render the same skeleton.

**`skeleton.tsx` API:**

```ts
import type { HTMLAttributes } from "react";
import { cn } from "@/lib/utils";

export function Skeleton({ className, ...props }: HTMLAttributes<HTMLDivElement>) {
  return (
    <div
      role="presentation"
      aria-hidden="true"
      className={cn("animate-pulse rounded-md bg-muted", className)}
      {...props}
    />
  );
}
```

`cn` is already exported by `frontend/src/lib/utils.ts` (used by `button.tsx`, `card.tsx`,
`input.tsx`); confirm at execution time. The `bg-muted` Tailwind token is defined in the
project's globals (used by `<Card>`); confirm at execution time. If `bg-muted` is not
present, fall back to `bg-foreground/10` which is portable.

**i18n keys:**

- `tr.json` + `en.json`: add a top-level `common` namespace if absent (verify; otherwise add
  to existing). Single key:
  - TR: `"common": { "loading": "Yukleniyor" }`

If the `common` namespace already exists, append the `loading` key inside the existing block.
Per the existing v0.5 plans, the `common` namespace may already host `cancel`/`save`/`retry`;
verify and append idempotently. **No emoji; no trailing punctuation.**

**Verification (skeleton.test.tsx):**

## Risks and Mitigations

- **Risk: Tailwind v4 may not have `bg-muted` token defined in this project's globals.**
  *Mitigation:* check `frontend/src/app/globals.css` and `frontend/tailwind.config.ts` (or
  Tailwind v4 inline `@theme` block) at execution time. If `--color-muted` is undefined, the
  fallback is `bg-foreground/10` (portable across themes). Adjust `<Skeleton />` source
  accordingly. The `<Card>` component already references the bg-muted vocabulary via shadcn
  conventions; confirm during execution.
- **Risk: 15 new `loading.tsx` files inflate the bundle.** *Mitigation:* each
  `loading.tsx` is a 3-line server component that imports a single client component. Next.js
  tree-shakes; the actual delta is the `RouteSkeleton` module + its variant tree (~150 lines
  of JSX). Per-route bundle remains under 1KB additional. (Track this in Phase 36-03 budget.)
- **Risk: existing tests assert on `getByText(/loading/i)` and break.** *Mitigation:* T4
  walks every touched test file; the replacement pattern is mechanical. If any test breaks
  with a less-obvious assertion (e.g. snapshot test), fall back to a `data-testid="route-skeleton"`
  attr on the wrapper for direct querying — but this is a last resort, the role-based query
  is preferred.
- **Risk: `loading.tsx` server component imports a client component using
  `useTranslations`.** *Mitigation:* this is a supported Next 15 pattern; the
  `RouteSkeleton` carries `"use client"` and the wrapper `loading.tsx` is a server file that
  imports it. Verified via the `dashboard/page.tsx` precedent which is a client file.
- **Risk: cascade-test churn.** Touching 15 client components + 15 test files in one plan is
  large. *Mitigation:* the per-file diff is tiny (one return statement + one import). The
  three split commits in T4 keep review chunks under ~200 lines each.
- **Risk: `<RouteSkeleton variant="exercise-detail" />` for a dynamic `[id]` segment may
  have a flicker if the page layout differs significantly from the skeleton.** *Mitigation:*
  the skeleton is structural, not pixel-perfect. Layout shift is bounded because both use
  the same `space-y-3 max-w-6xl` parent from the (app) layout. CLS measurement happens in
  Phase 36-03.
