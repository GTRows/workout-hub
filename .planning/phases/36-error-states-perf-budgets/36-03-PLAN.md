**Milestone:** v0.6 Operational Maturity

## Goal

Close out Phase 36 by giving the (app) surfaces real, measurable runtime performance signals
plus a written, source-of-truth perf budget — without touching any protected file.

Phase 35 already added a process-local Prometheus metrics registry (`frontend/src/lib/metrics/registry.ts`)
and a `/api/metrics` endpoint. That registry currently records server-observed HTTP request
count + duration; it does NOT capture client-side rendering performance. The five Core Web
Vitals (LCP, CLS, INP, FCP, TTFB) live entirely in the browser and require a client-side
collector.

This sub-plan delivers:

1. **Client collector:** a tiny `<WebVitalsReporter />` Client Component that uses Next 15's
   built-in `useReportWebVitals` hook (re-exported from `next/web-vitals`, ships with the
   `next` package — no new dependency) and `POST`s each metric event to a new Next.js Route
   Handler at `/api/vitals`.
2. **Ingest endpoint:** `frontend/src/app/api/vitals/route.ts` — a Node-runtime POST handler
   that validates a small Zod payload (`zod` is already a project dep) and records the metric
   into the existing process-local registry as a histogram family
   `wh_frontend_web_vital_seconds` (or `wh_frontend_web_vital_score` for unitless metrics —
   see T2). Aggregates surface through the existing `/api/metrics` Prometheus scrape with
   zero operator-side wiring.
3. **Histogram extension:** widen the existing registry to host a second histogram family
   keyed by `(name, route)` rather than `(method, route)`. Avoid breaking the existing HTTP
   histogram by keeping it intact and adding a parallel registration path. Two new public
   functions: `recordWebVital(name, route, value)` and the corresponding render block in
   `renderProm()`.
4. **Perf-budget doc:** a NEW `docs/PERF_BUDGETS.md` (NOT a protected file — `docs/` is open
   for new files) recording numerical targets for LCP, CLS, INP, FCP, TTFB, the per-route JS
   bundle ceiling, and the next-action procedure when a target regresses. This is the
   "budget" deliverable; CI enforcement is explicitly deferred.
5. **CHANGELOG note:** the v0.6 unreleased section in `CHANGELOG.md` is protected per the
   project hook; we DO NOT touch it. Phase-close note happens at the v0.6 release plan, not
   here. (See "Files NOT touched" below.)

The result: every authenticated render of the (app) shell silently emits Web Vitals to the
in-process registry, the operator can scrape `/api/metrics` and see real-user LCP/CLS/INP
distributions per route, and the project carries a written budget that future regressions
can be measured against.

## Architecture Decision: Next 15's built-in `useReportWebVitals` -> POST `/api/vitals` -> existing registry; doc-only budget

**Decision:** Use the framework-native `useReportWebVitals` hook re-exported from
`next/web-vitals` (built into the `next` package; no `web-vitals` dep add). The hook fires
once per metric (LCP, CLS, INP, FCP, TTFB) per page load with a `Metric` object carrying
`{ name, value, id, navigationType, ...}`. We `fetch("/api/vitals", { method: "POST", body
... })` from inside the hook body; the route handler validates a Zod payload and records to
the existing registry. Aggregates surface via the Phase 35 `/api/metrics` endpoint that the
operator already scrapes.

For the budget deliverable: a NEW `docs/PERF_BUDGETS.md` (not protected; `docs/` allows new
files but `docs/SELF_HOSTED_CONTRACT.md` is the only protected entry — verified by inspecting
`.claude/hooks/pre_guard_release_files.py` against `CLAUDE.md`'s Protected Files list).

**Rejected alternatives:**

1. *Add `web-vitals` as a direct dependency.* — rejected. `frontend/package.json` is a
   protected file (CLAUDE.md "Protected Files"). Cannot add deps. Next 15 already re-exports
   the upstream `web-vitals` library through its own `next/web-vitals` entry point, so we get
   the same primitive without touching `package.json`.
2. *Lighthouse CI workflow integration* (`.github/workflows/lighthouse.yml` + `lighthouserc.json`).
   — **STATUS: BLOCKED.** Adding a new workflow file would edit `.github/workflows/**`
   (protected). Surface as a deferred item in `docs/PERF_BUDGETS.md` (see T4) with a clear
   trigger ("operator approves a workflow add" or "v1.0 hardening phase 38+"). Capture in
   `.planning/ISSUES.md` per CLAUDE.md "Deferred Work" convention (see T5).
3. *Bundle-size budget enforcement via `scripts/check-bundle-size.mjs`.* — rejected for THIS
   plan. `scripts/` is also a protected directory. Reporting via the doc is acceptable;
   enforcement defers to v1.0.
4. *Send vitals to an external sink (e.g. Vercel Analytics, custom OTLP).* — rejected. The
   Self-Hosted Contract requires single-tenant, air-gapped-friendly defaults; no external
   telemetry. The existing `/api/metrics` Prometheus scrape is the operator-facing surface
   already approved by Phase 35.
5. *Render the WebVitalsReporter inside the (app) layout only* — partially adopted. To match
   what `useReportWebVitals` measures (the whole document, not a fragment), the component
   mounts at the **root layout** so vitals fire for every route including `(auth)`. The
   route-label segregation happens at the registry side via the request's `pathname`.
6. *Write a generic `/api/telemetry` endpoint* — rejected. Specific endpoint
   (`/api/vitals`) keeps payload validation tight and avoids a future general-telemetry
   surface that would invite scope creep.
7. *Use `navigator.sendBeacon` instead of `fetch`* — partially adopted. `useReportWebVitals`
   internally batches metrics and the recommended client pattern from Next docs is `fetch`
   with `keepalive: true` (or `sendBeacon` if available). Plan-baseline: try
   `navigator.sendBeacon` first (best for unload-time delivery), fall back to
   `fetch(url, { method: "POST", keepalive: true })`. This is a 5-line client snippet.
8. *Skip the doc; just ship the collector.* — rejected. The phase title is
   "error-states-perf-budgets"; the budget IS the deliverable. Without written targets the
   collector is just data with no decision rule.

**Why this is the right call here:**

- **Zero protected-file edits.** `package.json`, `pnpm-lock.yaml`, `compose.yml`,
  `.github/workflows/**`, `scripts/**`, `IDENTITY.yaml`, `CHANGELOG.md`, `docs/SELF_HOSTED_CONTRACT.md`
  are all UNTOUCHED. `docs/PERF_BUDGETS.md` is a NEW file, not an edit to an existing
  protected file.
- **No new runtime dependency.** `next/web-vitals` is shipped with the existing `next`
  package; `zod` is already used by the app for request validation; `getRegistry()` is the
  Phase 35 in-process singleton.
- **Self-Hosted Contract neutrality.** The new `/api/vitals` endpoint does not require an
  env var, does not add a new operator surface area beyond the existing `/api/metrics`
  scrape, does not log secrets, and does not mutate state on disk. Section 9.x of the
  contract (logging/metrics) is satisfied.
- **Operator can already see the result.** No infra change; the same Prometheus scraper that
  reads `/api/metrics` (Phase 35) now sees additional histogram families.
- **Tests stay deterministic.** A Zod payload validator + a registry record call are pure
  functions; vitest covers both. No browser-only `PerformanceObserver` mocking needed
  because the hook itself is mocked in tests.

## Runtime model (load-bearing)

`useReportWebVitals` is a Next 15 client-side hook. Lifecycle:

1. `<WebVitalsReporter />` mounts inside the root `<Providers>` tree (it is a Client
   Component with `"use client"`).
2. Inside the component, the hook receives a single callback invoked once per Web Vital event.
   Next.js's runtime wires the upstream `web-vitals` library and emits a stable schema:
   ```ts
   {
     id: string;            // unique per event
     name: "LCP" | "CLS" | "INP" | "FCP" | "TTFB" | "Next.js-hydration" | "Next.js-route-change-to-render" | "Next.js-render";
     value: number;         // ms for time-based metrics; unitless score for CLS
     delta: number;
     entries: PerformanceEntry[];
     navigationType: "navigate" | "reload" | "back-forward" | "back-forward-cache" | "prerender";
     rating?: "good" | "needs-improvement" | "poor";  // not always present
     startTime: number;
     label?: "web-vital" | "custom";
   }
   ```
3. The callback POSTs a small JSON payload `{ name, value, id, navigationType, route }` to
   `/api/vitals`. `route` is `window.location.pathname`, normalized via the existing
   `route-label.ts` helper to keep cardinality bounded (`/exercises/[id]` not the literal
   id; `route-label.ts` already exists at `frontend/src/lib/metrics/route-label.ts` per Phase 35).
4. The route handler validates the payload with Zod, calls `getRegistry().recordWebVital(...)`,
   and returns 204 No Content. No body, no logging on success path. On Zod failure: 400 with
   a minimal JSON body (`{ "error": "invalid payload" }`) — no detail leak.
5. The registry stores the metric in a new histogram family. On the next `/api/metrics`
   scrape, the lines render alongside existing HTTP histograms.

**Important constraints:**

- Only the five **standard Core Web Vitals** are recorded: `LCP`, `CLS`, `INP`, `FCP`, `TTFB`.
  Next-specific events (`Next.js-hydration`, `Next.js-route-change-to-render`,
  `Next.js-render`) are **dropped** at the client side to keep registry cardinality predictable.
- `CLS` is unitless; the histogram bucket set differs from time-based metrics (see T3).
- `value` is in milliseconds for `LCP`, `INP`, `FCP`, `TTFB` (Next emits ms — verify at
  execution time; the spec is browser milliseconds). The registry stores **seconds** for
  time-based metrics to match the existing histogram convention; the route handler converts
  ms -> seconds (`value / 1000`) before recording.
- **Backpressure:** if the POST fails (network error, server 5xx), the client logs once via
  `console.warn` and drops the metric. No retry, no IndexedDB queue. Web Vitals are best-effort
  observability, not durable telemetry.
- **CSRF/auth:** the existing middleware (Phase 29.5/35) does NOT rewrite or redirect
  `/api/metrics`; we extend the same exempt-path treatment to `/api/vitals` if applicable.
  Verify at execution time by reading `frontend/src/middleware.ts`. If middleware exempts
  `/api/*` already, no middleware edit needed.
- **Cardinality bound:** the registry's histogram key becomes `(name, route)`. With 5 vital
  names and an upper bound of ~20 normalized routes, cardinality is ~100 series — well within
  Prometheus conventions.

### T2 - `/api/vitals` POST route handler

**Files:**

- New: `frontend/src/app/api/vitals/route.ts`
- New: `frontend/src/app/api/vitals/route.test.ts`

**Handler shape:**

```ts
import { z } from "zod";
import { getRegistry } from "@/lib/metrics/registry";
import { normalizeRoute } from "@/lib/metrics/route-label";

export const dynamic = "force-dynamic";
export const runtime = "nodejs";

const VitalSchema = z.object({
  name: z.enum(["LCP", "CLS", "INP", "FCP", "TTFB"]),
  value: z.number().finite().nonnegative(),
  id: z.string().min(1).max(128),
  navigationType: z
    .enum(["navigate", "reload", "back-forward", "back-forward-cache", "prerender"])
    .optional(),
  route: z.string().min(1).max(256),
});

export async function POST(req: Request) {
  let parsed;
  try {
    const body = await req.json();
    parsed = VitalSchema.safeParse(body);
  } catch {
    return new Response(JSON.stringify({ error: "invalid payload" }), {
      status: 400,
      headers: { "content-type": "application/json" },
    });
  }
  if (!parsed.success) {
    return new Response(JSON.stringify({ error: "invalid payload" }), {
      status: 400,
      headers: { "content-type": "application/json" },
    });
  }
  const { name, value, route } = parsed.data;
  const seconds = name === "CLS" ? value : value / 1000;
  getRegistry().recordWebVital(name, normalizeRoute(route), seconds);
  return new Response(null, { status: 204 });
}
```

**Notes on the snippet:**

- The `try/catch` around `req.json()` is permitted because the JSON parse can throw on a
  malformed body — that IS a real runtime failure mode (CLAUDE.md "Do not add error
  handling for scenarios that cannot happen" does NOT cover protocol parse errors).
- `value` arriving from the browser is **in milliseconds** for time-based vitals (this is
  what `useReportWebVitals` emits); we divide by 1000 server-side. CLS arrives unitless and
  passes through.
- `normalizeRoute` is the Phase 35 helper. Verify signature at execution time; if the
  helper expects an HTTP `URL`, adapt accordingly (read its source first; do not duplicate).

**Test cases (`route.test.ts`):**

1. POST with a valid LCP payload (value: 2500 ms) returns 204; the registry's
   `wh_frontend_web_vital_seconds` histogram has the bucket `le="2.5"` incremented for
   `name="LCP",route="/dashboard"`.
2. POST with a valid CLS payload (value: 0.07) returns 204; the registry's
   `wh_frontend_web_vital_score` histogram has the bucket `le="0.1"` incremented for
   `name="CLS",route="/dashboard"`.
3. POST with an invalid `name` returns 400 and does NOT touch the registry.
4. POST with a malformed JSON body returns 400.
5. POST with a negative `value` returns 400 (Zod `.nonnegative()`).
6. POST with a path-style route that contains a UUID-like id (e.g. `/exercises/abc123`) is
   normalized to `/exercises/[id]` before recording (asserted via the rendered Prometheus
   line).

Use `beforeEach` with `getRegistry().reset()` mirroring `route.test.ts` from `/api/metrics`.

### T3 - `<WebVitalsReporter />` Client Component + test

**Files:**

- New: `frontend/src/components/web-vitals-reporter.tsx`
- New: `frontend/src/components/web-vitals-reporter.test.tsx`

**Component shape:**

```tsx
"use client";

import { useReportWebVitals } from "next/web-vitals";

const ALLOWED = new Set(["LCP", "CLS", "INP", "FCP", "TTFB"]);

export function WebVitalsReporter() {
  useReportWebVitals((metric) => {
    if (!ALLOWED.has(metric.name)) return;
    const payload = JSON.stringify({
      name: metric.name,
      value: metric.value,
      id: metric.id,
      navigationType: metric.navigationType,
      route: typeof window !== "undefined" ? window.location.pathname : "/",
    });
    const url = "/api/vitals";
    if (typeof navigator !== "undefined" && typeof navigator.sendBeacon === "function") {
      const blob = new Blob([payload], { type: "application/json" });
      navigator.sendBeacon(url, blob);
      return;
    }
    void fetch(url, {
      method: "POST",
      body: payload,
      headers: { "content-type": "application/json" },
      keepalive: true,
    }).catch(() => {
      // best-effort observability; drop on failure
    });
  });
  return null;
}
```

**Notes:**

- Returns `null`; no DOM. Pure side-effect mounting.
- `useReportWebVitals` is the Next 15 official hook; importing from `next/web-vitals` does
  NOT pull in a separate dep — Next bundles upstream `web-vitals` internally. Verified by
  Next 15 docs and absence of `web-vitals` in `package.json`.
- Filters non-Core-Web-Vitals events client-side so the registry stays bounded.
- Uses `sendBeacon` first (best for unload-time delivery), falls back to `fetch` with
  `keepalive: true`.
- The `.catch(() => {})` is intentional: best-effort telemetry; we do NOT log on failure
  beyond the silent drop. (If ESLint complains about the empty catch, add a single
  `// best-effort observability; drop on failure` inline comment as shown.)

## Risks and Mitigations

- **Risk: `next/web-vitals` is not actually a Next 15 export and requires a separate dep.**
  *Mitigation:* verify at execution time. Run `node -e "console.log(Object.keys(require('next/web-vitals')))"`
  inside `frontend/`. If `useReportWebVitals` is not present, fall back to **Plan B**: skip
  T2/T3/T4 and ship only T1 (registry extension) + T5 (doc) — the registry extension is
  still useful for future operator pushes, and the doc records the deferred client-side
  collection. Surface as deviation, do not block the entire plan.
- **Risk: `useReportWebVitals` requires the rendered tree to mount under `<NextIntlClientProvider>`
  or another provider.** *Mitigation:* the official Next docs document `useReportWebVitals`
  as a standalone hook with no provider requirement. The `<WebVitalsReporter />` mounts
  outside `<Providers>` precisely to avoid coupling.
- **Risk: `navigator.sendBeacon` may be blocked by some Content-Security-Policy headers.**
  *Mitigation:* the fallback is `fetch(...)`; both eventually succeed unless the
  POST endpoint is unreachable. Operator-side CSP tuning is out of scope — this repo
  doesn't ship a CSP today (verify via Next config; if it does, the `connect-src 'self'`
  default permits same-origin POST). If CSP blocks `/api/vitals`, the metric is silently
  dropped — same as any other failure path.
- **Risk: Histogram cardinality explodes if the route normalizer is too permissive.**
  *Mitigation:* `normalizeRoute` from Phase 35 is already deployed against the Prometheus
  HTTP histogram and known to produce <= ~20 stable labels. Reuse the same helper to keep
  the cardinality bound tight. Verify at execution time that the helper exists and exports
  the expected name.
- **Risk: vitest jsdom does not implement `navigator.sendBeacon` (it doesn't).**
  *Mitigation:* T3 test #1 stubs `navigator.sendBeacon` via `vi.spyOn`. T3 test #2 deletes
  the property to force the `fetch` path. Both branches are covered.
- **Risk: `registry.ts` exceeds the 200-line cap after the addition.** *Mitigation:* T1
  documents the helper-extraction escape hatch (`web-vital-histogram.ts`). Plan-baseline
  is to extract proactively if the post-edit count exceeds 195.
- **Risk: Zod 3.x changes its enum syntax in a future minor.** *Mitigation:* the project is
  pinned to `zod ^3.24.0`; the `z.enum([...])` API is stable in 3.x. Future bumps land in a
  separate phase.
- **Risk: The route handler runs in the Edge runtime accidentally and `getRegistry()`'s
  `globalThis` storage does not persist.** *Mitigation:* the handler explicitly sets
  `export const runtime = "nodejs"` mirroring `/api/metrics/route.ts:4`. Same-process
  storage is the design.
- **Risk: `docs/PERF_BUDGETS.md` collides with an existing perf doc.** *Mitigation:* `Glob`
  reports no match for `docs/PERF*` today. New file.
- **Risk: `.planning/ISSUES.md` does not exist or has a different schema than expected.**
  *Mitigation:* T5 instructs the executor to verify the schema at execution time and
  mirror it. If the file is empty or has no entries, the executor creates the first entry
  using the schema defined in CLAUDE.md "Deferred Work": what / why / trigger / owner.
- **Risk: A test that mocks `next/web-vitals` interferes with other tests in the same
  vitest worker.** *Mitigation:* `vi.mock` is module-scoped to the test file; vitest
  unmocks between files. T3 test file uses `vi.mock` at top-of-file; no leak.
- **Risk: The middleware redirects `/api/vitals` to `/login` (401 cascade).** *Mitigation:*
  `frontend/src/middleware.ts` (Phase 29.5/35) exempts `/api/*` paths. Verify at execution
  time; if `/api/vitals` is NOT exempt, **add it to the exempt list**. The middleware file

  and a small additive change is in scope here. If middleware is on the protected list
  after all, surface as a deviation and consider rewriting the request from a Server
