# Phase 36 - Plan 02: Error Boundaries (Next.js `error.tsx` per (app) route + global)

**Milestone:** v0.6 Operational Maturity
**Phase:** 36 - error-states-perf-budgets
**Plan:** 36-02 (second of three; sub-plan 36-01 loading skeletons shipped at af8209e; 36-03 perf-budgets remains)
**Status:** Not started
**Author date:** 2026-05-09

## Goal

Eliminate the raw "white-screen / unhandled exception" experience for every authenticated
(app) surface. Today the (app) layout renders nav + bottom-nav + main, but if a Server
Component, route handler, or Client Component throws during render, Next.js falls back to
its built-in error overlay in dev and a generic browser error in production. There is **zero**
`error.tsx` file under `frontend/src/app/` (`Glob` returned no matches), and no
`global-error.tsx` at root. The (app) layout already mounts a `<SessionExpiredShell />` at
`frontend/src/app/(app)/layout.tsx:9`, so 401-driven redirects are handled separately and out
of scope here.

This sub-plan introduces:

1. A small reusable `<RouteError />` Client Component at
   `frontend/src/components/errors/route-error.tsx` that renders a stable, branded fallback
   built on the existing `<Card>` + `<Button>` primitives, with i18n strings, a "Try again"
   button wired to Next 15's `reset` prop, an `<a>` to `/dashboard` for forced unstuck, and a
   `console.error(error)` log (no external sink in this repo).
2. A Next.js `error.tsx` segment file per (app) surface that imports `<RouteError />` and
   forwards its `error` + `reset` props. These are Client Components per the Next 15
   contract.
3. A top-level `frontend/src/app/global-error.tsx` for app-shell-level crashes that escape the
   per-segment boundary (e.g. a throw inside the root layout). Per Next 15 spec, a
   `global-error.tsx` MUST render its own `<html>` and `<body>` because it replaces the root
   layout when triggered.
4. Three i18n keys in the existing `common` namespace: `common.error`, `common.errorHint`,
   `common.tryAgain`. (`common.loading` was added by 36-01; we are extending the same block.)
5. Tests: one component test for `<RouteError />` covering reset wiring, log emission, and
   accessibility; the per-segment `error.tsx` files are one-line wrappers and do not earn
   their own tests (same precedent as 36-01's `loading.tsx` files).

The result: every (app) surface paints a branded, recoverable error card when its subtree
throws, with a "Try again" button that calls Next.js `reset()` and re-mounts the segment, and
the user is never stranded on a blank page.

## Architecture Decision: thin per-segment wrappers + one shared `<RouteError />`

**Decision:** Implement a single shared `<RouteError />` Client Component composing the
existing `<Card>` (`frontend/src/components/ui/card.tsx`) + `<Button>` (`button.tsx`)
primitives. Each segment-level `error.tsx` is a 5-line wrapper that imports `<RouteError />`
and forwards Next 15's `{ error, reset }` props. `global-error.tsx` mirrors the wrapper but
also renders its own `<html lang>` + `<body>` shell (Next 15 contract).

**Rejected alternatives:**

1. *Per-route bespoke error components (`<DashboardError />`, `<PlanError />`, ...)* —
   rejected. The error fallback's job is to be uniform, not to mimic the route's success
   shape. A user mid-fatal-error does not benefit from a route-shaped skeleton; they need a
   recognizable error surface and a clear way out. One component, one shape.
2. *Inline JSX in every `error.tsx`* — rejected. Would duplicate the i18n + reset + log
   logic 13+ times. Maintenance liability; tests would have to cover each.
3. *Re-use a third-party error-boundary lib (`react-error-boundary`)* — rejected.
   `frontend/package.json` is on the protected-files list (CLAUDE.md "Protected Files");
   we cannot add a dependency. Next 15's segment-error contract is the native idiom.
4. *Wrap the (app) layout in a single `error.tsx` instead of one per segment* — rejected
   for two reasons: (a) Next 15 layouts cannot be wrapped by a sibling `error.tsx` directly
   from within their own group; the boundary placement that catches a layout's children is
   the layout's adjacent `error.tsx`. A single `error.tsx` at the (app) layout level catches
   ALL nested route throws but renders ABOVE the nav, which strips the user of navigation —
   poor UX. Per-segment placement keeps `<Nav />` + `<BottomNav />` visible during error
   recovery. (b) Per-segment placement also gives Next.js a tighter "reset" boundary so
   `reset()` re-renders only the affected page tree, not the entire (app) shell.
5. *Defer `global-error.tsx`* — rejected. Without it, an exception in `layout.tsx` itself
   (e.g. a translation-load error during SSR, a malformed cookie) falls back to the browser's
   default behaviour. Adding it is one new file at root; no downside.
6. *Send errors to an external sink (Sentry, OpenTelemetry, custom `/api/errors`)* —
   rejected. The Self-Hosted Contract (`docs/SELF_HOSTED_CONTRACT.md`) keeps the app
   single-tenant + air-gapped-friendly; no external telemetry by default. The existing repo
   has no error-collection endpoint. `console.error` is the only sink for this sub-plan; a
   future operator-controlled error-reporting endpoint is out of scope.

**Why this is the right call here:**

- **No protected-file edits.** `frontend/package.json` and `pnpm-lock.yaml` stay untouched.
  The new component reuses `<Card>` / `<Button>` and Tailwind utilities already in scope.
- **Self-Hosted Contract neutrality.** Error UI is presentational; no operator surface area
  (no env vars, no metrics, no contract delta). Section 9 logging stays untouched.
- **Symmetry with 36-01.** Mirrors the shape of 36-01: one shared component
  (`route-skeleton.tsx`), 15 thin segment wrappers, one i18n namespace extension. Reviewable
  diff.
- **Recoverable by design.** `reset()` is the Next 15-prescribed escape hatch; the user
  retries the failed segment without a full page reload.
- **Tests stay deterministic.** `<RouteError />` is a pure Client Component with two props
  (`error`, `reset`); a vitest unit test asserts on aria roles, button click -> reset call,
  and `console.error` invocation.

## Runtime model (load-bearing)

Next.js 15 App Router treats `error.tsx` per-segment as a **React Error Boundary** for that
segment's `page.tsx` and any nested children that did not declare their own `error.tsx`. The
file MUST be a Client Component (`"use client"` directive) because Error Boundaries are a
React class-component feature that needs to run on the client. Next.js wraps the segment's
content in this boundary automatically. When a render-time exception is thrown:

1. The boundary catches it. Next.js passes two props to the default export:
   `error: Error & { digest?: string }` and `reset: () => void`.
2. The boundary unmounts the failed subtree and mounts the `error.tsx` component instead.
3. Calling `reset()` tells Next.js to attempt re-rendering the boundary's children.

Important constraints from the Next 15 spec:

- `error.tsx` does NOT catch errors thrown in the **same segment's `layout.tsx`** (or
  `template.tsx`); that requires the parent segment's `error.tsx` to catch. We accept this:
  the (app) group's `layout.tsx` is small (nav + main + bottom-nav, no async work), and the
  root `app/layout.tsx` errors are caught by `global-error.tsx`.
- `error.tsx` does NOT catch errors during navigation (those are caught by the framework's
  own reload path).
- `global-error.tsx` REPLACES `app/layout.tsx` when triggered, so it MUST render its own
  `<html>` and `<body>` tags. Next 15 enforces this; if missing, the app crashes harder.
- The `error` prop's `.digest` field is the server-side error digest (set when an RSC
  throws); we do not surface it to users in this sub-plan but we DO log it to the console
  with the rest of the error metadata.

- **File-size cap (CLAUDE.md):** max ~200 lines per file. `route-error.tsx` aims for ~70
  lines. The `error.tsx` segment files are 5-7 lines each.
- **No emojis.** Plain Tailwind classes; English code; user-facing strings live in i18n
  resource files only.
- **i18n keys are additive.** Add three keys inside the existing `common` namespace:
  - `common.error` — heading text. TR: "Bir seyler ters gitti". EN: "Something went wrong".
  - `common.errorHint` — body paragraph. TR: "Tekrar dene veya panele don.". EN: "Try
    again, or return to the dashboard."

  `{ error: Error & { digest?: string }; reset: () => void }`. The Next 15 documented type
  for `error.tsx` props.
- **Client Component only.** Every `error.tsx` and `global-error.tsx` MUST start with
  `"use client";` per Next 15 spec.
- **No new directory** outside `components/errors/`. The `errors/` group is new; place it
  directly under `components/` (not nested in `ui/`) — same convention as `skeletons/` from
  36-01.
- **Per CLAUDE.md:** "Do not add error handling for scenarios that cannot happen." The
  `<RouteError />` component has no try/catch — the props are guaranteed by Next 15. The
  `console.error` is logging, not handling.
- **Per CLAUDE.md:** "Do not add docstrings, comments, or type annotations to code you did
  not change." The new files MAY carry a single one-line file-header comment (mirrors
  36-01's `<Skeleton>` and `<RouteSkeleton>` precedent); existing files MUST NOT gain new
  comments beyond the import statement that the test-file change requires.
- **No `data-testid`** unless a test cannot reach the element via accessible role/name.
  Prefer `getByRole("alert")` and `getByRole("button", { name: /try again/i })`.
- **Reset semantics.** The "Try again" button MUST call `reset()` (Next 15 prop), not
  `window.location.reload()`. The link to `/dashboard` MUST be a `next/link` `<Link>` (not a
  raw `<a>`), so soft-navigation engages.
- **Console-only logging.** `console.error("Route error", { message: error.message,
  digest: error.digest })` ONCE on mount via `useEffect(() => { ... }, [error])`. Do not
  spam on re-renders. No external HTTP call, no `navigator.sendBeacon`.
- **Accessibility.** The wrapper carries `role="alert"` so screen readers announce the
  error on mount. Heading is an `<h2>` (consistent with `<CardTitle>`). The "Try again"
  button is a real `<button>`; the dashboard link is a real `<a>` via `<Link>`.

### T4 - `global-error.tsx` at root

**File:**

- New: `frontend/src/app/global-error.tsx`

Per the Next 15 spec, `global-error.tsx` REPLACES the root layout when triggered, so it MUST
render its own `<html>` and `<body>` shell. It MUST also be a Client Component. Because the
root layout's `Providers` may have failed (that's why we got here), the global error MUST NOT
depend on any provider context — including `next-intl`. It uses **hardcoded English strings**
as a final fallback (the operator-facing screen).

**Component shape:**

```tsx
"use client";

import { useEffect } from "react";

export default function GlobalError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  useEffect(() => {
    // eslint-disable-next-line no-console
    console.error("Global error", {
      message: error.message,
      digest: error.digest,
    });
  }, [error]);

  return (
    <html lang="en">
      <body className="min-h-screen bg-background text-foreground antialiased">
        <main className="mx-auto flex min-h-screen max-w-md flex-col items-center justify-center gap-4 p-6 text-center">
          <h1 className="text-2xl font-semibold">Something went wrong</h1>
          <p className="text-muted-foreground">
            The application crashed. Reload to try again.
          </p>
          <button
            type="button"
            onClick={() => reset()}
            className="inline-flex h-10 items-center justify-center rounded-md bg-primary px-4 text-sm font-medium text-primary-foreground hover:bg-primary/90"
          >
            Try again
          </button>
        </main>
      </body>
    </html>
  );
}
```

**Why hardcoded English (not i18n):** if `global-error.tsx` is triggered, the root layout's
`Providers` may have crashed; calling `useTranslations()` would throw (no
`NextIntlClientProvider` in scope) and we would loop into the framework's last-resort
overlay. The Next 15 docs explicitly recommend a self-contained global-error file that does
not depend on the app's normal provider tree. EN-only is acceptable as the operator-facing
last-resort screen; the repo's primary locale is TR but global-error is the absolute
final-fallback path.

**Verification:** no unit test for `global-error.tsx` (its render path is special and the
component is trivial). Verified via:

1. `pnpm typecheck` — props shape conforms to Next 15.
2. `pnpm build` — Next 15 recognizes `global-error.tsx` as a known special file. If misnamed
   or mis-located, the build fails.

Commit: `feat(ui-36-02): add global-error.tsx for app-shell crashes`

## Risks and Mitigations

- **Risk: `<Link href="/dashboard">` inside `<RouteError />` triggers a navigation that
  re-renders the same broken segment.** *Mitigation:* `/dashboard` is a different segment;
  Next.js soft-navigates to it. If the user is already on `/dashboard` and the dashboard
  route is what threw, clicking the link is a no-op visually but Next.js still attempts a
  re-render (the boundary's reset effectively); confirm at smoke time. Acceptable behaviour
  — the user has the "Try again" button as the primary recovery.
- **Risk: `next-intl` provider may have crashed before per-segment `error.tsx` mounts (e.g.
  if `Providers` itself threw).** *Mitigation:* the per-segment `error.tsx` mounts INSIDE the
  (app) layout, which is INSIDE the root `Providers`; a Providers-level crash escapes to
  `global-error.tsx`, which uses no providers. So `<RouteError />` always has a valid
  `useTranslations` context when it mounts. Verified by the boundary placement model.
- **Risk: `pnpm build` may fail if `global-error.tsx` does not include `<html>` + `<body>`.**
  *Mitigation:* the T4 snippet renders both. Build verifies.
- **Risk: ESLint `no-console` rule rejects the `console.error` call.** *Mitigation:* T2
  adds an inline `eslint-disable-next-line no-console` comment. If the project's ESLint
  config is silent on `no-console`, the disable is benign and may be removed at execution
  time to minimize diff.
- **Risk: `error.tsx` files placed outside the `(app)` group catch other route groups'
  errors silently.** *Mitigation:* placement is strictly inside `frontend/src/app/(app)/`
  and root. The `(auth)` group does not get an `error.tsx` in this plan; if its routes
  throw, they fall through to `global-error.tsx`. Acceptable: (auth) is short, SSR-only,
  and its login page already has explicit error UX.
- **Risk: re-renders with the SAME error reference cause repeated `console.error` calls.**
  *Mitigation:* the `useEffect(() => {...}, [error])` dependency confines logging to one
  call per distinct error. Test #7 in T2 covers this.
- **Risk: Next 15 may pass an additional `digest` field shape we did not expect.**
  *Mitigation:* the type `Error & { digest?: string }` is per Next 15 official docs; if Next
  changes this, the type-check fails loudly at execution time and the plan surfaces.
- **Risk: cascade test churn is small but the new component test fixtures must mirror
  existing patterns or vitest will fail at JSX rendering.** *Mitigation:* read
  `route-skeleton.test.tsx` (precedent from 36-01) before writing `route-error.test.tsx`;
  reuse the same `NextIntlClientProvider` wrapper helper (likely under
  `frontend/src/test-utils/` or inlined per file).
- **Risk: the secondary "Dashboard" button label key (`common.goHome` vs reusing an
  existing key).** *Mitigation:* T2 instructs the executor to verify and add `common.goHome`
  if no equivalent exists; this is a one-line addition to T1's i18n diff.
