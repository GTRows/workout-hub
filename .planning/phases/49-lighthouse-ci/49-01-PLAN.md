## Goal

Close deferred issue **i-15** by wiring three perf-budget gates into CI that the v0.6 Phase 36-03 doc-only ship intentionally postponed:

1. **Lighthouse CI workflow** at `.github/workflows/lighthouse.yml` — runs `lhci autorun` against the built frontend on every PR + push to `main`, asserting Core Web Vitals targets from `docs/PERF_BUDGETS.md` (LCP <= 2.5s, INP <= 200ms, CLS <= 0.1, FCP <= 1.8s, TTFB <= 0.8s) at the per-route p75 threshold.
2. **Bundle-size enforcement script** at `scripts/check-bundle-size.mjs` — runs after `pnpm build`, walks `.next/build-manifest.json` + `.next/app-path-routes-manifest.json` + the per-route chunk directories under `.next/static/chunks/app/`, computes the gzip-compressed size of each route's first-load JS, fails if any route exceeds **250KB compressed** (the `docs/PERF_BUDGETS.md` ceiling).
3. **`@next/bundle-analyzer` devDependency** in `frontend/package.json` — enables `ANALYZE=true pnpm build` to emit per-route bundle treemaps for human review (operator-side investigation tool; not gated in CI).

All three artifacts are pre-authorised in the v1.1 milestone-opening scope (per the spawn prompt: "The protected `.github/workflows/**` and `scripts/**` edits required by Phase 49 are pre-approved by the user as part of opening this milestone."). The `@next/bundle-analyzer` add lands in `frontend/package.json` (also protected; pre-approved). All three edits land in a single commit.

The roadmap line for Phase 49 reads "Phase 49: lighthouse-ci - .github/workflows/lighthouse.yml + scripts/check-bundle-size.mjs + bundle-analyzer dep (closes i-15)." Plan-author audit at HEAD (commit `1fefe67`, 2026-05-09; v1.1 Phase 48 just shipped) found:

**Why this is the right call here:**

- **i-15 has an enriched closure spec.** Phase 49 IS the closure window per the v1.1 milestone scope. The deferred-work playbook from `docs/PERF_BUDGETS.md`'s "Deferred (NOT in v0.6)" section enumerates the three artifacts; this plan ships exactly those three.
- **Single-commit cadence matches v1.0 / v1.1 standard.** All eight edits land together; CI validates the new workflow on the same push that defines it.
- **Stand-alone frontend Lighthouse coverage is the right v1.1 trade-off.** Auditing `/login`, `/`, `/offline`, `/_not-found` exercises the Web Vitals + bundle-size signal without requiring a CI-side backend boot. Authenticated-route Lighthouse coverage is a separate concern (deferred — the Out-of-Scope block records this).
- **Webpack-emitted manifests are the canonical bundle-size source.** Phase 48 locked the v1.1 frontend bundler at webpack via `--webpack` flag; the bundle-size script reads webpack's `.next/build-manifest.json` + `.next/app-path-routes-manifest.json` directly. If a future plan flips the bundler to Turbopack-as-default, the script needs an update; that future plan owns the change.
- **Bundle-analyzer is opt-in, not gated.** Per `docs/PERF_BUDGETS.md`'s "How to measure (operator)" section, the analyzer's treemap is operator-side investigation, not CI gating. Wrapping `next.config.ts` with `enabled: process.env.ANALYZE === "true"` keeps the production / CI build paths zero-impact (the wrap is a no-op when `ANALYZE` is unset) while enabling `ANALYZE=true pnpm build` for human review.
- **Bundle-size script is the gating mechanism, not the analyzer.** The analyzer produces an HTML report; CI cannot read HTML to make a pass / fail decision. The `check-bundle-size.mjs` script returns exit 0 (pass) or exit 1 (fail) based on per-route compressed-size computation against the 250KB ceiling. CI's `lighthouse.yml` `bundle-size` job invokes the script; the script's exit code is the gate.
- **Lighthouse CI thresholds match `docs/PERF_BUDGETS.md` verbatim.** No re-derivation; the doc is the source of truth (web.dev's published Web Vitals thresholds, recorded with the source URL). Future doc updates flow through to the workflow via a single-line edit in `.lighthouserc.cjs`.
- **Three-run averaging in lhci config.** Lighthouse measurements have intrinsic variance (network jitter, GC pauses); `numberOfRuns: 3` reduces flakiness without doubling CI minutes.
- **No `ci.yml` mutation.** The new workflow lives in its own file; mixing it into `ci.yml` would balloon that file's job count and complicate the existing concurrency-group scope. Separate workflow file = separate concurrency group = clean bisect.
- **`.lighthouserc.cjs` at repo root, not under `frontend/`.** lhci's working-directory default and its `startServerCommand` semantics make repo-root the canonical placement (`startServerCommand: "pnpm --filter ./frontend start"` references the frontend subpackage explicitly). This also keeps the file alongside `compose.yml` and `IDENTITY.yaml` which are both repo-root contracts.
- **CI is the verification backstop.** Local gates (the executor running `pnpm install`, `pnpm build`, `node scripts/check-bundle-size.mjs`, `npx lhci autorun --collect.url=http://localhost:3000/login`) validate the bump first; CI re-runs them as a regression backstop on push.

**Rejected alternatives:**

1. *Mix the lighthouse + bundle-size jobs into the existing `ci.yml`* — rejected. Concurrency-group scope, bisect cleanliness, and per-job runtime budget all favour a separate workflow file.
2. *Audit only the frontend stand-alone (no `pnpm build` in CI; just static assets)* — rejected. Lighthouse measures rendering performance which depends on a running server. Static-asset analysis is a different gate (covered by `check-bundle-size.mjs`).
3. *Audit authenticated routes (e.g., `/dashboard`) with a CI-side backend boot* — rejected as scope creep for v1.1. The Out-of-Scope block records this for v1.2+.
4. *Use `next-build-stats-tool` or `webpack-bundle-analyzer` directly instead of `@next/bundle-analyzer`* — rejected. `@next/bundle-analyzer` is the framework-native wrapper that handles the webpack vs Turbopack switch and integrates cleanly with `next.config.ts`. Direct webpack-bundle-analyzer would require manually wiring the webpack callback in `next.config.ts`.
5. *Write `check-bundle-size.mjs` in TypeScript and require a build step* — rejected. The script is a CI runtime utility; an `.mjs` ES-module file runs directly under Node 22 (CI's node version) without a TypeScript build. Keep the surface minimal.
6. *Use uncompressed (raw) bundle size as the gate instead of gzip* — rejected. `docs/PERF_BUDGETS.md` explicitly states "250KB compressed (uncompressed roughly 750KB)". Compressed is the doc-canonical metric. The script computes gzip via Node's built-in `zlib.gzipSync` against each chunk file's raw bytes.
7. *Separate "lhci" and "bundle-size" into two distinct workflow files* — rejected. Both gates run after the same `pnpm build` artifact and share the same `actions/setup-node` + `pnpm install` setup. Co-locating them in one workflow with two jobs (or one job with two steps) saves CI minutes by reusing the install + build cache.
8. *Run Lighthouse against the production-deployed environment* — rejected. The repo is the application; the homelab repo is the deployment. CI Lighthouse runs against the just-built artifact, not a live deployment.
9. *Add the budget thresholds inline in the workflow YAML instead of `.lighthouserc.cjs`* — rejected. `.lighthouserc.cjs` is the lhci-canonical config location; using a separate file keeps the workflow YAML focused on orchestration (setup, install, build, run) instead of policy (the thresholds).
10. *Pin `@lhci/cli` to `^0.13.x` instead of `^0.14.0`* — rejected without execute-time verification. The executor confirms the latest stable on the npm `latest` dist-tag (`pnpm view @lhci/cli dist-tags.latest`); whichever stable is current at execute time is the pin. RC / canary / pre-release versions are NOT acceptable.
11. *Add a `lighthouse` script to `frontend/package.json`* (`"lighthouse": "lhci autorun"`) — rejected as redundant. The workflow invokes `pnpm exec lhci autorun` directly; a top-level script alias is convenient for local use but not load-bearing. Optionally accepted at executor discretion if the local-developer ergonomics matter.
12. *Skip the `build:analyze` script and rely on direct `ANALYZE=true pnpm build` invocation* — rejected. The script-alias is two characters of YAML to add in `package.json` and a documented entry-point for operators reading `docs/PERF_BUDGETS.md`. Operator ergonomics matter.
13. *Defer the `@next/bundle-analyzer` add and ship only the workflow + script* — rejected. The doc explicitly enumerates all three (workflow + script + analyzer dep) as the deferred set; partial closure leaves i-15 partially open.
14. *Tighten the per-route ceiling below 250KB to be conservative* — rejected. The doc's 250KB is the locked-in ceiling. Lowering the threshold without doc revision creates a contract drift; if the threshold needs to move, update the doc first (separate sub-plan).
15. *Add a `lighthouse-budget-comment` GitHub-PR-comment integration* (e.g., `treosh/lighthouse-ci-action` for PR comments) — rejected as scope creep. v1.1 ships the gate; PR-comment ergonomics are a separate concern. The workflow's pass / fail status check is sufficient signal.
16. *Run Lighthouse on every commit, not just PRs + main pushes* — rejected. CI minutes; the `pull_request` + `push: branches: [main]` triggers cover the regression-detection surface without burning compute on draft commits.
17. *Use `pnpm dlx @lhci/cli` instead of adding `@lhci/cli` to devDependencies* — rejected. Adding to devDependencies pins the version in the lockfile; `pnpm dlx` would re-resolve on every CI run, which is slower and version-drift-prone.
18. *Require Lighthouse CI to upload reports to a public dashboard* (e.g., Lighthouse CI Server) — rejected as scope creep. v1.1 ships the gate, not the dashboard. Reports stay as workflow artifacts uploaded via `actions/upload-artifact@v4`.
19. *Bundle-size script reads `.next/standalone/.next/build-manifest.json` instead of `.next/build-manifest.json`* — rejected. The standalone trace is for runtime deployment; the bundle-size gate measures the build artifact's client chunks, which live under `.next/static/chunks/app/`.
20. *Re-defer i-15 to a v1.2 milestone* — rejected. v1.1 explicitly schedules i-15 for Phase 49 per the milestone-opening scope. The user pre-approved the protected-path edits. Deferring would be dishonest planning.

### Task 2: create `scripts/check-bundle-size.mjs`

**Action:** Create the file `D:/Workspace/Self/OpenSource/WorkoutHub/scripts/check-bundle-size.mjs` with the following content (ES-module Node script; runs under Node 22):

```js
#!/usr/bin/env node
// Per-route bundle-size gate. Walks the webpack-emitted manifests under
// frontend/.next, computes the gzip-compressed first-load JS size per
// route, fails with exit 1 if any route exceeds the threshold.
//
// Threshold source-of-truth: docs/PERF_BUDGETS.md (250KB compressed).
// Run AFTER `pnpm build` (or `pnpm build --webpack`); the script reads
// the build output directly.
import { readFileSync, statSync, readdirSync } from "node:fs";
import { join, resolve, dirname } from "node:path";
import { gzipSync } from "node:zlib";
import { fileURLToPath } from "node:url";

const ROUTE_LIMIT_BYTES = 250 * 1024; // 250KB compressed

const __filename = fileURLToPath(import.meta.url);
const repoRoot = resolve(dirname(__filename), "..");
const buildDir = join(repoRoot, "frontend", ".next");

function readJson(path) {
  return JSON.parse(readFileSync(path, "utf8"));
}

function gzipSizeOf(absPath) {
  const raw = readFileSync(absPath);
  return gzipSync(raw, { level: 9 }).byteLength;
}

function listFilesRec(dir) {
  const out = [];
  for (const entry of readdirSync(dir, { withFileTypes: true })) {
    const full = join(dir, entry.name);
    if (entry.isDirectory()) out.push(...listFilesRec(full));
    else if (entry.isFile() && entry.name.endsWith(".js")) out.push(full);
  }
  return out;
}

function main() {
  const buildManifest = readJson(join(buildDir, "build-manifest.json"));
  const appRoutes = readJson(
    join(buildDir, "app-path-routes-manifest.json")
  );

  const rootMain = (buildManifest.rootMainFiles || []).map((f) =>
    join(buildDir, f)
  );
  const rootMainSize = rootMain.reduce(
    (acc, f) => acc + gzipSizeOf(f),
    0
  );

  const routes = [];
  for (const [page, urlPath] of Object.entries(appRoutes)) {
    if (page.startsWith("/api/")) continue; // API routes have no client bundle
    if (page === "/_not-found/page" || page === "/_global-error/page") {
      // framework-internal; counted but not gated separately
    }
    const segDir = page.replace(/\/page$/, "").replace(/^\//, "");
    const chunkDir = join(buildDir, "static", "chunks", "app", segDir);
    let chunkFiles = [];
    try {
      chunkFiles = listFilesRec(chunkDir);
    } catch {
      // Some routes have no per-segment chunk dir (purely SSR). Treat
      // their first-load JS as rootMain only.
      chunkFiles = [];
    }
    const segSize = chunkFiles.reduce(
      (acc, f) => acc + gzipSizeOf(f),
      0
    );
    const total = rootMainSize + segSize;
    routes.push({ page, urlPath, segSize, total });
  }

  routes.sort((a, b) => b.total - a.total);

  const fail = [];
  console.log(
    "Route                                          Segment KB  Total KB"
  );
  console.log(
    "-------------------------------------------- ---------- ---------"
  );
  for (const r of routes) {
    const segKb = (r.segSize / 1024).toFixed(1);
    const totKb = (r.total / 1024).toFixed(1);
    console.log(
      `${r.urlPath.padEnd(44)} ${segKb.padStart(10)} ${totKb.padStart(9)}`
    );
    if (r.total > ROUTE_LIMIT_BYTES) fail.push(r);
  }
  console.log("");
  console.log(
    `Root-main shared (counted in every route total): ${(
      rootMainSize / 1024
    ).toFixed(1)} KB`
  );
  console.log(
    `Per-route ceiling: ${(ROUTE_LIMIT_BYTES / 1024).toFixed(0)} KB compressed`
  );

  if (fail.length > 0) {
    console.error("");
    console.error(
      `BUDGET FAIL: ${fail.length} route(s) exceed the 250KB compressed ceiling:`
    );
    for (const r of fail) {
      console.error(
        `  ${r.urlPath} -> ${(r.total / 1024).toFixed(1)} KB`
      );
    }
    process.exit(1);
  }

  console.log("");
  console.log("BUDGET OK: all routes under the 250KB compressed ceiling.");
}

main();
```

**Why:** This is the gating mechanism that produces a pass / fail signal CI can consume (exit 0 / exit 1). The script:
- Reads webpack's `.next/build-manifest.json` for `rootMainFiles` (the per-page-shared chunks).
- Reads `.next/app-path-routes-manifest.json` for the route -> file mapping.
- Walks `.next/static/chunks/app/<segment>/` for each route's per-segment chunks.
- Computes gzip size at compression level 9 (mirrors the production-served compressed size).
- Sorts routes by total size; prints a table; fails if any route exceeds 250KB.

The script is self-contained (Node built-ins only; no external deps); it runs cleanly in CI without any `pnpm install` step beyond the regular frontend install.

**Pre-edit hook:** `scripts/` is in `PROTECTED_DIRS`. The pre-edit hook will prompt; spawn prompt grants pre-authorisation. Acknowledge per the documented pattern.

**Verification:** Task 8 local-gate confirms `node scripts/check-bundle-size.mjs` against a fresh `pnpm build` produces exit 0 (assuming the codebase's current routes are all under 250KB; if any current route exceeds, this is a real regression that needs separate triage and Plan 49-01 is blocked pending that fix).
