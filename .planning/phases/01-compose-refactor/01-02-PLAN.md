<objective>
Finish Phase 1 by hardening the compose stack's lifecycle: healthchecks on every service something else depends on, the right `depends_on.condition`, and CPU + memory limits on all three containers per `docs/SELF_HOSTED_CONTRACT.md` sections 3.5 and 3.7.

Purpose: Prevents the cascade-startup-bug where the frontend boots before the backend is actually ready, and gives operators a known resource ceiling so the stack is predictable on smaller hosts. The healthchecks added here are PROVISIONAL (backend uses `/actuator/health`, frontend uses an HTTP probe of `/`) and will be re-pointed to `/healthz` and `/livez` in Phase 2 once those endpoints exist.

Output: Updated `compose.yml` with healthchecks on backend + frontend, frontend's `depends_on` switched to wait for backend `service_healthy`, and per-service `deploy.resources.limits.{cpus,memory}` blocks. Operator-visible defaults documented in a brief inline comment block at the top of the file.
</objective>

<task type="auto">
  <name>Task 1: Add backend and frontend healthchecks plus dependency condition</name>
  <files>compose.yml</files>
  <action>
Add a `healthcheck:` block to the `backend` service. Use the `/actuator/health` endpoint which already exists. The probe runs inside the container; `wget` is not in `eclipse-temurin:21-jre` so use a raw HTTP probe that does not need extra packages:

```yaml
healthcheck:
  test: ["CMD-SHELL", "curl -fsS http://localhost:8080/actuator/health || exit 1"]
  interval: 15s
  timeout: 5s
  retries: 5
  start_period: 30s
```

If `curl` is also missing from the JRE base image (verify by checking `backend/Dockerfile`), fall back to a tiny Java HTTP probe via the JRE itself:

```yaml
test: ["CMD-SHELL", "java -jar /opt/java/openjdk/lib/healthcheck.jar 2>/dev/null || (exec 3<>/dev/tcp/localhost/8080; echo -e 'GET /actuator/health HTTP/1.0\\r\\n\\r\\n' >&3; head -1 <&3 | grep -q '200 OK')"]
```

Pick whichever works - `curl` is preferred. If neither is available without modifying the Dockerfile, the safest minimal fix is to ensure `curl` is present in the JRE stage (one-line addition to `backend/Dockerfile` `apt-get install -y curl` step). Keep that change minimal and document it in the SUMMARY.

Add a healthcheck to `frontend`. Next.js standalone always responds to `/` once the server has bound. Node has no `wget` either; use the `node` runtime built-in fetch:

```yaml
healthcheck:
  test: ["CMD-SHELL", "node -e \"fetch('http://localhost:3000/').then(r => process.exit(r.ok ? 0 : 1)).catch(() => process.exit(1))\""]
  interval: 15s
  timeout: 5s
  retries: 5
  start_period: 30s
```

Update `frontend.depends_on` from the plain list form to the long form with condition per contract section 3.5:

```yaml
depends_on:
  backend:
    condition: service_healthy
```

Add a brief comment above the backend healthcheck noting that this is provisional and Phase 2 will re-point both probes to `/healthz` once the dedicated endpoints land.

Do NOT change resource limits in this task - keep the diff focused. Do NOT remove or alter the existing `db` healthcheck.

<task type="auto">
  <name>Task 2: Add resource limits to all three services</name>
  <files>compose.yml</files>
  <action>
Add `deploy.resources.limits.{cpus,memory}` and matching `reservations` to every service per contract section 3.7. Use these defaults (sized for maintainer's PC primary host but documented as tunable for smaller hosts):

```yaml
db:
  deploy:
    resources:
      limits:
        cpus: "1.0"
        memory: 512M
      reservations:
        cpus: "0.25"
        memory: 128M

backend:
  deploy:
    resources:
      limits:
        cpus: "2.0"
        memory: 768M
      reservations:
        cpus: "0.5"
        memory: 384M

frontend:
  deploy:
    resources:
      limits:
        cpus: "1.0"
        memory: 256M
      reservations:
        cpus: "0.25"
        memory: 128M
```

Add a comment block at the top of `compose.yml` (right under `services:` or as a leading file-level comment) summarising the defaults and pointing operators at `docker-compose.override.yml.example` (which Phase 6 will ship) for smaller-host tuning:

```yaml
# Resource defaults tuned for a single-host x86_64 home server.
# Total ceiling: 4 CPU + 1536 MB. Reservations: 1 CPU + 640 MB.
# To run on smaller hosts (Raspberry Pi etc.), override via
# docker-compose.override.yml (see docker-compose.override.yml.example
# once Phase 6 lands).
```

Note: under Compose v2 standalone (not Swarm), `deploy.resources.limits` IS honored by `docker compose up`; it has been since Docker 23.0. No `compatibility` flag needed. Do not switch to the legacy `mem_limit` / `cpus` keys - the contract uses the modern form.

Do NOT add `restart_policy` under `deploy:` - we already have the top-level `restart: unless-stopped` on each service which is the recommended Compose-standalone form.
  </action>

- `docker compose up -d` runs without warnings about ignored deploy keys
- `docker stats --no-stream` shows MEM LIMIT values matching the configured limits (proves Compose actually applied them)
  </verify>
  <done>
- All three services have explicit limits AND reservations
- Total ceiling documented inline
- `compose config` validates and `docker stats` shows enforced limits
  </done>
