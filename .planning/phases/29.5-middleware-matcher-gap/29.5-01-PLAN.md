<objective>
Phase 29.5 was inserted into v0.5 (sha 4be5d49) as a small, surgical frontend phase that closes a route-coverage gap surfaced by the 21-01 audit (Section 3c row "Missing from matcher (compared to `(app)/` route group): `/achievements/:path*`" and Section 6 net-new phases row `phase-29.5-middleware-route-coverage`). The frontend `next/server` middleware at `frontend/src/middleware.ts:14-26,42-54` gates the protected (app)-group routes via two parallel structures: (a) a `PROTECTED_PREFIXES` array used at runtime to decide whether to run the cookie check, and (b) a `config.matcher` array that scopes Next.js middleware execution. Both structures enumerate `/dashboard`, `/plan`, `/history`, `/exercises`, `/insights`, `/prs`, `/nutrition`, `/metrics`, `/profile`, `/export`, `/session` — but BOTH omit `/achievements`. The route exists at `frontend/src/app/(app)/achievements/page.tsx` and is reachable via the top nav (`frontend/src/components/nav.tsx:17`) and the bottom-nav scope (`frontend/src/components/bottom-nav.tsx:15-21` excludes it but the desktop nav surfaces it). Today an unauthenticated visitor to `/achievements` does NOT receive the matcher-driven redirect to `/login?next=/achievements`; instead the (app) shell renders, the `achievements-client.tsx` mount fires `GET /api/achievements/me` without a Bearer token, the API returns 401, and the user sees an error UX rather than the canonical login redirect.

The fix is two literal entries:

1. Add `"/achievements"` to `PROTECTED_PREFIXES` (array used at runtime by `middleware()` to decide whether to check the cookie).
2. Add `"/achievements/:path*"` to `config.matcher` (the Next.js compile-time array used to scope middleware execution to the protected route subtree).

Both arrays must be edited in the same commit because the matcher decides whether the function runs at all, and the prefix array decides what the function does once it runs. Editing only one yields a half-fix that's worse than the current state (matcher gates without prefix check is a no-op fall-through; prefix check without matcher never executes).

Cross-check: walk the (app)/ route tree and confirm no other route is missing. Per Glob at plan time, the (app) group contains: `dashboard`, `plan`, `history`, `exercises` (+ `[id]`), `insights`, `prs`, `achievements`, `nutrition`, `metrics`, `profile`, `export` (+ `ai`, `ai/apply`), `session/[id]`. After the patch, `PROTECTED_PREFIXES` and `config.matcher` enumerate all 12 (app)-group top-level segments. The `(app)/layout.tsx` itself is not a routable URL; the parenthesized group is a Next.js routing artifact that does not appear in the path. Sub-routes like `/exercises/[id]` and `/session/[id]` are already covered by the existing `:path*` suffixes; `/export/ai` and `/export/ai/apply` are covered by the existing `/export/:path*` entry. No other matcher additions are needed.

Tests: a NEW vitest unit suite for `middleware.ts` is added. The audit Section 7 row 29.5 calls out: "vitest unit | middleware matcher includes `/achievements/:path*` | needs Next middleware test scaffold (currently absent)". The plan delivers that scaffold. The suite imports the live `PROTECTED_PREFIXES` constant + `config.matcher` array (both already exported as named bindings; the plan re-exports `PROTECTED_PREFIXES` to make it testable — see Constraining Decisions) and asserts both arrays cover every (app)-group route via a single source-of-truth list. The middleware function itself is also tested: a mocked `NextRequest` that targets `/achievements` without the `wh.hasSession` cookie redirects to `/login?next=/achievements`; with the cookie, the request passes through (`NextResponse.next()`).

The plan is intentionally narrow: pure frontend middleware edit + new test suite; no backend, no migrations, no protected files, no `package.json` touch, no consumer page change, no nav rewiring. One sub-plan per audit verdict.
</objective>

**Constraining decisions (this planner; locked at plan time):**

- **Add to BOTH arrays in one commit, not just one.** The matcher and prefix arrays are coupled. Adding to only the matcher would re-run middleware for `/achievements/*` requests but the `isProtected` check would return `false`, so the function would `NextResponse.next()` and never redirect. Adding to only the prefix array would have no effect because the middleware would never run for `/achievements`. The fix MUST touch both arrays in the same edit.
- **Insert position: between the existing `prs` and `nutrition` entries in BOTH arrays.** This matches the visual order in `frontend/src/components/nav.tsx:11-22` LINKS array (`dashboard, plan, history, exercises, insights, prs, achievements, nutrition, metrics, profile, export`). The planner deliberately mirrors the nav order so a future reader can scan nav -> middleware in lockstep without mental remapping. Concrete: after `"/prs",` insert `"/achievements",` in `PROTECTED_PREFIXES`; after `"/prs/:path*",` insert `"/achievements/:path*",` in `config.matcher`.
- **Export `PROTECTED_PREFIXES` as a named const so the test suite can import it.** Today the array is module-internal. The plan converts the declaration from `const PROTECTED_PREFIXES = [...]` to `export const PROTECTED_PREFIXES = [...]`. The middleware function continues to read it via closure unchanged. Rationale: the alternative is a brittle source-text scan in the test (regex over `middleware.ts`), which would falsely-pass if a maintainer renamed the array. The export is the lightest possible change.
- **Test file location: `frontend/src/middleware.test.ts` (sibling of `middleware.ts`).** Per the project convention (verified via Glob `frontend/**/*.test.*`): test files sit next to the module they cover. The repo has no `__tests__/` directory pattern. Vitest's default include glob picks this up via `frontend/vitest.config.ts`.
- **Do NOT add a `session` redirect-cookie integration test.** The audit Section 7 row 29.5 calls for "vitest unit | middleware matcher includes `/achievements/:path*`". A unit test asserting both array contents AND a tiny smoke test of the redirect logic for `/achievements` is sufficient. Full e2e coverage (Playwright across all 12 routes) is out of scope; that's a v0.6 hardening phase if it's ever needed.
- **The redirect smoke test uses `NextRequest` + `NextResponse` directly, NOT a Next.js dev server.** Construct `new NextRequest(new URL("http://localhost/achievements"))` with no `wh.hasSession` cookie; call the live `middleware()` function; assert the returned `NextResponse` is a 307/308 redirect to `/login?next=/achievements`. Repeat with the cookie set; assert the returned response is `NextResponse.next()` (status 200, no `Location` header). This is the existing testing pattern other Next.js codebases use; no new test infra is required.
- **The matcher coverage assertion uses a single source-of-truth `(app)`-route list.** The test declares `EXPECTED_PROTECTED_ROUTES = ["dashboard", "plan", "history", "exercises", "insights", "prs", "achievements", "nutrition", "metrics", "profile", "export", "session"]` (12 segments) and asserts: (a) every entry has a matching `/<seg>` in `PROTECTED_PREFIXES`, (b) every entry has a matching `/<seg>/:path*` in `config.matcher`, (c) the array lengths match `EXPECTED_PROTECTED_ROUTES.length` (no extras, no duplicates).
