# Phase 34 - Plan 01: Rest-Timer Push Notifications

**Milestone:** v0.6 Operational Maturity
**Phase:** 34 - rest-timer-notifications
**Plan:** 34-01 (sole sub-plan)
**Status:** Not started
**Author date:** 2026-05-09

## Goal

When the user starts a rest timer during a session, deliver a notification when the rest interval ends, even if the screen is off, the tab is backgrounded, or the device is locked. Today's `notifyRestElapsed` (in `frontend/src/lib/push/rest-timer.ts`) only fires `registration.showNotification` from a foreground `setInterval`, which iOS/Android suspend aggressively when the page loses focus. Phase 34 closes that gap by routing rest-end alerts through the already-functional Web Push pipeline shipped in Phase 33.

## Architecture Decision: Server-side scheduled push, with a client-side fallback

**Decision:** **Server-scheduled** rest-timer push is the primary path. The client `POST`s a lightweight schedule request when a rest interval starts; the backend persists a row, an in-process scheduler dispatches a Web Push to that user's subscriptions when the rest interval elapses, and a row TTL/cleanup keeps the table bounded. The existing in-page `setInterval` UI (visible countdown) and the existing foreground `notifyRestElapsed` showNotification call stay as-is for the foreground/visible case; they are not the delivery channel for backgrounded states.

**Rejected alternatives (with rationale):**

1. *Pure client-side (Service Worker `setTimeout`)* - rejected. Service workers are aggressively terminated by the browser when idle (Chrome ~30s, Safari almost immediately). A `setTimeout` inside the SW will not survive a 60-180s rest. There is no portable "scheduled showNotification" API in production browsers (the `TimestampTrigger` proposal is Chromium-only, behind a flag, and not on iOS WebKit).
2. *Web Push self-trigger via service worker `push` event with a delay* - rejected. The push event handler must complete its `event.waitUntil` synchronously; you cannot schedule a future notification from inside it. The push has to arrive at the right moment from the server.
3. *Hybrid where the client also runs a fallback `setTimeout` inside a foreground tab* - **kept**, but as a UX-only fallback. If the page is in the foreground when the rest elapses, both the server push and the existing foreground `notifyRestElapsed` may fire. The notification `tag: "wh-rest-timer"` already deduplicates them (`renotify: false`). This is acceptable and matches Phase 33's `tag: "wh-reminder"` model.

**Why server-scheduled is the right call here:**
- The Web Push pipeline (VAPID, `WebPushNotificationDispatcher`, `PushSubscriptionRepository`, SW push handler) was built in Phase 33 specifically to wake a backgrounded device. Reusing it costs almost nothing.
- Rest intervals are short (typ. 30-300s) and bounded - no cron, no quartz, no persistent job queue is needed. A simple `ScheduledExecutorService` (or `@Scheduled(fixedDelay=...)` poller over a small table) is sufficient.
- Cancellation is trivial: when the user posts another set, finishes the session, or stops the rest, the client `DELETE`s the schedule. No window of time where the SW has to coordinate with the network.

## Scope

In scope:
- New backend endpoint pair: `POST /api/sessions/{sessionId}/rest-timer` (schedule) and `DELETE /api/sessions/{sessionId}/rest-timer` (cancel). Auth: existing JWT principal; the user must own the session.
- New backend table `rest_timer_schedules` (Flyway migration) keyed by `(user_id, session_id)`. One in-flight schedule per session, per user (set on insert, replaced on conflict).
- New backend scheduler bean that polls due rows every ~1s (configurable, default 1s) and dispatches via the existing `NotificationDispatcher` interface. Uses a `for update skip locked`-style claim or a row-level "dispatched_at" guard to avoid double-fire.
- Frontend wiring: when `useRestTimer.start(seconds)` is invoked from `session-client.tsx`, also `POST` a schedule request. When the timer is stopped/cleared (next set logged, session finished, manual stop), `DELETE` the schedule. Never block the UI on these requests; they are best-effort.
- Service-worker payload contract: identical to Phase 33's `{title, body, url}`, with `url` = `/session/{sessionId}` and a fixed `tag: "wh-rest-timer"` (already used by the foreground path) so both channels coalesce.
- i18n: localised title/body strings injected from the frontend at schedule time so the push body is in the user's language without backend i18n bundles. Keys added to `frontend/messages/en.json` + `frontend/messages/tr.json`.
- Tests: backend unit + WebMvc + Testcontainers slice; frontend vitest coverage of the schedule/cancel calls in the session-execution flow.

Out of scope:
- Persistent durable job queues (Quartz, ShedLock, DB-backed cron). Rest timers are short-lived; an in-process scheduler is enough. If we ever need horizontal scaling or restart durability, that is a follow-up issue, not this phase.
- Browser-native scheduled notifications (`TimestampTrigger`). Not portable.
- Editing or rescheduling: cancel + re-schedule is the contract.
- Snooze / "extra 30 seconds" interaction. Out of scope; can land later as a separate phase.
- Sound and vibration tuning beyond what `showNotification` opts into by default. Operator/browser controls these.

## Constraints

- Backend `mvn` is unavailable on the local Windows host (per `pending_ci_fixes` memory). All backend tests run in CI. The plan must list test files to add but cannot rely on a green local backend run.
- `.env.example` is permission-restricted; do **not** edit it. Document any new env vars in `docs/DEPLOYMENT.md` per the Phase 33 precedent.
- The Phase 33 push pipeline's `WebPushNotificationDispatcher` is `@ConditionalOnProperty(name = "app.push.vapid.private-key")`. When VAPID is not configured, the `LoggingNotificationDispatcher` is used. The rest-timer feature must continue to work (i.e. log the dispatch) when VAPID is absent - the schedule should still be created and "dispatched" via the no-op logging dispatcher, so end-to-end wiring tests work without a real VAPID key.
- Self-Hosted Contract: no new always-on background processes that hold resources beyond the existing app JVM. The scheduler must be a lightweight `@Scheduled`/`ScheduledExecutorService` inside the existing app process. No new container.
- All new API surfaces must round-trip through Zod schemas (`frontend/src/lib/api/schemas.ts`) per the Phase 25.5 parity rule.
- ApiError catalog: any new error codes must be added to the `ApiErrorCode` typed enum (Phase 22.5 helper). Likely: `REST_TIMER_SESSION_NOT_FOUND` and `REST_TIMER_INVALID_DURATION`. If the existing 404/400 generic codes are sufficient, keep the enum unchanged.
- No emojis anywhere. English code; Turkish-first user-facing strings via i18n.

**Migration shape** (`rest_timer_schedules`):
- `id` UUID PK
- `user_id` UUID NOT NULL (FK to users via app-level join, no DB FK constraint per existing convention)
- `session_id` UUID NOT NULL
- `fire_at` TIMESTAMP WITH TIME ZONE NOT NULL
- `localized_title` TEXT NOT NULL
- `localized_body` TEXT NOT NULL
- `click_url` TEXT NOT NULL
- `dispatched_at` TIMESTAMP WITH TIME ZONE NULL (sentinel; set when delivered; row pruned later)
- `created_at`, `updated_at` TIMESTAMPTZ DEFAULT now()
- UNIQUE `(user_id, session_id)` so re-scheduling a still-pending row is an UPSERT
- Index on `(fire_at) WHERE dispatched_at IS NULL` for the polling query

**Pick the next free `V<n>__` number** by globbing `backend/src/main/resources/db/migration/`. Update `V<n>` placeholder before commit. Migrations are immutable post-merge per CLAUDE.md.

**Verification:** Flyway boots; `RestTimerScheduleRepository` is a Spring Data interface with a `findFirstByDispatchedAtIsNullAndFireAtBefore(Instant now)` query and a `deleteByUserIdAndSessionId(UUID, UUID)` method.

### T2 - Backend service: schedule, cancel, dispatch loop

**Files:**
- New: `backend/src/main/java/com/workouthub/sessions/resttimer/RestTimerScheduleService.java`
- New: `backend/src/main/java/com/workouthub/sessions/resttimer/RestTimerScheduler.java`

**`RestTimerScheduleService`:**
- `schedule(UUID userId, UUID sessionId, int seconds, String title, String body)`: validates `seconds` (1..3600), confirms session exists and belongs to user (via `SessionRepository`), upserts a row with `fire_at = now + seconds`. Returns DTO. Throws domain exceptions mapped via `@ControllerAdvice`.
- `cancel(UUID userId, UUID sessionId)`: best-effort delete by `(user, session)`; idempotent (no-op if absent).

**`RestTimerScheduler`** (a `@Component` with `@Scheduled(fixedDelayString = "${app.rest-timer.poll-interval-ms:1000}")`):
- Reads up to N (default 50) due rows in a single transactional batch.
- For each row: marks `dispatched_at = now()`, then calls `notificationDispatcher.send(userId, title, body, clickUrl)` outside the row's update transaction (defensive: a notifier failure must not roll back the dispatched_at write or we'd double-fire on the next tick).
- A separate `@Scheduled` cleanup tick (default every 5 minutes) deletes rows where `dispatched_at < now - 1h`. This avoids growing the table.

**Verification:** Unit tests for service-level happy path, validation, and ownership; an integration test (Testcontainers + WebMvc slice) that schedules a row with `fire_at = now()`, runs the scheduler tick, and asserts that a fake `NotificationDispatcher` saw the call exactly once.

## Risks and Mitigations

- **Risk:** Push subscription pruning races - if the scheduler dispatches at the same instant a user unsubscribes, the GONE outcome from `WebPushSender` already prunes the row in `WebPushNotificationDispatcher`. No action needed.
- **Risk:** Multiple application instances (operator-scaled deploy) double-firing. *Mitigation:* the contract pins to single-instance deploys (Self-Hosted Contract). If horizontal scale ever lands, switch the row claim to `SELECT ... FOR UPDATE SKIP LOCKED` - documented as a follow-up issue, not a blocker.
- **Risk:** Clock drift between the JVM and Postgres. *Mitigation:* persist `fire_at` in UTC TIMESTAMPTZ; let Postgres `now()` drive comparisons; the JVM only computes `fire_at = now() + seconds` once at insert time. A few-hundred-ms drift is invisible to a user who is resting.
- **Risk:** A foreground tab + a push delivered to the same device produces two notifications. *Mitigation:* the SW push handler uses `tag: "wh-reminder"` and `renotify: false`, which coalesces. The foreground path uses `tag: "wh-rest-timer"`. These do not coalesce with each other today; if both arrive, the user sees two banners briefly. Acceptable per Phase 33 precedent. If undesirable, executor may align tags - see T6.
- **Risk:** A user with no push subscription (declined permission) schedules a row and the dispatcher logs to no-op. *Mitigation:* this is by design; the foreground in-page timer still completes. The row is still cleaned up by the cleanup tick.
