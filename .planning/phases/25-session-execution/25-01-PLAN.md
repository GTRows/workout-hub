Open the v0.5 Phase 25 (session-execution) work. Per the 21-01 audit Section 6 row 25 verdict, Phase 25 splits into FOUR sub-plans:

- **25-01 addSet schema + clientSetId foundation** (THIS PLAN)
- 25-02 IndexedDB enqueue path + drain on `online` event
- 25-03 typed ApiError code branching for `SESSION_FINISHED`, `SESSION_ALREADY_FINISHED`, `SESSION_ALREADY_ACTIVE`, `SET_NUMBER_DUPLICATE`
- 25-04 RPE input + edit-existing-set (`PUT /api/sessions/{id}/sets/{setId}`)

This plan delivers EXACTLY the foundation that 25-02..04 sit on top of: a Zod-validated request schema for `addSet`, a `clientSetId` field threaded end-to-end through the existing `addSet` wrapper and the production `session-client.tsx`, plus the offline queue (`session-set-queue.ts`) updated to carry the same `clientSetId` for replay-after-online.

The audit calls out two concrete gaps that this plan closes:

1. **`AddSetPayload` lacks `clientSetId`** (`21-01-AUDIT.md:443`). The backend has supported the field since Phase 15-04 (`SessionSetsService.java:62-101`, `SessionSet.clientSetId`, `findBySessionIdAndClientSetId`); without it the frontend relies on the DB `UNIQUE(session_id, exercise_id, set_number)` 409 dedupe path - a degraded contract. Threading `clientSetId` end-to-end restores the v0.4 idempotency design: a queued enqueue + drain replay collapses to the same row whether the network round-trip succeeded once or twice.

2. **No vitest unit suite for `AddSetPayload` Zod schema** (`21-01-AUDIT.md:577`). Today `addSet` accepts a `AddSetPayload` TypeScript type at the call boundary but does not Zod-parse the OUTBOUND payload before sending. The plan introduces an outbound `addSetRequestSchema` + a re-runnable test fixture so 25-02 / 25-03 / 25-04 can layer on without re-deriving the contract.
