<objective>
Phase 25-03 surfaces the typed `ApiError.code` values produced by the v0.4 backend in the user-facing session-execution UX. The 22.5-01 helper (`frontend/src/lib/api/api-error-codes.ts`, sha bf01c34) shipped `ApiErrorCode` constants, `isApiError`, `isApiErrorWithCode`, and `apiErrorCodeMessageKey`; the 25-02 plan (sha 8c9c5c8) used two of those codes (`SESSION_FINISHED`, `SESSION_ALREADY_FINISHED`) inside the offline drain's permanent-reject branch but left the BROADER UX unchanged. Today the user-facing session flow has three error surfaces - dashboard `startSession` mutation, session-execution `addSet` (live, online path) mutation, session-execution `finishSession` mutation - and none of them branch on `error.code`. A 409 from the backend reaches the user as silence (no toast / inline message at all on `addSet` because the mutation has no `onError` handler beyond the `OfflineQueuedError` sentinel; on `startSession` and `finishSession` the user sees nothing too, no toast nor redirect, just an unresolved button state). The result is the v0.5 UX gap called out by 21-01 audit Section 5 row "ApiError.code branching missing on dashboard start, session add-set, session finish".

This plan delivers the typed-code UX EXACTLY for the four codes named in 25-01's deferral list and consumed at the three production surfaces:

1. **`SESSION_ALREADY_ACTIVE`** raised by `POST /api/sessions/start` when the user clicks "Antrenmani baslat" on the dashboard while another session is already running. Today the click silently fails. After this plan: a toast / inline message tells the user a session is already active and offers to resume it (a resume CTA that routes to the active session's screen). The dashboard already has a `resumeTitle` UX path when `fetchActiveSession` returns a session - this plan reuses that screen by invalidating the `["sessions", "active"]` query so the dashboard re-renders into the resume state, plus a one-shot toast explaining the redirect.

2. **`SESSION_ALREADY_FINISHED`** raised by `POST /api/sessions/{id}/finish` when the user double-taps the finish button or finishes the same session in two tabs. Today the second click silently fails. After this plan: a toast tells the user the session is already finished and the user is routed to `/dashboard` (matching the success-path destination). Because the session row IS finished from the backend's perspective, the optimistic UX matches the success path - the session is in a terminal state regardless of who finished it.

3. **`SESSION_FINISHED`** raised by `POST /api/sessions/{id}/sets` when the user submits a set after the session was finished elsewhere (e.g. another device, another tab). Today the live-online submit silently fails (the mutation reaches `onError` but only branches on `OfflineQueuedError`; everything else is dropped). After this plan: a toast tells the user the session was finished while they were submitting and the user is routed to `/dashboard` so they can start a new session. The 25-02 drain path ALREADY handles this code as a permanent-reject (it drops the queued row and shows `session.queuedDropped`); 25-03 closes the matching online-path UX so the symmetry is complete.

4. **`SET_NUMBER_DUPLICATE`** raised by `POST /api/sessions/{id}/sets` when the `(session_id, exercise_id, set_number)` UNIQUE constraint fires (the rare case where `clientSetId` was somehow omitted - e.g. a pre-25-01 IndexedDB row from a real user's browser - and two writes collide on the natural key). Today the live submit silently fails. After this plan: a toast tells the user "set number conflict, refresh to continue" and the session query is invalidated so the next render picks up the canonical set list and `nextSetNumber` re-derives from the fresh `existingSets.length + 1`. NO automatic retry-with-bumped-set-number; the planner explicitly chose the visible "refresh and re-enter" path because an automatic renumber could mask a real concurrency bug (two browser tabs writing simultaneously) under a silent retry. The user-facing message is a clear, actionable toast plus the auto-invalidation that fixes the underlying state.

The plan is intentionally narrow: typed error UX at the three mutation `onError` paths + 4 new translation key strings (the key paths `errors.api.sessionAlreadyActive`, `errors.api.sessionAlreadyFinished`, `errors.api.sessionFinished`, `errors.api.setNumberDuplicate` were declared by 22.5-01's `apiErrorCodeMessageKey` resolver but the actual TR / EN strings have NOT shipped yet). No new module file. No new lib dep. No backend change. No migration. No queue change. No RPE input. No edit-existing-set wrapper. The 25-02 drain path's `SESSION_FINISHED` / `SESSION_ALREADY_FINISHED` branch is unchanged (it already covers the offline-replay symmetric case).
</objective>

**Constraining decisions (this planner; locked at plan time):**

- **Single shared toast slot per surface, NOT one slot per code.** Both `SessionClient` and `DashboardPage` get ONE `useState<string | null>` named `apiErrorToast` that the new `onError` branches set. Rationale: a user who hits two codes in succession (e.g. `SESSION_FINISHED` then a refresh races into `SET_NUMBER_DUPLICATE`) sees the most-recent message; stacking the two as separate toasts would clutter the screen. The existing offline / drained / dropped toast slots in `SessionClient` stay distinct because they describe DIFFERENT classes of UX (queue lifecycle vs. typed errors); merging them would conflate "your offline write is queued" with "your write was permanently rejected" and obscure the user's mental model.
- **`apiErrorCodeMessageKey` IS the resolver path.** The new branches in each `onError` call `apiErrorCodeMessageKey(err.code)` (since `isApiErrorWithCode` already narrows `err` to `ApiError`, `err.code` is `string | undefined`) to get the i18n key path. The `useTranslations` hook is bound to a specific namespace, but `next-intl`'s `useTranslations` accepts dot-separated child paths within that namespace, OR a top-level `useTranslations()` call (no arg) returns a function that accepts any full path. The plan locks: each `onError` handler calls `t(apiErrorCodeMessageKey(err.code))` where `t = useTranslations()` (no namespace arg). Rationale: the resolver returns a full path like `"errors.api.sessionFinished"`; rebinding the translator to a namespace would force the consumer to strip the prefix, which leaks the resolver's internal contract.
- **`useTranslations()` (no arg) is added alongside `useTranslations("session")` and `useTranslations("dashboard")` in the two consumer files.** This is the documented next-intl pattern for typed-key resolution; the existing `t("session.queuedOffline")` style does NOT change. Plan-locked: each consumer file holds TWO translation hooks, one feature-namespaced (existing) and one full-path (NEW). They are NOT merged into a single hook because the feature copy keys (e.g. `t("queuedOffline")`) are far more numerous than the typed-error keys and the existing namespaced calls work correctly today.
