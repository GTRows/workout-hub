<objective>
Phase 25-02 wires the existing offline IndexedDB queue (`frontend/src/lib/offline/session-set-queue.ts`) into the production session-execution surface (`frontend/src/app/(app)/session/[id]/session-client.tsx`). Per the 21-01 audit Section 4 row "subscribeOnline used in session-client.tsx? No" the three queue helpers (`enqueueSet`, `drainForSession`, `subscribeOnline`) ship as dead code today: the queue is fully implemented and unit-tested in `session-set-queue.test.ts`, but no production component imports any of the three. This plan fixes the v0.5 highest-impact gap by mounting the drain on the session client and routing offline-time submits through `enqueueSet` so a real user mid-set on a flaky tailnet keeps logging without losing data.

The 25-01 foundation (sha c981d34) is already in place: every outbound `addSet` payload carries a `crypto.randomUUID()` `clientSetId`, the backend honors it via `findBySessionIdAndClientSetId`, and the queue's `payload: AddSetPayload` field automatically carries the new id without any schema bump. The 22.5 typed-error helper (`frontend/src/lib/api/api-error-codes.ts`) is also live and exports `isApiError`, `isApiErrorWithCode`, `ApiErrorCode`, and `apiErrorCodeMessageKey`. This plan composes those two prior closures: the drain post-fn translates `ApiError` instances into the queue's `PostOutcome` shape, sinks "permanent" backend rejections (e.g. `SESSION_FINISHED`, `SESSION_ALREADY_FINISHED`) by surfacing a one-shot toast and dropping the queued item rather than retrying forever, and re-queues / leaves transient failures in place for the next drain.

Concrete deliverables:

1. **Online-aware mutation flow inside `ExerciseBlock`** (`session-client.tsx:153-190`). The `submit` function continues to generate a `clientSetId` per submit and continues to call `mutation.mutate(payload)`. The mutation's `mutationFn` is rewritten so it:
   - Reads `navigator.onLine` (jsdom and every supported browser ship it; default `true` in SSR).
   - When offline: `await enqueueSet(sessionId, payload)`, then THROWS a sentinel `OfflineQueuedError` (a small in-file class in `session-client.tsx`, NOT a new exported module) so `mutation` lands in `onError` and TanStack Query does NOT optimistically update `["sessions", sessionId]`. The thrown sentinel is caught in `onError` and is the signal to (a) clear the inputs (the row is "saved" from the user's perspective even though it hasn't shipped yet), (b) bump a queued-count badge state (read from `queuedCount(sessionId)` async), (c) show a one-shot offline toast with the i18n key `session.queuedOffline`.
   - When online: `await drainForSession(sessionId, drainPostFn)` BEFORE the actual `addSet` call, so anything queued during a brief offline blip ships first in FIFO order and the new submit ships last. The drain runs best-effort - any failures are captured but don't block the new submit. After the drain, `await addSet(sessionId, payload)` runs as today and the resolved `SessionSet` is returned to `mutation.onSuccess` unchanged.

2. **Drain-on-online useEffect inside `SessionClient`** (the parent component, NOT `ExerciseBlock`, so the subscription mounts ONCE per session screen and not once per exercise card). `useEffect` registers `subscribeOnline(handler)` exactly once on mount. The handler invokes `drainForSession(sessionId, drainPostFn)` then refreshes the session query (`qc.invalidateQueries({ queryKey: ["sessions", sessionId] })`) so the drained sets re-render. Cleanup unsubscribes on unmount; the empty deps array is fine because `sessionId` and `qc` are stable for the screen's lifetime (verified in plan-time read; both are passed as a prop / hook output and don't re-key the component). The same `useEffect` ALSO calls `drainForSession` synchronously on first mount (covers the case where the user opens the session screen with an already-populated queue from a prior flaky session).

3. **`drainPostFn` factory** - a small in-file helper (NOT a new exported module) inside `session-client.tsx` that closes over `sessionId` (via React closure) and produces a `(payload: AddSetPayload) => Promise<PostOutcome>` matching the queue's signature. Behavior:
   - Calls `addSet(sessionId, payload)`.
   - On resolve: `return { ok: true }`.
   - On reject with an `ApiError` whose `status === 409`: `return { ok: false, status: 409 }` (the queue's existing 409-as-already-saved drop path takes over).
   - On reject with an `ApiError` whose `code` is one of `ApiErrorCode.SESSION_FINISHED` or `ApiErrorCode.SESSION_ALREADY_FINISHED` (regardless of HTTP status): `return { ok: false, status: 410 }` - the synthetic 410 hits the queue's existing "non-409 HTTP error" branch which today STOPS the drain and leaves remaining items. To keep the queue's existing semantics intact (no new branch), the drain factory ALSO records the dropped item in a closure-scoped `permanentlyDroppedCount` counter so the drain wrapper can surface a `session.queuedDropped` toast after the drain resolves. NOTE: a follow-up task in this plan widens the queue's `drainForSession` to accept a small typed result distinguishing "permanent reject" from "transient stop"; see Task 4.
   - On reject with a transient/network error (anything else, including `ApiError` with status 5xx, fetch network throws, AbortError): re-throw so the queue's existing `try/catch` around `postFn` triggers the "stop the drain" path and the item stays in the queue for the next drain.

4. **Queue API extension: typed permanent-reject branch** (`session-set-queue.ts`). The existing `PostOutcome` is `{ ok: true } | { ok: false; status: number }` and the existing 409 path drops items. The plan extends `PostOutcome` to `{ ok: true } | { ok: false; status: number } | { ok: false; permanent: true; reason: string }` and updates `drainForSession` so a `permanent: true` outcome drops the item AND increments a new `dropped` sub-counter (the existing `dropped` counter), but the drain CONTINUES rather than stopping. The drain return type gains a `permanentlyDropped: number` field on `DrainResult` so callers can surface UX. Rationale: the queue's current binary "drop on 409 OR stop on anything-else" model cannot express "this row is permanently rejected by the server but the rest can still ship" - which is exactly the `SESSION_FINISHED` case where a user finished a session on another device while sets were queued offline.

5. **Translation keys** - 4 new keys per locale in `frontend/messages/{tr,en}.json`:
   - `session.queuedOffline` - one-shot toast when the live submit lands in the queue. TR: `"Internet yok - set kaydedildi, baglandiginda gonderilecek."`. EN: `"Offline - set queued, will sync when reconnected."`.
   - `session.queuedDrained` - one-shot toast when the drain successfully ships N items. TR: `"{count} bekleyen set gonderildi."`. EN: `"{count} queued sets synced."`.
   - `session.queuedDropped` - one-shot toast when the drain hits a permanent reject (e.g. session finished elsewhere). TR: `"Bazi bekleyen setler artik kaydedilemiyor (oturum kapanmis olabilir)."`. EN: `"Some queued sets could not be saved (session may already be finished)."`.
   - `session.queuedBadge` - the queued-count badge label. TR: `"{count} bekleyen"`. EN: `"{count} pending"`.

6. **Queued-count badge** in `SessionClient`. A small inline display (NOT a new component file - the existing `Card` / `CardDescription` primitives are sufficient) that shows the badge label only when `queuedCount(sessionId) > 0`. The badge sits below the session header `CardDescription`. Implementation: a `useState<number>(0)` for `queuedCount` plus a small `refreshQueued` helper that the mutation `onError`, the drain handler, and the initial mount all call. Plan-locked: NO TanStack Query wrapper for `queuedCount` - it's read-once-on-event, not a long-lived fetch, and pulling it into `useQuery` would over-engineer.

7. **Tests** - 1 NEW vitest suite for the augmented queue API (Task 4) and 1 augmented suite for `session-client.test.tsx` covering the 4 wiring branches (offline submit, online submit with no queue, drain on online event, drain on mount with pre-populated queue, permanent-reject drain showing the dropped toast). Total +1 new it-block in `session-set-queue.test.ts` and +5 new it-blocks in `session-client.test.tsx`.

The plan is intentionally narrow: queue extension + session-client wiring + 4 translation keys + tests. NO new exported module file. NO changes to `endpoints.ts`. NO RPE input (25-04). NO typed-error UX beyond the two SESSION_FINISHED-family permanent-rejects (25-03 ships the broader UX). NO Dexie schema bump. NO `package.json` mutation. NO backend change. NO migration. NO change to `(auth)/login/page.tsx` or any non-session route.
</objective>

- **`mutationFn` is rewritten in-place; NO new wrapper function file.** The existing `mutation = useMutation({ mutationFn: ... })` at `session-client.tsx:153-171` becomes ~12 lines longer (offline branch + drain-then-add online branch). - **Sentinel `OfflineQueuedError`.** A 5-line in-file class in `session-client.tsx`. Used to distinguish "the live submit landed in the queue" from "the live submit hit a real error". The mutation's `onError` checks `err instanceof OfflineQueuedError` to pick the queued-toast vs. the generic-error path. NOT exported. NOT a new module. Rationale: TanStack Query's `mutationFn` MUST throw to reach `onError`; a void-return is treated as success. A sentinel is the cleanest way to signal "queued" without faking a `SessionSet` response.
- **`drainForSession` is called BEFORE the new `addSet` in the online branch.** Order matters for FIFO replay: a user whose previous submits landed offline expects them to ship in the order they were entered, with the new submit appended last. Calling drain first preserves that ordering even if the new submit's POST resolves before the queue's items. If the drain hits a transient error mid-loop, the new submit STILL ships (the drain stops; the post-drain `addSet` runs unconditionally). This means the user's new live data ships even when the queued history is stuck on a server-side issue - which is the right tradeoff for active workout logging.
- **`drainForSession` is also called in `useEffect` on mount AND on every `online` event.** Three drain triggers total: mount, online event, post-mutation success. Rationale: covers the user reopening the session tab after a flaky period (mount), the device coming back online with the tab open (online event), and the brief-offline-blip case (post-mutation success drains anything that landed in the queue between this submit and the previous one). The `online`-event drain is debounced naturally by Dexie's serial transaction semantics; concurrent drains on the same session collide on the `try/catch` around `postFn` and resolve cleanly because each drain takes a fresh snapshot from `db.queuedSets.where("sessionId").equals(sessionId)`.

```ts
/**
 * Drains queued sets for a session by invoking postFn one row at a time.
 * - 2xx -> drop the item, increment `drained`.
 * - 409 (duplicate per UNIQUE constraint) -> drop the item, increment `dropped`.
 * - permanent: true (server says this row will never succeed; e.g. the
 *   session was finished elsewhere) -> drop the item, increment
 *   `permanentlyDropped`, CONTINUE the drain.
 * - Other HTTP error -> stop the drain and leave remaining items for retry.
 * - Network failure (postFn throws) -> stop the drain.
 */
export async function drainForSession(
  sessionId: string,
  postFn: (payload: AddSetPayload) => Promise<PostOutcome>
): Promise<DrainResult> {
  const db = getOfflineDb();
  const items = await db.queuedSets
    .where("sessionId")
    .equals(sessionId)
    .sortBy("id");

  let drained = 0;
  let dropped = 0;
  let permanentlyDropped = 0;
  for (const item of items) {
    let outcome: PostOutcome;
    try {
      outcome = await postFn(item.payload);
    } catch {
      break;
    }
    if (outcome.ok) {
      await db.queuedSets.delete(item.id!);
      drained++;
      continue;
    }
    if ("permanent" in outcome && outcome.permanent) {
      await db.queuedSets.delete(item.id!);
      permanentlyDropped++;
      continue;
    }
    if (outcome.status === 409) {
      await db.queuedSets.delete(item.id!);
      dropped++;
      continue;
    }
    break;
  }
  const remaining = await queuedCount(sessionId);
  return { drained, dropped, permanentlyDropped, remaining };
}
```

The order of branches matters: `ok: true` first (the happy path), then `permanent: true` (drop and continue), then `status: 409` (legacy dedup drop, also continue), then the implicit fall-through `break` for transient HTTP errors. The TypeScript discriminated-union narrowing handles each branch cleanly.
