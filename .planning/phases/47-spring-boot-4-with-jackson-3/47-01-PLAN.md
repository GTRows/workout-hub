## Goal

Land the most invasive backend migration in the project history in one CI-validated commit:

1. Bump `<spring-boot-starter-parent>` in `backend/pom.xml` from `3.5.14` to `4.0.6` (latest stable Spring Boot 4 on Maven Central as of plan-author time, 2026-05-09). The bump pulls in Spring Framework 7.0.7 / Spring Security 7.0.5 / Hibernate 7.2.12.Final / Jakarta EE 11 (Servlet 6.1.0, Persistence 3.2.0, Validation 3.1.1) / Netty 4.2.12.Final / Tomcat 11 / Micrometer 1.15.x via the Spring Boot 4 BOM.
2. Preserve the v1.0 Phase 41 i-14 closure by keeping the `<netty.version>4.2.13.Final</netty.version>` property override in `backend/pom.xml`. The Spring Boot 4 BOM ships Netty 4.2.12.Final by default; the existing override resolves the BOM dependency to 4.2.13.Final to retain the CVE-2026-42577 patch posture.
3. Migrate all 36 Jackson 2 source files from `com.fasterxml.jackson.*` to `tools.jackson.*` (Jackson 3 package family). The migration covers 7 main-source files (annotations, ObjectMapper consumers, JsonNode reader, JacksonConfig customizer) and 29 test files (28 Spring `@Autowired ObjectMapper` injection sites plus 1 standalone `new ObjectMapper()` site in `WebPushNotificationDispatcherTest`).
4. Flip the `JacksonConfig.java` Spring customizer surface. Spring Boot 4 ships TWO customizer surfaces: (a) the Jackson 3 `JsonMapperBuilderCustomizer` in `org.springframework.boot.jackson.autoconfigure` (the new default) and (b) the Jackson 2 compat `Jackson2ObjectMapperBuilderCustomizer` relocated to `org.springframework.boot.jackson2.autoconfigure`. Plan-author commits to Path B: rewrite the existing `JacksonConfig` to declare a Jackson 3 `JsonMapperBuilderCustomizer @Bean` so the auto-configured Jackson 3 `ObjectMapper` (lives at `tools.jackson.databind.ObjectMapper`) carries the same three customizations the Spring Boot 3.5 build had: register `JavaTimeModule` (`tools.jackson.datatype.jsr310.JavaTimeModule`), disable `WRITE_DATES_AS_TIMESTAMPS` (`tools.jackson.databind.SerializationFeature.WRITE_DATES_AS_TIMESTAMPS`), set serialization inclusion to `NON_NULL` (`tools.jackson.annotation.JsonInclude.Include.NON_NULL`).
5. Flip the `PrometheusMetricsController.java` actuator imports. Spring Boot 4 splits the actuator surface into per-feature autoconfigure modules; `PrometheusScrapeEndpoint` and `PrometheusOutputFormat` move from `org.springframework.boot.actuate.metrics.export.prometheus` (Spring Boot 3 monolithic `spring-boot-actuator`) to `org.springframework.boot.micrometer.metrics.autoconfigure.export.prometheus` (Spring Boot 4 `spring-boot-micrometer-metrics`). `spring-boot-starter-actuator` continues to pull this module transitively in 4.0.x; no `pom.xml` dependency add is required for this controller's compile path.
6. Close deferred issue **i-8b** in `.planning/ISSUES.md` (move from `## Open` to `## Closed` and append a closure note matching the i-1, i-2, i-4, i-5, i-6, i-7, i-8, i-9, i-10, i-12, i-13, i-14 precedent format).

4. **Spring Boot 4 Jackson customizer surface decision.** Two paths exist in Spring Boot 4 for customizing the auto-configured ObjectMapper:
   - **Path A (Jackson 2 compat, foreclosed):** Add `<dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-jackson2</artifactId></dependency>` and import `org.springframework.boot.jackson2.autoconfigure.Jackson2ObjectMapperBuilderCustomizer`. The `addModules`, `disable`, and `serializationInclusion` builder methods on `JsonMapper.Builder` (or its Spring wrapper) are the equivalents.

The Jackson 3 `ObjectMapper.readTree(...)` and `ObjectMapper.writeValueAsString(...)` API surfaces are source-compatible with Jackson 2's; no per-call rewrites are required.

7. **Jackson 3's `JsonProcessingException` removal.** Jackson 3 collapses the Jackson 2 exception hierarchy (`JsonProcessingException` extends `IOException` extends `Exception`) into a unified `tools.jackson.core.JacksonException` (extends `RuntimeException` — runtime exceptions in Jackson 3 instead of checked). This matters in TWO main-source catch sites: `AuditLogService.toJson` and `WebPushNotificationDispatcher.buildPayload`. Plan-author DECISION: keep the `try/catch` blocks but rename the caught type from `JsonProcessingException` to `JacksonException`. The behavior stays identical (catch -> log/wrap). Removing the try/catch entirely (since `JacksonException` is now unchecked) is rejected as scope creep; minimal-diff migration.

## Risk Assessment

This is the **highest-risk plan in the project history** because:

1. **Local Maven gap.** Plan-author cannot validate the migration locally; CI is the only gate. The blast radius of a CI failure is up to 39 files of unrelated test infrastructure.
2. **Customizer interface uncertainty.** The exact Spring Boot 4 Jackson 3 customizer interface name is unresolved at plan-author time. The executor MUST resolve at execute time.
3. **BOM transitive uncertainty.** The Spring Boot 4 BOM pulls in 5 major-version bumps simultaneously (Spring Framework 7, Spring Security 7, Hibernate 7, Jakarta EE 11, Tomcat 11). Any one of them could surface a runtime incompatibility not caught by static analysis.
4. **SpringDoc 3.x is not battle-tested in this codebase.** Plan-author has zero prior CI runs of SpringDoc 3.x against this `OpenApiConfig` + `ApiError` schema.
5. **Single-commit cadence.** A 39-file commit cannot be partially reverted; if CI goes red, the whole bump rolls back via `git revert`.

**Mitigations:**

1. **Mechanical migration shape.** The 36 Jackson file rewrites are import-line edits only (with the JacksonConfig and 2 catch-type renames as the load-bearing surface). The diff shape is uniform; bisect is irrelevant.
2. **Path B foreclosed against Path A.** The Phase 46-01 deferral note documents Path A's foreclosure rationale exhaustively; the executor cannot accidentally pick the wrong path.
3. **Existing test coverage is the regression gate.** The 28 `@Autowired ObjectMapper` integration tests + `OpenApiSurfaceIntegrationTest` + `ExportIntegrationTest` + `FullExportImportIntegrationTest` + `AuditLogIntegrationTest` + `WebPushNotificationDispatcherTest` all implicitly validate the migration. Any failure of the migration surfaces as a failing test, not as silent runtime drift.
4. **Failure-mode triage list is exhaustive.** Task 8's 8-item triage list covers the most likely failure modes; the executor has a deterministic playbook for each.
5. **Re-defer playbook is available.** If the failure is non-trivial, the executor can re-defer i-8b to a v1.2 milestone-opening sub-plan via the i-6 / i-7 / i-8 / i-8b precedent.

If the executor judges the migration is fundamentally blocked at execute time (e.g. SpringDoc 3.0.3 has no Spring Boot 4 compat OR Hibernate 7 surfaces a non-trivial entity validation failure OR the Jackson 3 `@JsonNaming` accessor is renamed), the executor MUST stop and emit a `<<orchestrate-result>>{"status":"blocked",...}<<end>>` tail block referencing this plan, NOT push partial work.
