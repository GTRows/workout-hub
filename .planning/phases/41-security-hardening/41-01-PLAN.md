# Phase 41 - Plan 01: Bump Netty to 4.2.13.Final (closes i-14) and audit-document brute-force lockout + refresh-token hashing + rate-limit posture

**Milestone:** v1.0 Release Hardening
**Phase:** 41 - security-hardening (rate limiting review, brute-force lockout finalization, refresh-token hash collision fix from pending CI memory; close i-14 Netty 4.2)
**Plan:** 41-01 (first sub-plan; closes deferred issue i-14 Netty 4.2.13.Final bump and resolves the roadmap's three named security scopes for v1.0)
**Status:** Not started
**Author date:** 2026-05-09

## Goal

Bump `<netty.version>` from `4.1.133.Final` to `4.2.13.Final` in `backend/pom.xml`, remove the corresponding `CVE-2026-42577` suppression block from `.trivyignore`, and close deferred issue **i-14** in `.planning/ISSUES.md`. Confirm via codebase audit that the roadmap's two other named v1.0 security scopes — "brute-force lockout finalization" and "refresh-token hash collision fix from pending CI memory" — already meet the v1.0 hardening bar without source changes, and capture the audit evidence in `.planning/STATE.md` so a future planner does not re-open the question.

The roadmap line for Phase 41 reads "rate limiting review, brute-force lockout finalization, refresh-token hash collision fix from pending CI memory; close i-14 Netty 4.2." Plan-author audit at HEAD (commit `931cb69`, 2026-05-09) found:

1. **Refresh-token hash collisions:** `AuthService.sha256Hex` hashes the full JWT bytes via `MessageDigest.getInstance("SHA-256")` and `HexFormat.of().formatHex(...)` (64-hex-char output). The `refresh_tokens.token_hash` column is `VARCHAR(128) NOT NULL UNIQUE` per `V7__refresh_tokens.sql` line 11 + `refresh_tokens_token_hash_unique` constraint. The earlier "pending CI fixes" memory entry that listed refresh-token hash collisions as a failing test was explicitly superseded on 2026-05-04 (per `pending_ci_fixes.md` "the earlier list of 5 failures is no longer current — those tests pass on `96d81b0`"). v0.4 / v0.5 / v0.6 CI runs all green on this surface. **No source change needed.**

2. **Brute-force lockout:** `BruteForceGuard` enforces 10 failures / 15-minute window / 60-minute lockout, throws `ResponseStatusException(HttpStatus.LOCKED, ...)` (HTTP 423) on `assertNotLocked`, records every login outcome in `login_attempts` (`V15__login_attempts.sql`) via `@Transactional(propagation = REQUIRES_NEW)` so the row commits even when the outer login transaction rolls back. `BruteForceLockoutIntegrationTest` covers the three threshold cases (under-threshold pass, at-threshold lock, post-cooldown unlock). All three tests pass on origin/main per the `pending_ci_fixes.md` 2026-05-04 update. **No source change needed.**

3. **Rate limiting review:** the codebase has zero generic-purpose rate limiter (no Bucket4j, no `RateLimit*` class, no `Throttle*` filter). The Self-Hosted Contract delegates application-level rate limiting to the operator's reverse proxy (Caddy / nginx / Traefik); per the v0.3 lock-in "Reverse proxy: out of scope; operator brings their own. Public exposure: tailnet-only; never assume public exposure in app code." The only in-process throttle is `BruteForceGuard` itself (per-email login throttle), which is sufficient for the password-grant attack surface. Adding a generic rate-limit filter (e.g. Bucket4j) would (a) duplicate operator-layer enforcement, (b) introduce a new runtime dependency outside the v1.0-hardening single-commit cadence, and (c) break the contract's "never assume public exposure" posture by acting as if the app were directly internet-facing. **No source change needed for v1.0; the brute-force guard plus operator-layer rate limiting is the canonical posture.** The audit finding is recorded in `.planning/STATE.md` so the question doesn't reopen.

4. **i-14 Netty 4.2.13.Final bump:** the only concrete security debt with a published fix and a real trigger. The plan closes it by bumping the existing `<netty.version>` override property and removing the matching `.trivyignore` entry.

## Architecture Decision: bump `<netty.version>` 4.1.133.Final -> 4.2.13.Final via the existing pom.xml property override; remove the `.trivyignore` suppression for CVE-2026-42577; let CI validate Spring Boot 3.5.14 + Netty 4.2 transitive compatibility on the servlet stack; record the brute-force / refresh-token / rate-limit audit findings in STATE.md without source changes

**Maven Central evidence (captured at plan author time, 2026-05-09):**

- `io.netty:netty-bom:4.2.13.Final` published on Maven Central with `<lastUpdated>` no earlier than 2025-Q1 per the upstream Netty release schedule. The 4.2.x line carries the fix for CVE-2026-42577 (epoll RST DoS); no 4.1.x backport is published or planned per the Netty advisory thread referenced in the original i-14 entry.
- Spring Boot 3.5.x BOM (currently pinned to 3.5.14 in this repo per `backend/pom.xml` line 10) declares `netty.version` as a managed property. Setting `<netty.version>4.2.13.Final</netty.version>` in `<properties>` overrides the BOM-declared default; this is the same override mechanism v0.5.0 used to pin 4.1.133.Final (commit `71a097d` per `git log` and CHANGELOG line 200-202).
- Netty 4.2 is API-compatible with 4.1 for consumers that use the public `io.netty.*` packages. The Netty maintainers published a "What's new in Netty 4.2" guide (linked from the Netty 4.2.0 release notes) explicitly documenting the 4.2 line as a drop-in successor for 4.1 with the same semver-major contract preserved within the `4.x` line. The internal package `io.netty.util.internal.*` is not part of the public API; no part of this codebase or its declared dependencies references it.
- `mvn dependency:tree` posture (inferred from `pom.xml` declared deps): Netty enters the classpath transitively via `spring-boot-starter-web` -> Tomcat (no Netty there), via `async-http-client` -> Netty 4.x HTTP client (one consumer), and via `spring-boot-starter-actuator` (no Netty). The `async-http-client` dep is itself an explicit override (`asynchttpclient.version=2.12.4`) added in v0.5.0 to close CVE-2024-53990; that 2.12.x line declares Netty 4.1.x as a peer but accepts 4.2.x because Netty preserved the public API surface. The web-push 5.1.2 transitive does not pin Netty independently.
- This application is Spring MVC + embedded Tomcat (servlet stack). It does **NOT** use Spring WebFlux, Reactor Netty, or any Netty server transport for inbound HTTP. Plan-author Grep audit at HEAD: zero matches for `WebFlux`, `reactor.netty`, or `spring-boot-starter-webflux` under `backend/`. Netty is on the classpath only as the HTTP transport for `async-http-client` (used by `nl.martijndwars:web-push:5.1.2` for outbound web push notifications). The CVE-2026-42577 epoll-RST surface is therefore not on the request-handling path; the bump is a defense-in-depth close, not a runtime-exposure fix.

**Rejected alternatives:**

1. *Bump to Netty 4.2.x latest (e.g. 4.2.14.Final or whatever is current at execute time) instead of pinning to 4.2.13.Final* — soft-rejected. The i-14 entry names 4.2.13.Final as the minimum fix version. If a newer 4.2.x patch ships before execute time and is on Maven Central, the executor MAY substitute it (the plan does not block higher 4.2.x patches). Document the version actually pinned in the commit message. Default to 4.2.13.Final if the executor doesn't audit the registry at execute time.
2. *Bump to Netty 5.x* — rejected. No 5.x line is published; the Netty roadmap explicitly froze 5.0 development in 2018 and resumed it as Netty 5 alpha series with no GA. The 4.2.x line is the current stable line. Even if 5.x were available, jumping a major-major boundary inside a v1.0-hardening sub-plan would violate the single-line-bump cadence that v0.5.0 / v0.6.0 / v1.0 Phases 39-40 all established.
3. *Add Bucket4j as a generic rate-limit filter to satisfy the "rate limiting review" roadmap line* — rejected. The Self-Hosted Contract delegates rate limiting to the operator's reverse proxy. Adding an in-process rate limiter would (a) duplicate operator-layer enforcement, (b) require a new runtime dep outside v1.0-hardening's single-commit budget, (c) require a Redis or in-memory token-bucket store decision (further scope creep), (d) require operator-facing config docs (Phase 42 docs scope, not 41 hardening scope). The brute-force guard plus operator-layer rate limiting is the canonical posture; the audit finding is recorded in STATE.md.
4. *Tighten the brute-force lockout thresholds (e.g. 5 failures / 5 minutes / 30-minute lockout instead of 10 / 15 / 60)* — rejected. The current thresholds are a v0.3 / v0.4 lock-in based on the trade-off between attack-surface reduction and legitimate-user friction (mistyped passwords on a phone keyboard). Tightening the thresholds in v1.0 hardening would be a behaviour change that requires user-facing release notes and might surprise existing operators. Out of scope for Phase 41-01.
5. *Migrate `BruteForceGuard` from email-keyed to (email, IP)-keyed lockout* — rejected. The codebase does not capture client IP at the login endpoint (Phase 1 lock-in); adding IP capture would require touching the controller, the entity, the migration, and the test suite. Out of scope for v1.0 hardening; would inflate the diff beyond a single-commit close. Track as follow-up if the maintainer wants the upgrade.
6. *Switch refresh-token hashing from SHA-256 to bcrypt or Argon2* — rejected. Refresh tokens are 256-bit JWT-signed random values (see `JwtService.generateRefreshToken`); they have full cryptographic entropy at issuance. SHA-256 is a fingerprint for unique-index lookup, not a password-style derivation; bcrypt/Argon2 would add ~100ms per refresh call for zero security gain (the JWT signature already protects against forgery; the hash protects only against DB-dump replay, which SHA-256 fully covers for non-guessable inputs). Out of scope.
7. *Add a uniqueness collision retry loop in `AuthService.issueTokens`* — rejected. SHA-256 collision probability for 256-bit JWT random inputs is cryptographically negligible (~2^-128 per pair). The DB UNIQUE constraint will throw `DataIntegrityViolationException` on the impossible collision; the controller's global `@ControllerAdvice` will return HTTP 500 — which is correct behaviour for an impossible state. Defensive code against impossible states is explicitly forbidden by `CLAUDE.md` "What NOT to Do".
8. *Move the Netty version override into a `<dependencyManagement>` block instead of `<properties>` substitution* — rejected. Spring Boot's parent BOM uses property substitution as the override mechanism; using `<dependencyManagement>` would override at a different layer and may not propagate to all transitive Netty modules (`netty-buffer`, `netty-codec`, `netty-codec-http`, `netty-common`, `netty-handler`, `netty-resolver`, `netty-transport`, `netty-transport-native-epoll`, etc.). The property-substitution path is the documented Spring Boot way and matches v0.5.0's working precedent.
9. *Bump async-http-client at the same time* — rejected. `asynchttpclient.version=2.12.4` is the v0.5.0 override that closed CVE-2024-53990. There is no published security advisory against 2.12.4 as of plan-author time. Bundling an unrelated bump would inflate the bisect-blame surface and is forbidden by the single-commit cadence.
10. *Run `mvn dependency:tree` locally to confirm the Netty transitive surface* — rejected. Local Maven gap (`local_maven_gap.md`) makes this impossible on the Windows dev host. The CI run will produce the equivalent evidence via the actuator startup logs and the integration test suite. Plan-author static audit (Grep for WebFlux / Reactor Netty zero matches; `pom.xml` declared-dep audit) is sufficient pre-execute evidence.
11. *Add a CI step that runs `trivy` against the locally built backend image to confirm the suppression removal does not surface a new finding* — rejected. The existing CI image-scan job already runs trivy against the backend image; removing the suppression and observing the green/red signal IS the validation. Adding a separate step is redundant.
12. *Update `CHANGELOG.md` to record the Netty bump under `## [Unreleased]`* — rejected. Spawn prompt explicitly says "no CHANGELOG, no workflows, no protected file beyond pom.xml". CHANGELOG rotation is Phase 44 release scope.

The contract already documents the reverse-proxy-out-of-scope posture; the plan-author audit is already recorded indirectly via the v0.3 lock-in. STATE.md is the canonical place for v1.0-cycle audit findings; SELF_HOSTED_CONTRACT.md is for operator-facing contract terms, not internal audit history.
