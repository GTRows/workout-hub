<objective>
Close the v0.5 Phase 26 (exercise-catalog) gaps left after the 21-01 audit verdict "narrow" (audit Section 6 row 26). The catalog list, filters (muscle/equipment/difficulty), debounced search, in-session detail modal, and standalone detail page are already shipped (audit Section 5 "Exercise catalog" rows: List / Filters / Search / Detail page / Detail modal all `Implemented`). The audit explicitly notes this phase is "over-shipped" relative to the v0.5 outline: the only operationally meaningful gaps the orchestrator narrowed against ProjectBrief Phase 5 (PB:365-369) are surfacing per-exercise PR + progress data inside the standalone `/exercises/[id]` detail page.

This plan delivers exactly that. The standalone detail page (`frontend/src/app/(app)/exercises/[id]/exercise-detail-client.tsx`, 94 lines today) currently renders bilingual name, description, form-tips, common-mistakes, primary/secondary muscle, and an `ExerciseMedia` block. It does NOT show:

- The user's current personal record on this exercise (max weight + reps + when achieved).
- Any progress chart from `GET /api/exercises/{exerciseId}/progress`.

Both endpoints exist and are wired in v0.4 backend (`ExerciseAnalyticsController` at `backend/src/main/java/com/workouthub/analytics/ExerciseAnalyticsController.java:32` for `/last-performance`, and the same controller at line 41 for `/progress`). Today the frontend wraps `/last-performance` (`fetchLastPerformance` at `endpoints.ts:179`, consumed only by the in-session detail modal) but does NOT wrap `/progress`. The audit's catalog-gap row (Section 4 4d "Backend endpoints with no frontend wrapper") flags `GET /api/exercises/{id}/progress` as the catalog-relevant missing wrapper and explicitly cites ProjectBrief Phase 4 ("how-to / tips / mistakes / PR / progress chart"). PR display is satisfied by surfacing the existing `last-performance` payload in the standalone detail page (its `bestSet` field carries the per-exercise top-weight set, so no new endpoint is required for PR). Progress chart requires the new `/progress` wrapper plus a recharts LineChart consumer.

**Constraining decisions (this planner; locked at plan time):**

- **`progressPointSchema` field types follow the wire shape.** `sessionId: z.string().uuid()`, `startedAt: z.string()` (ISO instant string; not coerced to Date - the consumer parses via `new Date()` at render time), `setCount: z.number().int()`, `totalVolumeKg: z.number()`, `maxWeightKg: z.number()`, `topRepsDone: z.number().int()`, `estimatedOneRmKg: z.number()`. Rationale: the backend rejects out-of-range values with a 400; clamping client-side surfaces a deterministic default for callers that pass unvalidated user input.
